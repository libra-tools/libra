## Document responsibility

Deliver complete, maintainable completion coverage for the public CLI that Libra actually implements. This document contains both the implementation plan and its executable task cards; the coverage ledger defined below is the per-parameter acceptance artifact.

### Scope

Every public command, subcommand, public alias, flag and value-taking argument in the compiled command tree, including Libra-only and feature-gated capabilities. Static coverage includes syntax, fixed choices and appropriate filesystem hints. Dynamic coverage adds existing repository/configuration objects where the command already accepts them.

### Non-goals

Do not implement missing Git behavior, new business commands, remote-branch guessing, new refspec semantics, schema migrations, credential discovery, or network-backed suggestions. Do not execute user hooks, automation actions, external agent binaries or shell configuration edits. Hidden internal commands receive an explicit exclusion record. Free text, secrets and newly created identifiers are classified deliberately, not populated with misleading existing-object candidates.

### Success definition

1. Every current public command and argument has an explicit coverage disposition and owner.
2. Static completion is independently accepted and released before any dynamic implementation begins.
3. Dynamic mode is opt-in and preserves the accepted static mode.
4. Candidates match the consuming command's existing value semantics, identity scope and context.
5. Both stages have real shell evidence, documentation, release coverage and reconciled tracking.

## Coverage ledger and scope contract

CP-00 produces `docs/development/plan/plan-20260923-coverage.tsv`. It is a reviewed inventory, not a second hand-maintained command parser. Columns:

`command_path`, `arg_id`, `feature_profile`, `source_anchor`, `accepted_semantics`, `static_disposition`, `dynamic_disposition`, `candidate_source`, `context_and_scope`, `owner`, `test_case`, `status`, `reason`.

Allowed dispositions: static `grammar`, `fixed-values`, `file`, `directory`, `free-text`, `secret`, `new-name`, `hidden`; dynamic `existing-object`, `reuse-provider`, `not-applicable`, `external-deferred`, `unassigned`. Every public node and argument must appear, including valueless flags; hidden entries carry a reason. `unassigned` is an audit failure, never a completion-state exemption. A missing underlying capability is `not-applicable` with handler evidence, not a task to implement that capability.

The inventory must cover default and supported feature-dependent CLI trees (including fastcdc media and platform/worktree-fuse surfaces). Do not enable live services merely to enumerate commands. Public aliases must be accepted as invocation paths; whether a non-visible alias is advertised follows current clap visibility. Annotation changes must not accidentally narrow accepted command input.

| Coverage family | Mandatory survey | Initial dynamic owner |
|---|---|---|
| Setup/configuration | init, clone, config, completions, accepted global arguments | CP-09 or CP-19 for eligible local names/keys |
| Working tree | add/rm/mv/restore/clean/status, paths, worktree, stash, sparse-view, hydrate, lfs/media | CP-10/11/19; filesystem hints in CP-03 |
| History/refs | all implemented revision consumers, including plumbing and Libra revision command | CP-08; index-aware paths in CP-19 |
| Remote/cloud | remote/fetch/pull/push, cloud/cache/auth/mega2 and other shipped commands | CP-09/19; no network or credential suggestions |
| Captured agents | names, sessions, checkpoints, workspaces, graph and public filters | CP-12..15; agent push --remote uses CP-09 |
| Automation/local extensions | automation, op, layer, metadata, deps, alternates, review/investigate/sandbox/service | CP-16..19; unsuitable free text is explicitly classified |

Existing-object arguments and creation destinations are different. Support local remote-tracking refs, special refs, revision expressions or refspec components only where the current consumer accepts them. CP-00 records that evidence per parameter. Git documentation can inform UX but cannot add acceptance semantics. Stash and basic worktree completion belong to shared Git-like workflows; agent workspace/doctor behavior remains Libra-specific.

Any uncovered eligible existing-object domain discovered by CP-00 becomes a bounded named card before implementation approval. CP-19 checks for omissions; it is not an unlimited implementation bucket. No fixed estimate of card count can override complete coverage.

## Accepted design decisions

### ADR-CP-01: Capability-led scope

- **Status:** Accepted (user direction, 2026-09-23).
- **Context:** Copying Git ignores Libra's implemented contracts and unique objects.
- **Decision:** Inventory actual public CLI behavior and cover all suitable parameters.
- **Alternatives considered:** Git parity checklist as scope authority; rejected.
- **Consequences:** Unsupported business behavior stays outside this plan; undiscovered domains must be assigned before implementation.
- **Revisit when:** Current commands or supported features change.

### ADR-CP-02: Static acceptance precedes dynamic implementation

- **Status:** Accepted (user direction, 2026-09-23).
- **Context:** The static baseline is not yet exhaustively verified.
- **Decision:** CP-06 is a hard barrier before CP-07; keep default AOT output. Add explicit --dynamic only in stage two, retaining the existing shell/script JSON data contract.
- **Alternatives considered:** Immediately replace static output; rejected.
- **Consequences:** Both modes remain tested; dynamic is optional, not a prerequisite for static installation.
- **Revisit when:** A separately approved compatibility decision changes the default.

### ADR-CP-03: Metadata and providers supplement one command tree

- **Status:** Proposed implementation design, subject to plan review.
- **Context:** Scattered candidate rules drift; one giant registry card is not independently reviewable.
- **Decision:** Use src/internal/completion/{mod.rs,static_metadata.rs,registry.rs,context.rs,providers/}; supplement the real clap tree without changing command parsing. Fixed choices must already be enforced/recognized by handlers. Validate every path/arg ID against the compiled tree.
- **Alternatives considered:** Reconstructing commands in a parallel parser; rejected. If the pinned API cannot attach required metadata without changing validation, use bounded derive annotations with revised write sets/cards before implementation.
- **Consequences:** No silent fallback to edits across 15+ command files; G-03/G-04/G-10 are rerun first.
- **Revisit when:** The pinned clap API cannot preserve the input contract.

### ADR-CP-04: Bounded read-only dynamic requests

- **Status:** Proposed implementation design, subject to plan review.
- **Context:** TAB must not execute normal command preflight or migrations.
- **Decision:** Intercept only recognized completion requests before side-effectful startup; preserve normal invocation otherwise. Local sources only. Expected unavailable data yields empty candidates with exit 0 and clean stderr; diagnostics are opt-in, sanitized and outside the completion stream.
- **Alternatives considered:** Calling list/mutation CLI handlers; rejected because they may bootstrap, migrate or produce unrelated output.
- **Consequences:** Repository, GlobalConfig and SystemConfig are read-only roles; Derived has no persistent writer. Migration/bootstrap/top-up allowlists are empty for every role. Unknown/new schemas return no candidates. Existing path-resolution semantics are reused without migration.
- **Revisit when:** A future explicit product requirement needs remote suggestions.
