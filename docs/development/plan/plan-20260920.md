## 文档职责

本文解决：在「只保留外部 Agent 观测与 traces」的产品前提下，如何把 `libra code` 从公开命令、嵌入式 Web、内部执行器与测试/CI 面完整拆除，并同时拆除只服务该产品线的 Cloudflare Publish/Worker 宿主，同时让 `libra agent` 捕获主线与 `libra cloud` 仓库备份继续编译与运行。

目标是：一份可执行的拆卸队列——先抽出捕获仍依赖的共享缝，再按家族卡一次性删除公开 Code **与** Publish 表面（breaking `minor` `0.23.0`），最后删除内部模块、`worker/` 与 Code UI 测试。落地时每张卡必须先按 ER-02 重核源码锚点。

### 非目标

- **不**写 `ai_*` 表的 down-migration，不物理回收既有 `refs/libra/intent` 对象（DEFER-RC-01 / DEFER-RC-02）。

- **不**删除 `libra cloud` 仓库备份，不删除 `upgrade` / `release.yml` 的 signed-manifest **release publish**（名字含 publish，不是 `libra publish`）。
- **不**改 `libra agent bridge` 的 20-method v1 协议（plan-20260818 已完成）。
- **不**删除 `libra automation`：它被 `add`/`commit`/`push`/`branch`/`switch` 的 VCS 事件路径调用，不是闲置的开发-agent 工具（ADR-RC-07）。

- `libra agent status|list|session|checkpoint|import|doctor|push|graph|bridge` 与只读 `review` / `investigate`、`sandbox`、`automation`、`cloud`、非 `libra+cloud` 的 `clone` 在 focused + 收口全量下保持绿。

- `COMPATIBILITY.md`、命令文档 EN+zh、error-codes、测试索引、`plan-long.md` 与网站文档已同步。
- 全部非延后卡 `Lifecycle=done` 且 `Acceptance=complete`；全量收口门绿。满足这些之后，本计划才可标记完成。

- **Status:** Accepted
- **Context:** 用户确认目标是只保留外部 Agent 观测与 traces，并再次要求分析「可否拆除 Code 的全部功能」。捕获与 Code 在 Gate 8 已是两条轨道。
- **Decision:**
  1. 留下：`libra agent` 全套、只读 `review` / `investigate`、`agent bridge --stdio`、`sandbox`、`automation`、`service`、`refs/libra/traces`、`agent_*` / `agent_bridge_*`、`.libra/sessions/agent/`。
  2. 拆除：`libra code`（含 control / MCP stdio / Web UI / AgentRuntime 执行器）、顶层 `libra graph`、`review --fix`、`investigate fix`、`session promote --as-intent`、`libra usage`、未接线 `libra package` 模块、`libra publish`、`libra clone libra+cloud://`、仓库根 `worker/`。

- **Alternatives considered:** 只删 CLI、保留库内 runtime（拒绝：继续支付 10 万行与凭据面）。把 `--fix` 改接到外部 agent（拒绝：本计划非目标；违反 Gate 8）。

- **Revisit when:** 另立计划要重建内部执行器。

### ADR-RC-02: 公开删除一次 breaking `minor` `0.23.0`，无 deprecation bake

- **Status:** Accepted
- **Context:** ER-08 允许 `minor`/`major` 用于删除公开表面。W5 删除 TUI / `code-control` 用家族点 `v0.20.0`；DF-08 删除 SSE v1 用 `v0.22.0`。用户要求全面拆除，不要半残兼容层。

  2. REL-RC-PUB 家族子卡不 bump；唯一发布点 RC-14 把版本从当时的 `0.22.x` **一次**升到 `0.23.0`（`Version increment = minor`），同步**当时仍存在的五处**版本面（`worker/package.json` 尚未删），`gh release create v0.23.0`。RC-36 之后 bump 改为四处。

### ADR-RC-08: 先断 CLI，后按 rustc 边删文件

- **Status:** Accepted
- **Context:** grok R2：`pub mod web` / `pub mod code` 仍编译，因此「CLI 已删、文件可先 rm」不成立。`web/mod.rs` 与 `code.rs` 仍 `use command::graph`；`orchestrator` 仍调 `runtime::phase1/phase2`；`sources` 与 `sandbox` 仍 `use tools`。`tests/command/mod.rs` 无条件 `mod` Code/usage 集成测试；`compat_agent_architecture_guard` 读 `code.rs` / `runtime/mod.rs` 并要求文档含 `Web Code UI`。
- **Decision:**
  1. Phase 2 家族子卡只删除**公开 argv / help / 命令文档 / COMPATIBILITY 行**（RC-34 例外：必须改写 `clone.rs` 去掉 `libra+cloud` 源，否则 RC-35 无法删类型）。`src/command/{code,code_control,code_control_files,graph,usage,publish}.rs` 的物理删除不得发生在仍有生产 `use` 的树上。**RC-15 不得 `rm usage.rs` / `pub mod usage`**（与 RC-12/13 对 `graph.rs`/`code.rs`、RC-33 对 `publish.rs` 相同）；`code`/`graph`/`usage` 文件删除在 RC-23；`publish.rs` / `internal/publish/` 删除在 RC-35。
  2. ### ADR-RC-09: 删除 Publish 产品（CLI + `libra+cloud` clone + Worker），保留 `cloud` 备份与 release publish

- **Status:** Accepted
- **Context:** 成稿把 `libra publish` 当 KEEP，并为此立 RC-17 抽 projection。DEFER-RC-07 把 `worker/` 标成「publish 另议」。用户 2026-09-18 要求在本拆除计划新增删除 Worker 与 Publish。`clone.rs` 的 `libra+cloud://` 源读已发布 D1/R2 站点，与 `libra cloud` 仓库备份不是同一条管线。
- **Decision:**
  1. `0.23.0` 起删除公开成功路径：`libra publish`（任意子命令）与 `libra clone libra+cloud://…`。迁移提示指向 `libra cloud` / 普通 git remote clone。
  2. 不保留「只读 clone 已发布站点」半残面：留下会锁住 `PublishStorage`、`sql/publish/`、`d1_client` publish API 与 `internal/publish/contract`，等于没删 Publish。
  3. Phase 3 删除 `src/command/publish.rs`、`src/internal/publish/`、`src/utils/storage/publish_storage.rs`、`sql/publish/`、`d1_client` 的 `ensure_publish_schema` / `Publish*Row` API、`cloud::create_publish_storage`、全部 `publish_*` 测试 target、`live-compat.yml` 的 `publish_live_test` 步。
  4. 随后删除仓库根 `worker/`（含 `worker/package.json`），版本面改为四处（ADR-RC-03）。
  5. **保留** `libra cloud`（`create_r2_storage` / D1 备份 schema）、`libra clone` 的 git/https/ssh/file 源、`upgrade_publish_contract_test` 与 `release.yml` 的 signed-manifest publish。
  6. 本计划不对远端 publish D1/R2 做 down-migration 或远程 `unpublish`。已部署 Worker 继续跑到运维另撤。`cloud.clone_domains.*` 配置键冷冻，不再读取。
  7. RC-17 不再抽缝；`projection/` 等 RC-35 删掉 publish 文件后再由 RC-23 删除。
- **Alternatives considered:** 只删 CLI、保留 `libra+cloud` 读路径（拒绝：半残产品 + 编译锁）。只删 `worker/`、保留 `libra publish sync`（拒绝：无宿主的 writer）。把 clone-from-publish 抽成 KEEP 薄模块（拒绝：用户要求删除 Publish，不是再养一条只读宿主）。
- **Consequences:** 不能再从本二进制发布或从已发布站点 `libra+cloud` 恢复。仓库备份与 Git 互操作不受影响。
- **Revisit when:** 另立计划要重建只读站点宿主。
