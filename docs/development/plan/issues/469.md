> 状态：设计计划；全部任务卡 `pending`，尚未进行 Codex review（见「Codex review log」）。

## 文档职责

issue #469 报告：一次携带 33 个路径的 `libra add` 以 `LBR-IO-002` 失败，原因是等待 object-index repair **generation 锁**超时，错误文案称「another Libra process may be stalled」；但当时没有任何 Libra 进程，锁文件是 12 小时前留下的零字节文件，逐个 `add` 同样的文件则全部成功。issue 提出四项后续：确认批量 `add` 是否在同一进程内争用该锁、改为每次调用只取一次锁或容忍进程内争用、修正误导性文案、重新考虑「对象已存储但 marker 注册失败」时是否应放弃整个 `add`。

本计划在当前 libra 0.22.28 上复核，结论分三类：

- **已修复的根因（进程内争用）：**
  - 0.22.10 的后台 index 更新消费者在 SQLite 重试期间持有仓库级 generation 锁，前台发布下一个 marker 时只等 2 秒便超时，这是 issue 猜测的进程内自我争用。
  - 该路径在 v0.22.16 → v0.22.17 之间改为只取 OID 分片锁，源码注释写明「Keeping that repository-wide lock across SQLite retries would let the consumer starve the next foreground marker publisher」（`src/utils/client_storage.rs:655-660`）。
  - 当前 33/500/3000 文件批量 `add` 全部成功（R1），但仓库内没有守住这一行为的回归测试。
- **仍然存在的问题：**
  - 跨进程争用仍会让 `add` 失败：另一个进程持有 generation 锁超过 2 秒时，`add` 以 `LBR-IO-002` 失败且不暂存任何文件（R2′）。
  - 只读命令（如 `status`）的预检回放会取 generation 锁并批量回放 marker（R6′），在慢速外置卷上足以超过 2 秒预算。
  - 超时文案始终断言「another Libra process may be stalled」，不区分持有者是本进程、存活的其它进程还是无人持有。
  - 每个对象单独获取一次 generation 锁并单独 fsync marker：3000 文件 `add` 耗时 9.17 秒（git 1.39 秒），并在锁目录留下 5773 个文件（R1）。
  - 失败时错误链出现重复前缀 `state facet capture failed: facet capture failed:`（R2′），且没有说明对象已安全写入、直接重试即可。
- **issue 中不成立或无需改动的部分：**
  - 零字节旧锁文件本身不会阻塞获取：锁基于 `flock`（Windows 为零共享句柄），进程退出即释放（R4）。
  - 锁文件目录上限为 65,536 个分片加 1 个 generation 文件，属于设计内的持久命名空间。

本计划交付 5 张卡，完全解决 issue 描述的问题：
1. **OI-01：** 为已修复的进程内争用补回归守卫。
2. **OI-02：** 锁持有者识别与分情形诊断文案。
3. **OI-03：** Git 式退避等待、延长发布方预算，只读命令预检回放忙时跳过。
4. **OI-04：** 每批只取一次 generation 锁发布 marker。
5. **OI-05：** `add` 失败语义保持原子，但文案说明对象已安全存储并去掉重复前缀。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `src/utils/client_storage.rs` 的 object-index repair 锁：generation 锁与 OID 分片锁的获取、等待、超时文案与持有者元数据。
- marker 发布路径：`ClientStorage::put` 系列与操作日志快照捕获（`src/internal/operation/snapshot.rs`）的对象写入。
- CLI 预检回放（`src/cli.rs` 的 `repair_pending_object_index_updates_before_command`）与后台消费者。
- `add` 在 marker 注册失败时的错误契约与文案，以及共用该存储层的 `commit`、`hash-object`、`update-index` 文档中的错误说明。
- 同步：`docs/commands/{add,commit,hash-object,update-index,cloud}.md` EN + zh-CN、`docs/development/commands/add.md`、`docs/error-codes.md` 示例列、`COMPATIBILITY.md` add 行、`../libra-backend` 网站 add 页。

### 非目标

- 删除或回收锁目录中的旧锁文件：`flock` 与 `unlink` 并发存在经典竞态，删除可能让两个进程同时「持有」同一路径的不同 inode（DEFER-01）。
- 新增超时配置键（如对应 Git `core.filesRefLockTimeout` 的 Libra 配置）（DEFER-02）。
- 并发两个 `add` 时第二个被 Operation Log v2 租约拒绝并报 `LBR-INTERNAL-001`（R5′）：属于 `plan-20260822` 的租约分类问题，不在本 issue 描述范围（DEFER-03）。
- 批量 `add` 中与锁无关的性能差距（逐对象 blob 写入与索引刷新）（DEFER-04）。
- 改变 `LBR-IO-002` 的稳定错误码或退出码（ADR-OI-05）。

### 成功定义

- 判据矩阵 M-GUARD、M-DIAG、M-WAIT、M-BATCH、M-FAIL 全部行由测试或手工证据证明，并附 git 2.54 语义对照（锁超时与失败原子性）。
- issue 的原始形态（带 130 余个旧锁文件的仓库、33 个修改文件一次 `add`）在当前实现与每张卡发布后都成功。
- 另一个进程持有 generation 锁 5 秒时，发布方在 10 秒预算内等待成功；持有超过预算时，错误文案准确指出持有者（存活进程的 pid 与用途、本进程、或无法判定）。
- 3000 文件批量 `add` 的 generation 锁获取次数不超过 ⌈3000/256⌉ 加常数，并记录前后耗时对比。
- 5 张卡各自完成 C 组发布并取得 D 组证据，然后全量收口门全绿；issue 只在全部卡片完成后关闭。

### Git 锁语义参照

| 场景 | git 2.54 |
|---|---|
| `git add` 时 `.git/index.lock` 已存在（RG） | 立即失败 exit 128：`fatal: Unable to create '<path>/index.lock': File exists.` 与 `Another git process seems to be running in this repository, or the lock file may be stale`；暂存区不变 |

### ADR-OI-01: 判据矩阵

- **Status:** Accepted
- **Context:** issue 未给出确定性复现；需要可自动化的判据。
- **Decision:** 使用事实基线实测与下列矩阵。外部持有者由测试辅助进程（或测试内独立线程打开独立文件描述符）持有 `flock`；进程内延迟用既有调试环境变量 `LIBRA_TEST_OBJECT_INDEX_UPDATE_DELAY_MS`（`client_storage.rs:620-626`）。自动化测试不调用系统 git；git 对照为手工证据。

  **M-GUARD（OI-01）**

  | 行 | 场景 | 期望 |
  |---|---|---|
  | G1 | 消费者延迟 200ms，一次 `add` 300 个修改文件 | exit 0，全部暂存，无超时 |

### ADR-OI-02: 锁持有者元数据与诊断

- **Status:** Accepted
- **Context:** GAP-02；git `lockfile.c:90`、`:105`、`:141`、`:254-300` 以 pid 文件区分三种情形。Libra 的锁基于 `flock`，文件内容可在持有期间写入。
- **Decision:**
  1. 获取 generation 锁或分片锁成功后，截断并写入一行 JSON 元数据 `{pid, purpose, started_at_ms, invocation}`；`purpose` 取值 `marker_publication`、`queued_update`、`replay`、`deletion_fence`。写入失败不影响加锁（M-DIAG D6）。
  2. 超时后读取元数据（读上限 1 KiB）：pid 等于本进程 → D2；pid 存活 → D1；pid 不存在或元数据缺失、不可读 → D3。Windows 无法打开时走 D3。
  3. 所有文案追加 D4 说明。判定与文案集中在一个函数，替换 `client_storage.rs:299` 的固定文案，并更新钉住旧文案的测试（`:3316`）。
  4. 元数据不作为锁语义的一部分：释放锁时不清空内容，下一个持有者覆盖；读取方只把它当诊断线索。
- **Alternatives considered:** 另建 pid 侧车文件——需要额外原子写与清理，拒绝。改用 SQLite 记录持有者——锁与数据库连接生命周期不一致，拒绝。
- **Consequences:** 锁文件由零字节变为含一行元数据；锁命名空间规模不变。
- **Revisit when:** 锁实现更换。

### ADR-OI-03: 等待策略与只读预检回放

- **Status:** Accepted
- **Context:** GAP-03、GAP-04；git `lockfile.c:198-199`、`:206-251`；`Documentation/config/core.adoc:580-590`。
- **Decision:**
  1. 发布方与回放方的等待改为 1ms 起步二次退避加 ±25% 抖动，单次休眠上限 1 秒；非测试构建预算由 2 秒改为 10 秒，测试构建保持 100ms。
  2. `repair_pending_object_index_updates_before_command` 在 `require_complete=false` 的命令中使用非阻塞尝试获取 generation 锁；忙时本次跳过回放，不输出告警，只记 debug 日志。
  3. `require_complete=true` 的命令（`cloud sync`、破坏性 agent 清理等）保持阻塞等待，预算同第 1 条，失败时 fail-closed。
  4. 删除栅栏与回放持锁范围不变（保持与发布方的全序）。
- **Alternatives considered:** 新增配置键——需要配置文档与跨层读取，登记 DEFER-02。无限等待——卡死时用户无反馈，拒绝。
- **Consequences:** 慢速卷上写命令的最坏等待由 2 秒增至 10 秒，换取不失败。
- **Revisit when:** DEFER-02 排期。

### ADR-OI-04: 批量发布 repair marker

- **Status:** Accepted
- **Context:** GAP-05；issue 建议「每次调用只取一次锁」；git `builtin/add.c:531`、`:686-688` 整个调用只持有一次索引锁。
- **Decision:**
  1. `ClientStorage` 新增批量发布接口：调用方累积已存储对象的 `IndexUpdateMsg`，每满 256 个（或调用结束）在一次 generation 锁持有期间原子写入该批 marker，再逐个入队。
  2. `add`（经 `object_ext` 的 blob 保存路径）与操作日志快照的 blob/tree 写入改用批量接口；单对象 `put` 保持现有语义，内部等价于批大小 1。
  3. 语义不变式：每个 marker 在其消息入队前已持久化；删除栅栏与回放在批与批之间可以取得 generation 锁；批内失败时已写入的 marker 保留并返回错误（M-BATCH B2）。
  4. 批大小为常量，不暴露配置。
- **Alternatives considered:** 整个调用只取一次锁——长时间阻塞删除栅栏与其它进程，拒绝。调用开始先取锁、结束释放——同上，拒绝。
- **Consequences:** 发布路径命中 T-1；需要计数钩子（仅测试构建）断言锁获取次数。
- **Revisit when:** 锁实现更换。

### ADR-OI-05: `add` 在 marker 注册失败时的契约

- **Status:** Accepted
- **Context:** issue 后续第 4 项；R2′ 显示对象已写入而暂存区为空；git 在索引锁失败时同样整体失败且暂存区不变，已写入的松散对象保留。
- **Decision:**
  1. 保持原子失败：exit 128、`LBR-IO-002` 不变，暂存区不变。理由是 marker 未持久化时继续暂存会让云端目录遗漏对象，而 marker 正是回放的唯一持久记录。
  2. 文案改为单一前缀：说明对象负载已安全写入、未暂存任何路径、锁释放后直接重试即可且不会重复写入负载、无需删除锁文件；锁超时情形拼接 ADR-OI-02 的持有者说明。
  3. `--json` error envelope 的 `details` 增加 `stored_objects` 与 `staged`。
  4. 去除快照路径的双重前缀：`SnapshotError` 包装内层 facet 错误时不重复「capture failed」字样（`snapshot.rs:95`、`facet.rs:111`、`middleware.rs:681-687`）。
- **Alternatives considered:** marker 失败时照常暂存并告警——破坏云端目录的持久性保证，拒绝。改用 `LBR-CONFLICT-002`——改变已发布稳定码，收益不足，拒绝。
- **Consequences:** `add` 文档错误表与 commit/hash-object/update-index 文档同步文案说明。
- **Revisit when:** 云端目录改为不依赖本地 marker 的一致性模型。

| 发布方等待超出预算 | 已存储对象；暂存区不变 | 按 M-FAIL F2 文案提示重试 | 删除锁文件；部分暂存 |
| 只读命令跳过回放 | marker 保留在目录中 | 下一个命令或要求完整回放的命令重试 | 输出误导性告警；静默丢弃 marker |
| 发布步 `gh release create` 失败 | 已推送的 `main` 提交 | 按 ER-09 记录，下一窗口补 tag/release | blind retry；只推 `main` 就宣称已发布 |
| D 组 `release.yml` 失败 | 已存在的 tag | 前滚修复，发新 patch | 回退已推送提交或删除已发布 artifact |
