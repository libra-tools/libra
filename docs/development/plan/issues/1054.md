## 已决议设计决策

### ADR-I1054-01: 去掉隐式 HEAD

无 spec、无 `--default`、无查询模式、无 `--verify`/`--short` 时，结果列表为空。文本模式不输出，退出 0。`--json` 沿用现有多 spec 分支，发出空数组，不新增信封；`--machine`（`src/cli.rs:255`，紧凑单行 JSON）同样只发一行、`data` 为空数组；EN 与 zh-CN 的结构化输出段同卡写明这一点。裸 `--verify`、`--short` 在 `--json` 下是本卡新增的失败路径：stdout 为空，stderr 是现有的错误信封（`ok` 为 false、`error_code` 为 `LBR-CLI-003`、`exit_code` 为 128，与 2026-11-07 在 0.30.158 上实测的 `--json rev-parse --verify nosuchref` 同形），退出 128；`--machine` 隐含安静模式，失败时静默退出 1（同日实测），本卡不改这一既有行为，也不为它写验收。仓库外运行仍由 `require_repo` 以 128 失败，所以精确句限定为「Inside a repository」。查询模式仍合成一次占位并打印原来的一个值。`--verify` 或 `--short` 且 spec 数不是 1 时保持 `Needed a single revision`（退出 128），不得再偷偷解析 HEAD。`--default <arg>` 与 `rev-parse -- <path>` 的现有分支不改。`--abbrev-ref`、`--symbolic`、`--symbolic-full-name`、`--sq` 在没有 spec 时同样输出为空、退出 0（Git 2.54 实测一致，开工时以固定 Git 复核；当前 Libra 的裸 `--symbolic-full-name` 打印 `refs/heads/main`）。help（`src/command/rev_parse.rs:155`）与注释（`:278-287`、`:614-615`）同卡改写，不再声称默认 HEAD 或「matching Git」。

  push_rc=$?
  set -e
  libra branch -D "$push_branch" || echo "warning: could not delete the local branch $push_branch" >&2
  libra fetch origin
  latest=$(libra rev-parse origin/main)
  test -n "$latest"
  landed=yes
  if [ "$latest" != "$SHA" ]; then landed=$(on_remote_main "$SHA"); fi
  if [ "$landed" = no ]; then
    if [ "$latest" = "$parent" ]; then echo "push exited $push_rc while origin/main did not move: authentication, network or server error; not retrying (ER-09)" >&2; else echo "origin/main advanced during the push; follow the recovery steps above" >&2; fi
    exit 1
  fi
fi
if [ "${MODE:-normal}" = repair ] && [ "$(state_get PUSHED_SHA)" != "$SHA" ]; then state_put REPAIRED_FROM "$(state_get PUSHED_SHA)"; fi
state_put PUSHED_SHA "$SHA"
state_put VERSION "$VERSION"
candidate="release/v$VERSION"
tip=$(remote_branch "$candidate")
if [ "$tip" != "$SHA" ]; then
  if [ "${MODE:-normal}" = normal ]; then
    if [ "$tip" != none ]; then echo "$candidate already exists at $tip; another release owns this version" >&2; exit 1; fi
  else
    if [ "$tip" = none ]; then echo "$candidate is missing in repair mode" >&2; exit 1; fi
    rel=$(gh api "repos/libra-tools/libra/compare/${tip}...${SHA}" --jq .status)
    if [ "$rel" != ahead ]; then echo "$candidate tip $tip is not an ancestor of $SHA ($rel)" >&2; exit 1; fi

  set +e
  libra push origin "$push_branch:$candidate"
  push_rc=$?
  set -e
  libra branch -D "$push_branch" || echo "warning: could not delete the local branch $push_branch" >&2
  tip=$(remote_branch "$candidate")
  if [ "$tip" != "$SHA" ]; then echo "$candidate is at $tip after a push that exited $push_rc; rerun this stage" >&2; exit 1; fi
fi
state_put CANDIDATE "$candidate"
echo "pushed $SHA (v$VERSION) to main and $candidate"

第一段成功后立即按「生命周期」第 4 步做 `remote-pending` 登记并推送。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

第三段，CI 通过后发布。脚本先从状态文件取回第二段记录的两个 run，重新向 GitHub 查询它们的结论、head SHA、分支与事件，必须是 success、本卡 SHA、候选分支、push，并逐个核对 run 内每个 job 都是 success（`base.yml` 的 8 个 job 在 `release/**` 上都没有跳过条件），所以漏跑或错序执行第二段时不会建 tag。本段开头先以 `WHEN=stage3` 执行外部前置检查（从本文件抽出原样运行），第一段开头同样以 `WHEN=stage1` 执行，所以这两次检查不靠执行者记得。随后确认本卡 SHA 仍在远端 `main` 上。本段可原样重跑：远端已有 `v$VERSION` 时，只有它指向本卡 SHA 且对应 Release 存在，才视为上一次第三段已成功（例如 `gh release create` 在服务端成功后客户端报错，或建 tag 后、写状态文件前中断），补记 `TAG` 后结束；tag 指向别的提交，或只有 tag 没有 Release，都停止报告，不改写 tag。远端还没有该 tag 时，候选分支必须仍指向本卡 SHA，前一个 patch 版本 `v<VERSION 的 patch − 1>` 必须已有 tag 且它的 `release.yml` run 都已结束（tag 已建而 release 仍在上传时 CDN 还是更旧的版本，两个发布会互相干扰；本族只做 patch + 1，修复模式沿用同一版本，所以前一版本就是 bump 前的基线；它没有 tag 说明有更早的发布未完成，`refuse_older_cdn` 会让两个发布互相干扰），另有两项检查与 `.github/workflows/release.yml:351-386` 的 `refuse_older_cdn` 对应：远端不存在版本号大于 `v$VERSION` 的 `vX.Y.Z` tag；`https://download.libra.tools/install.sh` 与 `install.ps1` 返回 200、能取出版本，且版本都小于 `v$VERSION`。等待 CI 的几个小时里其它计划可能已发布更高版本，此时 `gh release create` 会留下孤立 tag，而 `upload-install-scripts` 会拒绝上传。任一项不满足就停止，不建 tag：版本被抢先时按修复模式之外的正常路径，在新基线上以新的 C 组提交前滚（本卡版本号作废，记入「实施证据」）。`gh release create` 报错时先按同样规则复核远端，确认已发布才继续。

### 网站

网站交付按三段 fail-closed 脚本执行，用 `bash` 运行，任一段非零退出即停止。每段运行前 `export CARD=<本卡 ID>`，脚本按下表选取命令页与精确句，`CARD` 未设或不在表内即失败。网站前置（`/Volumes/Sea/libra-backend` 挂载、`.libra` 且无 `.git`、`cf` 分支干净且不超前、同步脚本、`pnpm`、`wrangler` 与 `gh` 已认证）由外部前置检查在开工前、发布第一段与第三段之前机械检查：开工前不满足时本卡保持 `pending`；开工后才发现不可用时本卡记为 `blocked`（ER-10），恢复后回到 `in-progress`。任何情况下都不写 `/Volumes/Data/gitmono/libra-backend`。

|---|---|---|
| `I1054-01` | `rev-parse` | `Inside a repository, rev-parse with no arguments prints nothing and exits 0; without a revision, --verify and --short fail with exit code 128, and --abbrev-ref, --symbolic, --symbolic-full-name and --sq print nothing.` |

2026-11-07 对只读副本与线上页面的核对结果：同步脚本 `--only <cmd>` 只写 `apps/tanstack-app/content/docs/commands/<cmd>.en.md`；线上 `zh-CN` 路由渲染同一份 EN 页面，且不做智能标点替换。因此网站写集只有 EN 页，两个 URL 都核对同一精确句。精确句在 EN、zh-CN 与开发文档里都要单独成行、不折行，不加反引号或其它行内标记；折行或加标记后渲染结果会拆开句子，grep 门就会失败。首次 check 必须报告 drift（exit 1），因为本卡已改源文档；exit 0 表示源文档未改或网站已含该变更，exit 2 表示同步拒绝，两者都停止调查。

网站三段在发布四段第四段确认 release 五个 job 全部成功之后执行（段一要求状态文件里已有 `RELEASE_RUN`；文档不早于可安装的二进制公开）。段三确认两个线上页面都含精确句之后写入 `SITE_VERIFIED`，终止链的暂存守卫要求这一项，并重新取回两个页面复核。同步脚本读取 `--libra-root` 下的 `src/cli.rs`、全部命令文档以及文档相对链接指向的文件（`--only` 只决定写哪一页）。所以段一不读本检出的工作区，而是用 `libra archive --format=zip` 把状态文件里的 `PUSHED_SHA`（第三段已在其上建 tag 的发布提交）整树导出到临时目录，以它作为 `--libra-root`：`tar` 格式会因仓库里超长的夹具路径以 `LBR-IO-002` 失败，`zip` 在 2026-11-07 实测约 2 秒，且同步脚本对导出树与工作区的 `--only ls-tree` 检查结果相同。网站发布的内容因此正是已发布版本的源文档，之后本检出或上游对 `src/cli.rs`、命令文档的任何改动都不会让段一失败或混进网站。后端若与 `origin/cf` 不同，段一用 `libra pull --ff-only` 快进（不会生成合并提交；本地有超前或分叉提交时它拒绝或不前进），之后核对 `HEAD` 等于 `origin/cf`，不等就停止。段一只在网站提交推送之前运行：段二推送成功后若段三超时需要重来，只重跑段三，不重跑段一，因为那时线上页面可能已含精确句，段一的负向证明会按设计失败。

**C 组运行器（`bash` 运行，`CARD` 为本卡 ID）：** 从本文件按下列固定锚点抽出脚本，所以执行的就是本文件里经过审查的门块，不靠执行者逐段复制。抽取规则：锚点在全文（或标注为本卡范围时在本卡 `Task` 标题到下一个 `Task` 标题之间）必须恰好出现一次，取它之后的第一个 `bash` 代码块，锚点与代码块之间不得隔着标题。Verification 门块按顺序拼成一个门块脚本，开头是 `set -eo pipefail`，块与块之间插入 `set +u`，在同一个 shell 里执行，所以前置块定义的函数可供后面的门块使用；C 组 fail-closed 脚本单独成一个脚本，在门块脚本通过之后以新的 `bash` 进程运行，门块里 TC 的 `export`（`LIBRA_BIN`、`TC_*`、`GIT_*` 等）因此不会带进 C 组的全量测试。任何一条命令失败，所在脚本立即非零退出，运行器随之停止。锚点只在正文里查找：代码块、「评审结论与修订记录」节与「实施证据」节都不参与匹配，所以脚本自身、日志与收据里出现同样的文字不会造成歧义。各卡的门块锚点及顺序就是下面脚本里 JSON 配置的 `gates`（`card` 表示只在本卡范围内查找），C 组脚本的锚点是 `c`。有 C 组提交的卡，门块脚本先跑 bump 前窗口检查、版本面内容检查（脚本开头导出 `VSRC=worktree`）与有网站面的卡的精确句预检，再跑本卡的 Verification 门块，所以这三项也由通过标记绑定，漏跑会被暂存守卫发现。运行器只接受 `MODE` 为 `normal`（缺省）或 `repair`，并原样传给门块脚本；工作区独占检查用的 `MODE=snapshot`、`MODE=verify` 由运行器在调用时单独设置。`no_c` 列出的卡没有 C 组提交，运行器拒绝它们，它们的门块只由 `PHASE=accept` 的暂存守卫重跑。

**bump 前窗口检查（`bash` 运行，`MODE` 取 `normal`（缺省）或 `repair`）：** `HEAD` 等于 `origin/main`（bump 前），或是父提交为 `origin/main` 的本卡 C 组提交（rebase 恢复时）。`origin/main` 的四个版本面（`Cargo.toml`、`Cargo.lock` 中 `libra` 包、`install.sh`、`install.ps1`）必须是同一版本，不一致时说明上游的版本面本身有漂移，停止并报告，不在其上 bump。正常模式要求 `origin/main` 的版本已经有 tag，说明没有任何计划（包括 issues/1050–1057 以外同样改版本面的计划）处于「已 bump、未发布」状态；修复模式要求 `origin/main` 的版本就是本卡状态文件里的 `VERSION`、它没有 tag，且上一次的 `PUSHED_SHA` 是 `origin/main` 的祖先。
