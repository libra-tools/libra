> 模板 v2.16。[Issue #672](https://github.com/libra-tools/libra/issues/672) OPEN，含 1 条评论。正文与评论 TC 全集为 TC-0119/0120，对应 `t/t4254-am-corrupt.sh`「NUL in commit message's body / header」，case 位于 `cases/tc0106-0122-am-abort-family`；两项均由本卡 AC/Verification 必过验收（实测基线确系纯因 ISO-8859-1 拒绝阻断）。仅规划，未授权执行；卡 `pending` / 验收空。Git 对照 pin `6de20f6092dcf9bdb1c8efe03db4b70c82b423dd`。实测基线 system `libra 0.30.171`。测试用例仓本计划不修改。

## 文档职责

### 适用范围

`libra mailinfo` 与 `libra am` 共用解析器对 `Content-Type: text/plain; charset=ISO-8859-1`（及 quoted-printable 传输编码）邮件的解析：是否接受该 charset、正文与 `Subject` 头如何转换为 UTF-8，以及解码后含 NUL 时暴露的诊断（退出码与文案）。正文 NUL 使用 commit-log 诊断；`Subject` NUL 使用 Subject 专属诊断。既有 `utf-8`/`us-ascii` 与其它 charset 拒绝行为同时纳入回归。

### 非目标

其它 charset（`Shift_JIS`、`GB18030`、`windows-1252` 等）与 `iconv` 全表支持（`DEFER-I672-01`）。非 `text/plain` leaf part（`DEFER-I672-02`）。`am` 的 `--keep`/`--scissors`/`--whitespace`/`--interactive` 选项（`issues/672` 之外）。`format-patch` 生成侧（不生成非 UTF-8）。

### 成功定义

- mailinfo/am 共享解析器接受 `charset=ISO-8859-1` 的 quoted-printable 邮件：正文与 Subject 的 Latin-1 字节按 `ISO-8859-1 → UTF-8` 正确转换（`0xE9` → `é`）后应用。
- 解码后正文含 NUL 时以非零退出并给出 `a NUL byte in commit log message not allowed`；`Subject` 含 NUL 时，`mailinfo` 与 `am` 都给出 `a NUL byte in 'Subject' is not allowed`。
- `utf-8`/`us-ascii` 行为不变；其它 charset 仍以既有 `unsupported text charset '<x>'` 拒绝（fail-closed）。
- 文档与兼容矩阵同卡，回归覆盖接受/拒绝/诊断三类。

## 已决议设计决策

### ADR-CHR-01: 先 quoted-printable 解码，再做 ISO-8859-1 转换；逐字节无损映射

- **Status:** Accepted
- **Context:** `validate_text_charset` 在解码前拒绝非 UTF-8/us-ascii；上游邮件用 `charset=ISO-8859-1` + quoted-printable。
- **Decision:** 解析顺序固定为：传输编码（quoted-printable）解码 → charset 转换（`ISO-8859-1` 逐字节映射为 `U+0000..U+00FF`，即 `byte as char`）→ 头部/正文校验（控制字符、NUL）。Latin-1 无失败分支，不需要外部依赖。
- **Alternatives considered:** 引入 `encoding_rs`（新增依赖、扩大写集）；用 `iconv` 子进程（外部工具依赖、平台差异）。
- **Consequences:** 其它 charset 仍拒绝；`windows-1252` 等近似编码不在本卡范围。
- **Revisit when:** 需要多 charset 支持（届时应引入专用库与 fuzz 用例）。

### ADR-CHR-02: 单一 `decode_charset` 入口并按字段对齐 NUL 文案

- **Status:** Accepted
- **Context:** charset 校验与 NUL 校验分散在 `validate_*` 与解码路径；Git 对正文与 Subject 使用不同诊断。
- **Decision:** 抽出 `decode_charset(bytes, charset) -> Result<String>` 供正文传输解码与 RFC 2047 头部共用；在 `mailinfo.rs` 的实际解码点保留原始 bytes 直至 charset 转换。正文 NUL 固定为 `a NUL byte in commit log message not allowed`；`validate_decoded_header("Subject", ...)` 对 NUL 特判为 `a NUL byte in 'Subject' is not allowed`，其它控制字符继续用通用 header 诊断；两条均保留退出码 129，并被 `mailinfo`/`am` 共用。
- **Alternatives considered:** 保留 Libra 自有文案（上游 `test_i18ngrep` 会失败）。
- **Consequences:** 实时诊断改动点只锚定 `mailinfo.rs:266-284,582-588,634-716` 的解析/校验路径；`am` 复用该结果。已持久化状态的防御性校验不作为本卡实时邮件诊断锚点。
- **Revisit when:** Git 改变该诊断文案。
