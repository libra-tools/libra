### 适用范围

## 已决议设计决策

### ADR-I1045-01: 干净树由 I1045-01 清空；`--discard-changes` 的脏字节恢复由 I1045-02 交付

- **Status:** 已决议。下面的步骤就是两张卡的实施合同。2026-11-07 的五步旧草案、未批准的 EX-I1045-01，以及「先清 index 再删文件」都作废，不实施。
- **Context:** `src/command/switch.rs:65` 的帮助仍写 preserving index/worktree。`switch_to_orphan_branch` 在 `:1276`。`:1314-1317` 的注释说 `switch --orphan` 会把 index/worktree 清成空树，`:1318-1321` 却只在非 checkout 且非 force 时调用 `ensure_clean_status`，然后调用 `:1372` 的 `switch_head_to_unborn_branch`，函数体只更新 HEAD 与 reflog。`:848-851` 写明 `--force` 也不做不安全的 gitlink 目录转换。`commit.rs:1250-1257` 只在 index 为空且没有 staged changes 时拒绝提交；空 index 若相对旧 HEAD 形成删除，不能靠这几行挡住。`reset.rs:1415-1427` 的 `IndexSnapshot` 能区分 index 不存在与已有字节，`:1424-1427` 的 `WorktreeSnapshotKind::Tracked` 只在工作树与 stage 0 相同时用对象 ID 回滚，不能当作脏文件副本。`:1458-1484` 的 `blocking_worktree_ancestor` 在跟随链接之前拒绝符号链接祖先。`middleware.rs:99-100` 把 `switch` 标成 `WorkspaceMutation`，`:655-668` 在命令失败时只 `persist_failed_operation` 并返回。`undo.rs:43` 只接受 `Success`。`snapshot.rs:69-71` 的默认上限是 30 秒、100000 文件、512 MiB，超限可以是 partial。因此 operation 租约、`op undo` 和通用快照都不是本计划的恢复机制。
- **Decision:** 只有 `NavigationCommand::Switch` 会清空。`checkout --orphan` 仍只改 HEAD。两张卡顺序实施，写集相交，由 I1045-02 依赖 I1045-01 串行。
  1. **I1045-01，干净树。** 不带 `--discard-changes` 时沿用 `ensure_clean_status`（`:1319`）。在任何恢复记录或删除之前，每个 stage-0 路径都必须只含 `Component::Normal`，且第一段不是 `.libra`（规则与 `reset.rs:1436-1455` 的 `validate_guarded_relative_path` 相同；本计划不改 `reset.rs`）。命中则退出 128，不写记录、不删除、不改 index、不改 HEAD。再用 `symlink_metadata` 检查每一级祖先；符号链接祖先以 `ConflictOperationBlocked`（退出 128）拒绝。mode 160000 且同名工作树目录非空时，即使带 `--discard-changes` 也拒绝；空目录或不存在则只从删除集合去掉。带 `--discard-changes` 时，本卡不删除、不改 index，仍只发布 HEAD（今天的行为）。不带该旗标且预检通过后：`NotFound` 视为已删除，删除已跟踪文件，再删因此变空的父目录（不删除工作树根；目录非空就停）。然后把空 index 写到 `<index>.orphan.tmp`，按 `atomic_write::sync_data_enabled()` 决定 fsync，`rename` 到 `path::index()` 并 fsync 父目录。最后才发布 HEAD。删除失败或临时文件/rename 失败：不发布 HEAD，原 index 字节保持不变，并删除残留临时文件。HEAD 发布失败：把预检时读入的原 index 字节原子写回；index 原本不存在时改为删除本命令创建的 index 文件。写回也失败时，错误同时报告两步。干净树的已删除文件用 `libra restore --worktree .` 从仍在的 index blob 取回。本卡不保存脏字节，也不调用 `libra op undo`。
  2. **I1045-02，`--discard-changes`。** 跳过干净检查，但仍执行同一套路径组件、`.libra` 第一段、符号链接与非空 gitlink 预检。拒绝发生在写恢复记录之前。首次删除之前，在本 worktree 的 `.libra/switch-orphan-recovery/<id>/` 写下旧 HEAD 身份、index 原字节或「原本不存在」，以及每个将删除路径的实际字节、模式、符号链接目标或「原本不存在」。记录总和超过 512 MiB，或记录写入/fsync 失败，则不删除、不写 index、不改 HEAD。之后使用与 I1045-01 相同的删除、空 index、HEAD 顺序。任一失败在返回前按记录恢复工作树字节和原 index，并保持原 HEAD；恢复失败则保留该目录并在错误里写出它的路径。只有 HEAD 发布成功且记录删除成功，才删除该目录。未跟踪文件永远不进入删除集合。`NotFound` 仍算删除成功。
  3. **不声称的事。** 进程在返回前被杀死时，不声称自动恢复，也不另设注入；这与 Git 在 index 已写、ref 尚未改时断电是同一类窗口。不把租约说成 index 锁。不修改 `reset.rs`、`middleware.rs` 或 `commit.rs`。
- **Alternatives considered:** 先清 index 再删文件（失败时下一次提交会把空 index 当成全删）；两条命令都清空（破坏 checkout 合同）；直接 `Index::save`（截断写）；把全部失败窗口放进一张卡并用未具名的门族 waiver 抬高 G-03 上限。前三项不安全，最后一项没有已具名的 Approver，因此改为两条各自完整的行为轴。
- **Consequences:** I1045-01 发布后，干净的 `switch --orphan` 清空 index 并删除已跟踪文件，`checkout --orphan` 仍保留，`--discard-changes --orphan` 仍保留。I1045-02 发布后，`--discard-changes --orphan` 也清空已跟踪改动并保留未跟踪文件，命令返回错误前恢复脏字节。Issue 的 switch 行为在两张卡收口。上游门只有 TC-2825 的恰好一行 PASS。TC-2824 留在 #537。
- **Revisit when:** Libra 引入真正的 index 锁，或 Git 改变 `switch --orphan` 对未跟踪文件的规则。

模块门和全量门不替代每卡具名测试。按用户指定工作流，用系统 `libra` 精确暂存本卡写集、计划状态与版本面，`libra commit -S -s` 提交，然后执行发布四段。

按下列四段依次执行。每段都是独立的 fail-closed 脚本，用 `bash` 运行（不用 zsh），任一段非零退出即停止，不进入下一段。断言一律写成单独的 `test` 语句：`test A && test B` 在第一个 `test` 失败时不会触发 `set -e`，所以脚本里不用这种写法；比较前先把命令结果赋给变量，让命令失败直接触发 `set -e`。管道里不用提前退出的 `awk ... exit` 或 `head`：在 `pipefail` 下，上游命令写入已关闭的管道会以 141 结束并静默触发 `set -e`（2026-11-07 对 70 KB 的线上 `install.sh` 实测会随机出现），所以取第一处匹配一律写成 `!seen { ...; seen = 1 }`。各段之间只通过运行状态文件 `/Volumes/Data/tmp/libra-plan-state/1045-<CARD>.env` 衔接（见「生命周期」）：第一段读取 `C_COMMIT`，写入实际推送的 `PUSHED_SHA` 与 `VERSION`；第二段写入候选分支上 base 与 CodeQL 的 run ID；第三段重新核对这些 run 后建 tag；第四段核对 release 后删除候选分支。各段都不用当前 `HEAD` 或工作区决定发布对象（第一段检查的就是将要推送的提交本身，之后各段只读状态文件），所以同一检出里之后出现的提交或改动不会让 tag 落到别的提交上。外部前置检查在 C 组提交之前（生命周期第 3 步第 1 小步，`WHEN=stage1`）、第一段之前（再次 `WHEN=stage1`）与第三段之前（`WHEN=stage3`）各执行一次，任一次失败都不推送、不发布：C 组提交之前与第三段之前的失败按生命周期第 8 步登记 `blocked`；第一段之前的失败只停止并报告，因为此时 C 组提交尚未推送，登记提交无法单独推送；前置恢复后从失败处重跑。

**D 取自发布候选分支，不承接其它提交。** 第一段把同一个 SHA 同时推到 `main` 与 `release/v<VERSION>`。`base.yml` 的 push 触发是 `branches: [main, 'release/**']`，注释写明「Release candidates must finish even while main continues advancing」（`.github/workflows/base.yml:3-5`），`cancel-in-progress` 只对 PR 与 `refs/heads/main` 生效（`:13-15`）；`.github/workflows/codeql.yml:16` 的 push 同样包含 `release/**`；`cancel-superseded-main.yml` 只在 `main` 上触发、只取消 `main` 的 run；`release.yml` 只由 `v*` tag 触发，推候选分支不会发布任何东西。仓库先例：`release/v0.30.155` 上 SHA `3462306b` 的 base run 41976607602（约 178 分钟）与 CodeQL run 41976607585 在 2026-11-05 都是 success，该分支事后已删除（2026-11-07 查询远端为 404）；更早有 `release/v0.30.92`。所以第二段只认候选分支上 head SHA 等于本卡 SHA 的 run，正是 ER-04 D 的「同一 head SHA」，没有偏离，也不承接任何后继提交的结论。候选分支是发布授权范围内的远端 ref，不是功能分支，不开 PR，第四段在 release 全部成功后删除它。

上游前进时不用 `libra pull` 制造合并提交。若 C 组提交之后、第一段推送之前 `origin/main` 前进，按以下步骤恢复，每步失败都停止：
1. 此时工作区必须干净（本卡改动都已在 C 组提交里，工作区独占检查保证没有他人改动）。执行 `libra rebase origin/main`。它失败时执行 `libra rebase --abort`：abort 成功说明 rebase 遇到冲突，版本面冲突按第 2 步处理，其它冲突手工 rebase：`plan-status.md` 与 `COMPATIBILITY.md` 这类按行登记的文件以 `origin/main` 的版本为底、只重放本卡的行，其它文件按双方语义合并；abort 失败说明 rebase 根本没有开始（例如工作区不干净），按错误信息处理，不计入恢复次数。
2. 版本面冲突（上游改了版本）：`libra reset --mixed HEAD^` 撤销本卡尚未推送的 C 组提交，同时清空暂存区（只涉及本卡自己的改动；`--soft` 会把本卡改动留在暂存区，之后的工作区独占检查与暂存守卫都会拒绝，2026-11-07 在隔离仓库实测两者差别），`libra restore --source HEAD --worktree Cargo.toml Cargo.lock install.sh install.ps1` 把四个版本面文件恢复为此时 `HEAD`（本卡原基线）的内容，使随后的 `pull --ff-only --autostash` 无冲突地带入上游的新版本，然后从生命周期第 3 步的第 1 小步重新开始（外部前置检查与工作区独占检查、`pull --ff-only --autostash`、窗口检查、在上游版本上 bump、C 组全套）。
3. rebase 成功后，以 `PHASE=c` 运行提交后范围检查，并核对 `libra diff --name-only HEAD^ HEAD` 与 rebase 前 `libra diff --name-only "$C_COMMIT^" "$C_COMMIT"` 的路径集合相同，防止重放丢文件；再运行 bump 前窗口检查（它接受父提交为 `origin/main` 的本卡提交）与版本面内容检查（`VSRC=head`）。
4. 先运行「C 组结论携带检查」。上游增量只含文件名未被 `tests/`、`src/`、`build.rs` 与 `.github/` 引用的计划文件，以及增删行不含测试读取模式的 `plan-status.md` 改动时，C 组结论随重放携带：该检查在新树上重跑窗口检查与版本面内容检查并写下携带标记。其它任何增量（包括改到 `tests/compat/agent_architecture_guard.rs:8181-8215` 读取的 `plan-status.md` 行，以及被测试读取的计划文件：`tests/session_capture_docs_contract.rs:10` 与 `tests/opencode_hook_contract_test.rs:24` 编入其它计划文件）都以 C 组运行器在重放后的树上整套重跑本卡全部门与 C 组脚本（含双环境全量 nextest）；此时工作区干净，被测的树就是 `HEAD`。
5. 只在本文件「实施证据」更新 C 组收据（仓库里没有构建或测试读取 `docs/development/plan/issues/`），以 `PHASE=amend` 运行暂存守卫（它只允许本文件，并要求运行器为重放后的树写下的通过标记，或指向当前 `HEAD` 的携带标记），执行 `libra commit --amend -S --no-edit`：`libra rebase` 会把旧提交的 `gpgsig` 头逐字节复制到重放后的提交上（2026-11-07 在 0.30.157 与 0.30.158 上实测），但树与父提交已变，这个签名已经失效，所以签名头存在不代表签名有效，必须用 `-S` 重新签名；随后运行的「记录 C_COMMIT」会比较新旧两个提交的 `gpgsig` 块，相同就失败；原提交信息里的 `Signed-off-by` 随重放保留，不再加 `-s`（加了会出现两行，2026-11-07 已实测）。
6. 以 `PHASE=c` 再跑提交后范围检查，运行「记录 C_COMMIT」脚本，然后重新执行第一段。

需要整套重跑的恢复同一张卡最多 3 次（携带不计次数，但每次携带之后都要重新执行第一段）；第 4 次需要整套重跑时停止，把卡保持在 `in-progress` / `locally-accepted`，在「实施证据」记录每次的上游增量，并向用户报告，由用户决定是否协调其它写者暂停推送。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1045-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第一段，推送本卡 SHA 到 `main` 与候选分支 `release/v<VERSION>`，并写入状态文件。`MODE` 取 `normal`（缺省）或 `repair`：

```bash

cd ../libra
case "${CARD:?export CARD first}" in
  I1045-01) allowed='src/command/switch.rs tests/command/switch_test.rs tests/compat/switch_orphan_root_test.rs tests/INDEX.md tests/compat/README.md docs/commands/switch.md docs/commands/zh-CN/switch.md docs/development/commands/switch.md docs/development/commands/README.md COMPATIBILITY.md'; compat_lines='210'; c_phase=yes; row_file=''; row_prefix='' ;;
  I1045-02) allowed='src/command/switch.rs tests/command/switch_test.rs tests/compat/switch_orphan_root_test.rs tests/INDEX.md tests/compat/README.md docs/commands/switch.md docs/commands/zh-CN/switch.md docs/development/commands/switch.md docs/development/commands/README.md COMPATIBILITY.md'; compat_lines='210'; c_phase=yes; row_file=''; row_prefix='' ;;
  *) echo "unknown CARD=$CARD" >&2; exit 1 ;;
esac
allowed="$allowed Cargo.toml Cargo.lock install.sh install.ps1 docs/development/plan/issues/1045.md docs/development/plan/plan-status.md"
STATE_DIR=/Volumes/Data/tmp/libra-plan-state

state_get() { if [ -f "$STATE" ]; then awk -v k="$1" 'index($0, k "=") == 1 { v = substr($0, length(k) + 2) } END { print v }' "$STATE"; fi; }
state_put() { mkdir -p "$STATE_DIR"; touch "$STATE"; awk -v k="$1" 'index($0, k "=") != 1' "$STATE" > "$STATE.tmp"; printf '%s=%s\n' "$1" "$2" >> "$STATE.tmp"; mv "$STATE.tmp" "$STATE"; }
version_of() { libra cat-file -p "$1:Cargo.toml" | awk -F'"' '/^version = "/ && !seen { print $2; seen = 1 }'; }
tag_status() {
  local code
  set +e
  code=$(gh api "repos/libra-tools/libra/git/ref/tags/v$1" -i 2>/dev/null | awk 'NR == 1 { print $2 }')
  set -e
  printf '%s\n' "$code"
}
remote_branch() {
  local resp code
  set +e
  resp=$(gh api "repos/libra-tools/libra/git/ref/heads/$1" -i 2>/dev/null)
  set -e
  code=$(printf '%s\n' "$resp" | awk 'NR == 1 { print $2 }')
  case "$code" in
    200) printf '%s\n' "$resp" | sed -n '/^{/,$p' | jq -er '.object.sha' ;;
    404) printf '%s\n' none ;;
    *) echo "cannot read remote branch $1 (HTTP ${code:-none})" >&2; return 1 ;;
  esac
}
on_remote_main() {
  local resp code rel
  set +e
  resp=$(gh api "repos/libra-tools/libra/compare/$1...main" -i 2>/dev/null)
  set -e
  code=$(printf '%s\n' "$resp" | awk 'NR == 1 { print $2 }')
  case "$code" in
    200) rel=$(printf '%s\n' "$resp" | sed -n '/^{/,$p' | jq -er .status) || return 1 ;;
    404) printf '%s\n' no; return 0 ;;
    *) echo "cannot compare $1 with remote main (HTTP ${code:-none})" >&2; return 1 ;;
  esac
  case "$rel" in ahead|identical) printf '%s\n' yes ;; *) printf '%s\n' no ;; esac
}
case "${MODE:-normal}" in normal|repair) ;; *) echo "unknown MODE=$MODE" >&2; exit 1 ;; esac
prereq_script=$(mktemp /Volumes/Data/tmp/prereq.XXXXXX)
python3 -I - docs/development/plan/issues/1045.md "$prereq_script" <<'PREREQX'

text = open(sys.argv[1], encoding='utf-8').read()

if len(hits) != 1:

m = re.compile('(?m)^' + fence + r'bash\n').search(text, hits[0])
end = text.find('\n' + fence + '\n', m.end() - 1)
open(sys.argv[2], 'w', encoding='utf-8').write(text[m.end():end + 1])

porcelain=$(libra status --porcelain --untracked-files=all)

test -n "$changed"
for path in $changed; do
  case " $allowed " in
    *" $path "*) ;;
    *) echo "pushed commit touches a path outside the write set: $path" >&2; exit 1 ;;
  esac
done

base_version=$(version_of "$parent")
test -n "$base_version"
if [ "${MODE:-normal}" = repair ]; then
  test "$VERSION" = "$base_version"
  test "$VERSION" = "$(state_get VERSION)"
else
  test "$VERSION" = "$(printf '%s\n' "$base_version" | awk -F. '{ printf "%d.%d.%d\n", $1, $2, $3 + 1 }')"
  base_code=$(tag_status "$base_version")
  if [ "$base_code" != 200 ]; then echo "the base version v$base_version has no tag (HTTP ${base_code:-none}): another release is in flight; do not push" >&2; exit 1; fi
fi
vtmp=$(mktemp -d /Volumes/Data/tmp/vsurf.XXXXXX)
trap 'rm -rf "$vtmp"' EXIT
for f in Cargo.toml Cargo.lock install.sh install.ps1; do
  libra cat-file -p "$parent:$f" > "$vtmp/base"
  libra cat-file -p "$SHA:$f" > "$vtmp/new"
  changes=$(diff "$vtmp/base" "$vtmp/new" | grep '^[<>]' || true)
  if [ "${MODE:-normal}" = repair ]; then
    want=
  else
    case "$f" in
      Cargo.toml|Cargo.lock) want=$(printf '< version = "%s"\n> version = "%s"' "$base_version" "$VERSION") ;;
      install.sh) want=$(printf '< DEFAULT_VERSION="v%s"\n> DEFAULT_VERSION="v%s"' "$base_version" "$VERSION") ;;
      install.ps1) want=$(printf '< $DefaultVersion = "v%s"\n> $DefaultVersion = "v%s"' "$base_version" "$VERSION") ;;
    esac
  fi
  if [ "$changes" != "$want" ]; then echo "unexpected version-surface change in $f" >&2; exit 1; fi
done

test "$code" = 404
push_branch="c-push-1045-$CARD"
libra fetch origin
remote_main=$(libra rev-parse origin/main)
test -n "$remote_main"
landed=yes
if [ "$remote_main" != "$SHA" ]; then landed=$(on_remote_main "$SHA"); fi
if [ "$landed" = no ]; then
  if [ "$parent" != "$remote_main" ]; then echo "origin/main moved past the parent of $SHA; follow the recovery steps above" >&2; exit 1; fi
  libra branch -f "$push_branch" "$SHA"
  set +e
  libra push origin "$push_branch:main"
  push_rc=$?
  set -e
  libra branch -D "$push_branch" || echo "warning: could not delete the local branch $push_branch" >&2
  libra fetch origin
  latest=$(libra rev-parse origin/main)
  test -n "$latest"
  landed=yes

    if [ "$latest" = "$parent" ]; then echo "push exited $push_rc while origin/main did not move: authentication, network or server error; not retrying (ER-09)" >&2; else echo "origin/main advanced during the push; follow the recovery steps above" >&2; fi

  fi
fi
if [ "${MODE:-normal}" = repair ] && [ "$(state_get PUSHED_SHA)" != "$SHA" ]; then state_put REPAIRED_FROM "$(state_get PUSHED_SHA)"; fi
state_put PUSHED_SHA "$SHA"
state_put VERSION "$VERSION"
candidate="release/v$VERSION"
tip=$(remote_branch "$candidate")
if [ "$tip" != "$SHA" ]; then

    if [ "$tip" = none ]; then echo "$candidate is missing in repair mode" >&2; exit 1; fi

    if [ "$rel" != ahead ]; then echo "$candidate tip $tip is not an ancestor of $SHA ($rel)" >&2; exit 1; fi
  fi
  libra branch -f "$push_branch" "$SHA"
  set +e
  libra push origin "$push_branch:$candidate"
  push_rc=$?
  set -e
  libra branch -D "$push_branch" || echo "warning: could not delete the local branch $push_branch" >&2
  tip=$(remote_branch "$candidate")
  if [ "$tip" != "$SHA" ]; then echo "$candidate is at $tip after a push that exited $push_rc; rerun this stage" >&2; exit 1; fi
fi
state_put CANDIDATE "$candidate"
echo "pushed $SHA (v$VERSION) to main and $candidate"
```

第一段成功后立即按「生命周期」第 4 步做 `remote-pending` 登记并推送。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job（显示名 `compat-offline-core`）自身超时为 360 分钟（`.github/workflows/base.yml:100`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

```bash
test -n "$VERSION"

test "$(state_get CANDIDATE)" = "$candidate"

  case "$workflow" in
    base.yml) limit=25200; key=BASE ;;
    codeql.yml) limit=5400; key=CODEQL ;;
  esac
  deadline=$(( $(date +%s) + limit ))
  run_id=
  while :; do
    set +e
    runs=$(gh run list --repo libra-tools/libra --workflow "$workflow" --branch "$candidate" --event push \
      --limit 20 --json databaseId,headSha,status,conclusion,attempt 2>/dev/null)
    list_rc=$?
    set -e
    line=
    if [ "$list_rc" = 0 ]; then
      line=$(printf '%s\n' "$runs" | jq -r --arg sha "$SHA" \
        '[.[] | select(.headSha == $sha)] | sort_by(.databaseId) | last // empty | "\(.databaseId) \(.status) \(.conclusion) \(.attempt)"')
    else
      echo "gh run list failed; retrying" >&2
    fi
    run_status=
    if [ -n "$line" ]; then read -r run_id run_status run_conclusion run_attempt <<< "$line"; fi
    if [ "$run_status" = completed ]; then
      rerun=$(state_get "CI_${key}_RERUN")
      rerun_sha=${rerun%% *}
      rerun_attempt=${rerun##* }
      if [ "$run_conclusion" = success ]; then break; fi
      if [ -n "$rerun" ] && [ "$rerun_sha" = "$SHA" ] && [ "$run_attempt" -le "$rerun_attempt" ]; then
        :
      else
        case "$run_conclusion" in
          cancelled|failure|timed_out|startup_failure)
            if [ -n "$rerun" ] && [ "$rerun_sha" = "$SHA" ]; then
              echo "$workflow run=$run_id attempt=$run_attempt $run_conclusion for $SHA after one rerun" >&2
              exit 1
            fi
            if [ "$run_conclusion" = cancelled ] || [ "$run_conclusion" = startup_failure ]; then
              gh run rerun "$run_id" --repo libra-tools/libra
            else
              gh run rerun "$run_id" --failed --repo libra-tools/libra
            fi
            state_put "CI_${key}_RERUN" "$SHA $run_attempt"
            echo "$workflow run=$run_id $run_conclusion; rerun requested once" >&2 ;;
          *)
            echo "$workflow run=$run_id $run_conclusion for $SHA" >&2
            exit 1 ;;
        esac
      fi
    fi
    if [ "$(date +%s)" -ge "$deadline" ]; then echo "$workflow timeout for $SHA on $candidate" >&2; exit 1; fi
    sleep 30
  done
  state_put "CI_${key}_RUN" "$run_id"
  echo "$workflow success run=$run_id attempt=$run_attempt sha=$SHA branch=$candidate"
done
```

第三段，CI 通过后发布。脚本先从状态文件取回第二段记录的两个 run，重新向 GitHub 查询它们的结论、head SHA、分支与事件，必须是 success、本卡 SHA、候选分支、push，并逐个核对 run 内每个 job 都是 success（`base.yml` 当前只有 `format`、`clippy`、`redundancy`、`test` 四个 job，显示名分别为 `compat-rustfmt`、`compat-clippy`、`compat-redundancy`、`compat-offline-core`，在 `release/**` 上都没有跳过条件），所以漏跑或错序执行第二段时不会建 tag。本段开头先以 `WHEN=stage3` 执行外部前置检查（从本文件抽出原样运行），第一段开头同样以 `WHEN=stage1` 执行，所以这两次检查不靠执行者记得。随后确认本卡 SHA 仍在远端 `main` 上。本段可原样重跑：远端已有 `v$VERSION` 时，只有它指向本卡 SHA 且对应 Release 存在，才视为上一次第三段已成功（例如 `gh release create` 在服务端成功后客户端报错，或建 tag 后、写状态文件前中断），补记 `TAG` 后结束；tag 指向别的提交，或只有 tag 没有 Release，都停止报告，不改写 tag。远端还没有该 tag 时，候选分支必须仍指向本卡 SHA，前一个 patch 版本 `v<VERSION 的 patch − 1>` 必须已有 tag 且它的 `release.yml` run 都已结束（tag 已建而 release 仍在上传时 CDN 还是更旧的版本，两个发布会互相干扰；本族只做 patch + 1，修复模式沿用同一版本，所以前一版本就是 bump 前的基线；它没有 tag 说明有更早的发布未完成，`refuse_older_cdn` 会让两个发布互相干扰），另有两项检查与 `.github/workflows/release.yml:361-395` 的 `refuse_older_cdn` 对应：远端不存在版本号大于 `v$VERSION` 的 `vX.Y.Z` tag；`https://download.libra.tools/install.sh` 与 `install.ps1` 返回 200、能取出版本，且版本都小于 `v$VERSION`。等待 CI 的几个小时里其它计划可能已发布更高版本，此时 `gh release create` 会留下孤立 tag，而 `upload-install-scripts` 会拒绝上传。任一项不满足就停止，不建 tag：版本被抢先时按修复模式之外的正常路径，在新基线上以新的 C 组提交前滚（本卡版本号作废，记入「实施证据」）。`gh release create` 报错时先按同样规则复核远端，确认已发布才继续。

1. 开工：依次执行三项检查，任一失败本卡保持 `pending`，不写 `in-progress`，不提交开工登记。先执行开工检查（整个工作区干净、fetch 后 `HEAD` 快进到 `origin/main`、`COMPATIBILITY.md` 行身份正确），再执行开工门（它自己再 fetch 一次，并断言工作区干净、`HEAD` 等于 `origin/main`，所以扫描的就是远端最新的计划文本），最后以 `WHEN=start` 执行外部前置检查。随后把本卡 `Lifecycle` 改为 `in-progress`，同步 `plan-status.md` 本计划行，以 `PHASE=start` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): start $CARD (#1045)"`，以 `PHASE=start` 运行提交后范围检查，再以 `PHASE=start` 运行计划目录推送脚本直推 main。该脚本在最后一次 fetch 并确认登记提交的父提交就是 `origin/main` 之后、推送之前，从本文件抽出开工门原样重跑一次（此时本地树就是 `origin/main` 加本卡登记），门失败就不推送。其它检出与其它计划的开工门由此从 `origin/main` 看到本卡处于 `in-progress`。
2. A/B 全部通过后，`Acceptance` 写 `locally-accepted`（留在工作区，随 C 组提交一起提交），再做 ER-05 review 直到 PASS。有 C 组提交的卡在 PASS 后先运行「ER-05 审查摘要」，再把 `<CARD>:ER05_SESSION=`、`<CARD>:ER05_OUTPUT_SHA256=`、`<CARD>:ER05_VERDICT=PASS`、`<CARD>:ER05_REVIEWED=` 四行写入「实施证据」（行首是卡 ID 与冒号，每个键恰好一行；重审 PASS 时替换旧值，历次结论记在评审日志），`ER05_REVIEWED` 的值就是该脚本的输出，即审查时产品改动的摘要。`PHASE=c` 的暂存守卫在 bump 之后的树上重算同一摘要并要求相等：C 组失败后在写集内修改产品文件，或修复模式改动产品文件，摘要都会变化，必须重新审查并替换这四行。
3. C 组：
   1. 以 `WHEN=stage1` 执行外部前置检查（网站等发布前置要在本卡改动提交之前满足；失败时本卡改动尚未提交，按第 8 步以 `PHASE=blocked` 登记并推送，前置恢复后从这里继续），再以 `MODE=check` 运行工作区独占检查（它同时要求暂存区为空）。
   2. 执行 bump 前窗口检查。`HEAD` 落后于 `origin/main` 时，先执行 `libra pull --ff-only --autostash`（第 1 小步的工作区独占检查已保证工作区里只有本卡允许集合内的改动，所以 autostash 只暂存本卡自己的改动；恢复冲突时，`plan-status.md` 与 `COMPATIBILITY.md` 这类按行登记的文件以 `origin/main` 的版本为底、只重放本卡的行，不把旧行与新行同时保留，其它文件按双方语义手工合并，并从 A/B 重新开始），再重跑窗口检查。窗口检查通过后，在未 bump 的树上运行版本面 parity 预检 `source .env.test && cargo nextest run --no-tests=fail --test compat_version_surface_sync`，失败即停、不 bump。
   3. bump 只改 `Cargo.toml`、`install.sh`、`install.ps1` 的版本行（修复模式不 bump，见第 6 步），随后执行一次 `cargo build`，由工具链刷新 `Cargo.lock`（不手改）；然后执行版本面内容检查（`VSRC=worktree`）与精确句预检（有网站面的卡）。
   4. 把 `plan-status.md` 本计划行写成「C 组进行中」的最终措辞（`agent_architecture_guard` 会读取该文件，所以它必须在快照之前定稿）。
   5. 运行 C 组运行器。它从本文件按固定锚点抽出本卡全部 Verification 门块与 C 组 fail-closed 脚本，然后依次以 `MODE=snapshot` 运行工作区独占检查（记录 `HEAD`、改动路径集合与每个改动文件的 SHA-256；本文件除外，仓库里没有任何构建或测试读取 `docs/development/plan/issues/`，2026-11-07 已用 `rg` 核对）、运行门块脚本、以新的 `bash` 进程运行 C 组脚本、以 `MODE=verify` 运行工作区独占检查。四步都通过后才写入通过标记，标记绑定快照文件、门块脚本与 C 组脚本三者的 SHA-256；任一门失败就没有标记。
   6. 在本文件「实施证据」写入 C 组收据（版本号、各门结论与计数、C 组脚本打印的 release 二进制 SHA-256、通过标记的三行；ER-05 的四行已在第 2 步写入）。卡字段保持 `in-progress` / `locally-accepted`。
   7. 以 `PHASE=c` 运行暂存守卫（它再次核对快照，并要求通过标记与重新抽出的脚本一致），执行 `libra commit -S -s -m "<type>(<scope>): <summary> (#1045)"`（`-S` 用仓库 vault key 强制签名，不得用 `--no-gpg-sign`），以 `PHASE=c` 运行提交后范围检查，再运行「记录 C_COMMIT」脚本。推送前 `origin/main` 前进时，按发布四段开头的恢复步骤处理。
4. 第一段起的推送、候选分支、tag 与 release 都是对外动作，只在本卡获得执行授权后进行；`release.yml` 使用的 environments 在 2026-11-07 核对时都没有保护规则，不需要人工审批。第一段之前再以 `WHEN=stage1` 执行一次外部前置检查：这时 C 组提交已在本地、尚未推送，检查失败只停止并报告，不做 `blocked` 登记（登记提交只能连同未过 D 的 C 组提交一起推送），本卡保持 `in-progress` / `locally-accepted`，前置恢复后重跑本检查与第一段。通过后执行发布四段的第一段，它把同一个 SHA 推到 `main` 与发布候选分支 `release/v<VERSION>`，并把 SHA 与版本写入状态文件。第一段成功后立即做 `remote-pending` 登记：把本卡 `Acceptance` 改为 `remote-pending`，在「实施证据」写入 `<CARD>:C_COMMIT=`、`<CARD>:PUSHED_SHA=`、`<CARD>:VERSION=` 三行（行首是卡 ID 与冒号，值与状态文件相同；同一计划有多张卡时按卡区分）与推送 UTC，同步 `plan-status.md` 本计划行，以 `PHASE=remote` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): record $CARD push (#1045)"`，以 `PHASE=remote` 运行提交后范围检查与计划目录推送脚本。这笔提交让 `main` 前进、取消 `main` 上本卡 SHA 的 run，但不影响 D：D 只取候选分支上 head SHA 等于本卡 SHA 的 run，`base.yml` 对 `release/**` 不取消进行中的 run，`cancel-superseded-main.yml` 只处理 `main`。
5. 依次执行第二至四段（第三段自己以 `WHEN=stage3` 执行外部前置检查），第四段确认 release 五个 job 全部成功之后执行网站三段（有网站面的计划；网站段一要求状态文件里已有 `RELEASE_RUN`）。
6. 修复模式：第二段在建 tag 之前以失败结论退出（本卡 SHA 在候选分支上的 run 重跑一次后仍失败；本卡版本 V 已在 main、但没有 tag），本卡保持 `in-progress` / `remote-pending`，不改写 tag，也不再 bump：在本卡写集内做修复，以 `MODE=repair` 重走第 3 步（窗口检查改为要求 `origin/main` 的版本就是状态文件里的 V、V 没有 tag、且上一次的 `PUSHED_SHA` 是 `origin/main` 的祖先；版本面内容检查要求四个版本面文件不变），再以 `MODE=repair` 执行第一段（版本必须等于父提交的版本且仍无 tag；候选分支 `release/v<V>` 必须已存在且是修复 SHA 的祖先，修复 SHA 以快进推上该分支）；第三段在修复 SHA 上建 V 的 tag。失败收据与修复提交写入「实施证据」。tag 建成之后 release 失败时，tag 不改写；先删除 V 的候选分支（尖端必须是 V 的 `PUSHED_SHA`，用 `gh api -X DELETE repos/libra-tools/libra/git/refs/heads/release/v<V>`，删除后回读为 404，删除结果写入「实施证据」），再按正常模式在 V 之上 bump 到 V+1 前滚修复（V 已有 tag，窗口检查放行），V+1 使用新的候选分支。本卡的 `Rollback mode` 是 `immutable-release`：tag 与 Release 建立后不改写，修复只发新版本前滚；C 组提交推送之前的撤销按第 9 步放弃处理，不是第二种恢复模式。
7. 终止链：本卡全部 D 都通过后，才把卡改为 `done` / `complete`。在「实施证据」写入 `<CARD>:CI_BASE_RUN=`、`<CARD>:CI_CODEQL_RUN=`（候选分支 `release/v<VERSION>` 上 head SHA 为 `PUSHED_SHA` 的 run）、`<CARD>:TAG=`、`<CARD>:RELEASE_RUN=`、`<CARD>:CANDIDATE_DELETED=yes`、`<CARD>:ROLLBACK_VERIFIED=`（第四段降级演练装上并核对的上一发布版本）各一行，有网站面的卡另写 `<CARD>:SITE_SHA=` 与 `<CARD>:SITE_VERIFIED=`，值都与状态文件相同；五个 release job 的结论与网站部署 ID 以文字记录（无网站面的计划写 N/A），同步 `plan-status.md` 本计划行。以 `PHASE=terminal` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): record $CARD delivery (#1045)"`，以 `PHASE=terminal` 运行提交后范围检查与计划目录推送脚本。按 v2.14，它自身的 base/CodeQL 结论由下一次 `plan-status.md` 例行同步补记，不另开提交，也不重启终止链。
8. `blocked` 登记与解除：已 `in-progress` 的卡遇到本卡自身的 ER-10 故障（工作区只含本卡允许集合内的改动），或第 3 步第 1 小步、第三段之前的外部前置检查失败时，把本卡 `Lifecycle` 改为 `blocked`，`Acceptance` 保持 `HEAD` 已提交的值（A/B 之后工作区里尚未提交的 `locally-accepted` 先改回 `HEAD` 的值、解除后再写回，未提交的验收结论不随登记提交公开；暂存守卫按这一点核对），写明原因与解除条件，同步 `plan-status.md` 本计划行，以 `PHASE=blocked` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): block $CARD (#1045)"`，以 `PHASE=blocked` 运行提交后范围检查与计划目录推送脚本，其它计划的开工门由此看到它。`PHASE=blocked` 只暂存本文件与 `plan-status.md`，允许本卡写集内尚未提交的改动留在工作区。两种情况不登记、只停止并向用户报告，本卡保持 `in-progress`（对其它计划的开工门同样算活动写者）：C 组提交已在本地而尚未推送时（见第 4 步；计划目录推送脚本也会拒绝父提交不在远端 `main` 上的登记提交）；工作区出现本卡允许集合以外的改动时（登记提交无法与他人改动隔离）。条件恢复后用同一 `PHASE` 把 `Lifecycle` 改回 `in-progress`（提交信息写 `unblock`），再从中断处继续。
9. 放弃（释放家族串行锁）：本卡还没有任何推送到远端 `main` 的 C 组提交（状态文件没有 `PUSHED_SHA`），而外部前置长期不可用或用户决定改期时，可以放弃本卡：本地已有未推送的 C 组提交时先 `libra reset --mixed HEAD^` 撤销它；再用 `libra restore` 逐个撤销本卡写集内产品文件与版本面文件的改动、删除本卡新建的未跟踪文件（只限本卡允许集合内的路径）；`plan-status.md` 不整文件还原，只把本计划行改回；然后把 `Lifecycle / Acceptance` 改回 `pending` / 空并写明原因，同步 `plan-status.md` 本计划行，以 `PHASE=abandon` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): abandon $CARD (#1045)"`，以 `PHASE=abandon` 运行提交后范围检查与计划目录推送脚本。「没有推送过」不只看可丢弃的本地状态文件：`PHASE=abandon` 的暂存守卫先 fetch，并向 GitHub 核对状态文件里的 `C_COMMIT`（若有）不在远端 `main` 上、`origin/main` 的版本仍等于当前 `HEAD`（撤销后的基线）的版本、下一 patch 版本的候选分支 `release/v<下一版本>` 与 tag `v<下一版本>` 都不存在；任一不满足（例如推送已经落地而状态文件还没写下 `PUSHED_SHA`）就拒绝放弃。已经推送过的卡不能放弃，只能按第 6 步修复或前滚。

**记录 C_COMMIT（`bash` 运行；C 组提交与提交后范围检查之后运行，rebase 恢复的 amend 之后再运行一次）：**

```bash
set -eo pipefail
cd ../libra
STATE_DIR=/Volumes/Data/tmp/libra-plan-state
STATE="$STATE_DIR/1045-${CARD:?export CARD first}.env"
state_get() { if [ -f "$STATE" ]; then awk -v k="$1" 'index($0, k "=") == 1 { v = substr($0, length(k) + 2) } END { print v }' "$STATE"; fi; }
state_put() { mkdir -p "$STATE_DIR"; touch "$STATE"; awk -v k="$1" 'index($0, k "=") != 1' "$STATE" > "$STATE.tmp"; printf '%s=%s\n' "$1" "$2" >> "$STATE.tmp"; mv "$STATE.tmp" "$STATE"; }
gpgsig_digest() { libra cat-file -p "$1" | awk '/^gpgsig /{ f = 1; print; next } f && /^ /{ print; next } f { exit }' | shasum -a 256 | cut -d' ' -f1; }
sha=$(libra rev-parse HEAD)
test -n "$sha"
previous=$(state_get C_COMMIT)
if [ -n "$previous" ] && [ "$previous" != "$sha" ] && [ "$(gpgsig_digest "$sha")" = "$(gpgsig_digest "$previous")" ]; then
  echo "HEAD carries the signature of $previous: libra rebase copies gpgsig verbatim and the copy is no longer valid; run libra commit --amend -S --no-edit first" >&2
  exit 1
fi
state_put C_COMMIT "$sha"
echo "C_COMMIT=$sha"
```

**C 组运行器（`bash` 运行，`CARD` 为本卡 ID）：** 从本文件按下列固定锚点抽出脚本，所以执行的就是本文件里经过审查的门块，不靠执行者逐段复制。抽取规则：锚点在全文（或标注为本卡范围时在本卡 `Task` 标题到下一个 `Task` 标题之间）必须恰好出现一次，取它之后的第一个 `bash` 代码块，锚点与代码块之间不得隔着标题。Verification 门块按顺序拼成一个门块脚本，开头是 `set -eo pipefail`，块与块之间插入 `set +u`，在同一个 shell 里执行，所以前置块定义的函数可供后面的门块使用；C 组 fail-closed 脚本单独成一个脚本，在门块脚本通过之后以新的 `bash` 进程运行，门块里 TC 的 `export`（`LIBRA_BIN`、`TC_*`、`GIT_*` 等）因此不会带进 C 组的全量测试。任何一条命令失败，所在脚本立即非零退出，运行器随之停止。锚点只在正文里查找：代码块、「评审结论与修订记录」节与「实施证据」节都不参与匹配，所以脚本自身、日志与收据里出现同样的文字不会造成歧义。各卡的门块锚点及顺序就是下面脚本里 JSON 配置的 `gates`（`card` 表示只在本卡范围内查找），C 组脚本的锚点是 `c`。有 C 组提交的卡，门块脚本先跑 bump 前窗口检查、版本面内容检查（脚本开头导出 `VSRC=worktree`）与有网站面的卡的精确句预检，再跑本卡的 Verification 门块，所以这三项也由通过标记绑定，漏跑会被暂存守卫发现。运行器只接受 `MODE` 为 `normal`（缺省）或 `repair`，并原样传给门块脚本；工作区独占检查用的 `MODE=snapshot`、`MODE=verify` 由运行器在调用时单独设置。`no_c` 列出的卡没有 C 组提交，运行器拒绝它们，它们的门块只由 `PHASE=accept` 的暂存守卫重跑。
