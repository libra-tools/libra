## 文档职责

### 适用范围

让 `libra switch --orphan` 与 Git 一样得到空的 index，并去掉已跟踪工作树文件，且清空过程在每个失败窗口都留下可恢复的状态。以未修改 Libra 轨重跑 TC-2824（t2060 #10）与 TC-2825（t2060 #11），完整通过后才能完成 Issue 目标。

### 非目标

### 成功定义

`switch --orphan` 后没有已跟踪路径，未跟踪文件保留；`--discard-changes` 也一样。预检拒绝、删除中途失败、空 index 发布失败、HEAD 发布失败四个窗口各有可复现的注入用例和恢复验收。`checkout --orphan` 保持现状。TC-2824 与 TC-2825 都须在未修改的 Libra 轨实际 PASS；TC-2824 因 `cat-file` 受阻时如实记录阻塞，不以 switch 聚焦测试通过替代完整 TC 通过。

## 已决议设计决策

### ADR-I1045-01: 只有 switch --orphan 清空，按「预检 → 删文件 → 原子发布空 index → 发布 HEAD」的顺序

- **Status:** 待重设计；Claude R6 `VERDICT: FAIL`。以下步骤为保留的旧草案，不得实施。
- **Context:** Git 的 `switch --orphan` 用空树做 unpack：持 index 锁（`builtin/checkout.c:883`），整体校验与更新工作树（`:907`、`:951`），失败回滚锁、index 不动（`:909`、`:921`、`:954`），成功后才 `write_locked_index`（`:962`），最后才改 HEAD。`checkout --orphan` 不碰工作树。Libra 的 `switch_to_orphan_branch`（`src/command/switch.rs:1276`）只做干净检查（`:1319`）然后改 HEAD（`:1372`），注释（`:1314-1317`）与实现不符。`git-internal 0.10.4` 的 `Index::to_file_with_hash_kind` 以 `File::create` 截断目标（`src/internal/index.rs:457-469`），`Index::save` 直接走这条路径，所以不能把空 index 直接 `save` 到当前 index。
- **Decision:** 只有 `NavigationCommand::Switch` 走下面五步，`Checkout` 原样只改 HEAD。
  1. **预检（不写任何东西）：** 不带 `--discard-changes` 时沿用现有 `ensure_clean_status`（`:1319`，退出 128，`uncommitted changes, can't switch branch`）。读入当前 index 的原始字节（用于第 5 步恢复）与 stage-0 条目，得到删除集合。对每个路径：词法上必须在工作树内；从工作树根到父目录的每一级祖先用 `symlink_metadata` 检查，任一级是符号链接就以 `ConflictOperationBlocked`（退出 128）拒绝；index 中 mode 为 160000 的 gitlink，若工作树同名目录存在且非空（已物化的子模块），即使带 `--discard-changes` 也拒绝（与 `switch.rs:848-851` 的「`--force` 也不做不安全的 gitlink 目录转换」合同一致），空目录或不存在则只从 index 去掉。预检全部通过之前不删除任何文件、不写 index、不改 HEAD。
  2. **删除已跟踪文件：** 按路径逐个 `remove_file`；`NotFound` 视为已删除，不算失败（`--discard-changes` 下最典型的脏态是已跟踪文件被手工删除）；未跟踪文件与 `.libra` 不在删除集合内。每删一个文件后，自下而上删除因此变空的父目录（不越过工作树根，目录非空就停）。任一删除失败立刻停止：不写 index、不改 HEAD，返回带路径的错误，提示用 `libra restore --worktree .` 取回已删除的已跟踪文件（它们的 blob 仍在对象库，index 未变）。
  3. **原子发布空 index：** 把空 index 用 `to_file_with_hash_kind` 写到同目录的临时路径 `<index>.orphan.tmp`（`<index>` 是 `path::index()` 给出的本工作树 index），按 `atomic_write::sync_data_enabled()` 决定是否 fsync，再 `fs::rename` 到 `<index>` 并 `fsync_parent_dir`。写临时文件或 rename 失败时删除临时文件，原 index 未被触碰，HEAD 不改，返回错误（同样提示 `libra restore --worktree .`）。
  4. **发布 HEAD：** 沿用 `switch_head_to_unborn_branch`（`:1372`）的 reflog 事务。
  5. **HEAD 发布失败的恢复：** 第 4 步失败时，用 `atomic_write::write_atomic` 把第 1 步读入的原 index 字节写回 `<index>`，然后返回 HEAD 错误；写回也失败时错误同时报告两者，并提示 `libra restore --staged --worktree --source HEAD .`。第 3–5 步实现为一个接收显式 index 路径与「发布 HEAD」future 的私有 async 函数，lib 单元测试在临时目录里注入失败的 future，不读进程当前目录。
- **失败窗口与可恢复状态：**

| 窗口 | 中断或失败后的状态 | 恢复 | 验收 |
|---|---|---|---|
| W0 预检拒绝 | 什么都没写 | 无需恢复 | I1045-01 AC3–AC5 |
| W1 删除中途失败或断电 | 部分已跟踪文件被删，index 与 HEAD 不变；`status` 显示未暂存的删除，下一次 `commit` 不会提交删除 | `libra restore --worktree .` | I1045-01 AC6、AC7 |
| W2 空 index 发布失败或断电 | 同 W1；rename 是原子的，`<index>` 要么是旧字节要么是空 index，不会是截断文件；残留的 `<index>.orphan.tmp` 下次运行时被覆盖 | 同 W1 | I1045-01 AC8 |
| W3 HEAD 发布失败 | 原 index 字节已写回，工作树文件已删，HEAD 不变，状态同 W1 | 同 W1 | I1045-02 AC8 |
| W3' 第 3 步之后、第 5 步写回之前断电 | index 为空、HEAD 在原分支，`status` 显示全部已暂存删除 | `libra restore --staged --worktree --source HEAD .`，或重跑 `libra switch --discard-changes --orphan <name>` 完成切换 | 与 Git 在 `write_locked_index` 之后、改 ref 之前断电的窗口相同；不另设注入 |

- **并发（旧草案待纠正）：** 不能仅依据 index 文件锁判断并发行为。`switch` 走中央 operation 边界的 `WorkspaceMutation` 范围租约和前后快照（`src/internal/operation/middleware.rs:99`、`:411-417`、`:445-730`）；重新设计时须核对该边界、租约失败以及 `op undo` / `op doctor` 的恢复语义，再决定 index 文件原子发布方式。
- **租约与快照的补核（2026-11-08，待设计）：** `classify_command`（`middleware.rs:95-111`）确实把 `switch` 归为 `WorkspaceMutation`，但这不是 Git 的 index 锁。边界在 `:448-454` 捕获 pre-snapshot，`:650-670` 对 operation 错误只调用 `persist_failed_operation` 并返回，不能当作命令失败自动还原。`snapshot.rs:365-382` 只在同一 hash kind 且 stat 足够时复用 index OID，`:385-402` 允许继续生成 partial 快照。没有既成证据表明强制删除的脏文件内容都能在 `op undo` 找回。新设计必须在租约成功后才允许任何破坏，分别处理：租约失败、完整或 partial 快照、哈希超时、快照写入失败、命令中途失败、后置快照失败和进程中断；为实际工作树内容、mode、symlink 目标定义可恢复存储和容量门。若采用「强制丢弃可恢复至原 index，已修改内容不保证恢复」，须在用户文档明确且不宣称完全还原；不能把通用 operation 记录当免费备份。
- **快照覆盖范围：** `snapshot.rs:187-204` 的 `WorkspaceSnapshotter::new` 默认 `CapturePolicy::TrackedAndUntracked`，`:385-402` 把 tracked 和 untracked 都纳入 manifest；但默认预算为 30 秒、100000 文件、512 MiB（`:66-70`），超过即非完整快照。快照是否能包含原 dirty 文件必须在夹具中直接验证 OID 与内容，而不只检查 `Completeness::Full` 标志。即便完整，恢复流程是否遵循 index 而非工作树原始修改，也须由新测试界定。`middleware.rs:685` 的 post-snapshot 同样执行有界捕获，故后置失败不能假定前后快照均可用于无损恢复。
- **边界入口：** `middleware.rs:283-286` 的 `run_with_operation` 是可选分类的 operation 包装；`:411-417` 按该分类获取 `ScopeLease`，不存在一个「所有命令都统一持有同一 index 锁」的全局事务。最终方案须指明 switch 实际经过的调用入口及其 `MutationClass`，在租约获取失败时不改 index、工作树或 HEAD，并通过故障注入验证。当前 `switch.rs:1319` 的干净检查和 `:1372` 的 HEAD 发布之间没有 index 清空，也不等于已有租约覆盖全部五步。
- **Alternatives considered:** 先清 index 再删文件（R4 指出：中途失败时 HEAD 在原分支而 index 已空，下一次 `commit` 会提交删除全部文件）；两条命令都清空（破坏 `checkout --orphan` 的合同与 Git 行为）；直接 `Index::save`（截断写，断电时 index 损坏）。R6 另指出 `reset.rs` 已有路径预检、index 快照和失败回滚（`:1436-1484`、`:1696-1708`、`:1976-2027`），须评估复用或抽取及其写集，而非默认再造较弱的恢复流程。
- **Consequences:** `--discard-changes` 下已修改、已暂存与已缺失的已跟踪文件都按删除集合处理；未跟踪文件始终保留（TC-2825 的 `foo.txt`）。旧守卫与两处测试索引改为「switch 清空、checkout 保留」。
- **Revisit when:** Libra 引入 index 锁，或 Git 改变 `switch --orphan` 对未跟踪文件的规则。

#### 重设计前核对：reset 守卫的适用边界

`reset.rs:1403-1427` 的 `IndexSnapshot` 区分 index 不存在与已有字节；`:1436-1484` 对 `.libra` 路径和符号链接祖先做预检；`:1976-2027` 在 index、工作树或 HEAD 发布失败时尝试恢复工作树及 index。它的 `WorktreeSnapshotKind::Tracked` 则明确假定被替换的工作树条目与 stage 0 相同，以对象 ID 作为回滚源。`switch --discard-changes --orphan` 允许丢弃已修改的已跟踪文件，因此不能不加验证地把该对象快照当作任意脏文件的完整回滚副本。新设计须明确强制模式下是否以及如何保存实际工作树内容、模式和符号链接目标，规定容量、失败与崩溃处理，并验证在 operation 租约和回滚路径下不会误删 `.libra` 或跟随越界符号链接。抽取共享 helper 如需修改 `reset.rs`，须先加入本卡写集、开工扫描、允许暂存集合与跨计划依赖，并保证旧 reset 行为不回退。

需要整套重跑的恢复同一张卡最多 3 次（携带不计次数，但每次携带之后都要重新执行第一段）；第 4 次需要整套重跑时停止，把卡保持在 `in-progress` / `locally-accepted`，在「实施证据」记录每次的上游增量，并向用户报告，由用户决定是否协调其它写者暂停推送。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1045-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

第三段，CI 通过后发布。脚本先从状态文件取回第二段记录的两个 run，重新向 GitHub 查询它们的结论、head SHA、分支与事件，必须是 success、本卡 SHA、候选分支、push，并逐个核对 run 内每个 job 都是 success（`base.yml` 的 8 个 job 在 `release/**` 上都没有跳过条件），所以漏跑或错序执行第二段时不会建 tag。本段开头先以 `WHEN=stage3` 执行外部前置检查（从本文件抽出原样运行），第一段开头同样以 `WHEN=stage1` 执行，所以这两次检查不靠执行者记得。随后确认本卡 SHA 仍在远端 `main` 上。本段可原样重跑：远端已有 `v$VERSION` 时，只有它指向本卡 SHA 且对应 Release 存在，才视为上一次第三段已成功（例如 `gh release create` 在服务端成功后客户端报错，或建 tag 后、写状态文件前中断），补记 `TAG` 后结束；tag 指向别的提交，或只有 tag 没有 Release，都停止报告，不改写 tag。远端还没有该 tag 时，候选分支必须仍指向本卡 SHA，前一个 patch 版本 `v<VERSION 的 patch − 1>` 必须已有 tag 且它的 `release.yml` run 都已结束（tag 已建而 release 仍在上传时 CDN 还是更旧的版本，两个发布会互相干扰；本族只做 patch + 1，修复模式沿用同一版本，所以前一版本就是 bump 前的基线；它没有 tag 说明有更早的发布未完成，`refuse_older_cdn` 会让两个发布互相干扰），另有两项检查与 `.github/workflows/release.yml:351-386` 的 `refuse_older_cdn` 对应：远端不存在版本号大于 `v$VERSION` 的 `vX.Y.Z` tag；`https://download.libra.tools/install.sh` 与 `install.ps1` 返回 200、能取出版本，且版本都小于 `v$VERSION`。等待 CI 的几个小时里其它计划可能已发布更高版本，此时 `gh release create` 会留下孤立 tag，而 `upload-install-scripts` 会拒绝上传。任一项不满足就停止，不建 tag：版本被抢先时按修复模式之外的正常路径，在新基线上以新的 C 组提交前滚（本卡版本号作废，记入「实施证据」）。`gh release create` 报错时先按同样规则复核远端，确认已发布才继续。

8. `blocked` 登记与解除：已 `in-progress` 的卡遇到本卡自身的 ER-10 故障（工作区只含本卡允许集合内的改动），或第 3 步第 1 小步、第三段之前的外部前置检查失败时，把本卡 `Lifecycle` 改为 `blocked`，`Acceptance` 保持 `HEAD` 已提交的值（A/B 之后工作区里尚未提交的 `locally-accepted` 先改回 `HEAD` 的值、解除后再写回，未提交的验收结论不随登记提交公开；暂存守卫按这一点核对），写明原因与解除条件，同步 `plan-status.md` 本计划行，以 `PHASE=blocked` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): block $CARD (#1045)"`，以 `PHASE=blocked` 运行提交后范围检查与计划目录推送脚本，其它计划的开工门由此看到它。`PHASE=blocked` 只暂存本文件与 `plan-status.md`，允许本卡写集内尚未提交的改动留在工作区。两种情况不登记、只停止并向用户报告，本卡保持 `in-progress`（对其它计划的开工门同样算活动写者）：C 组提交已在本地而尚未推送时（见第 4 步；计划目录推送脚本也会拒绝父提交不在远端 `main` 上的登记提交）；工作区出现本卡允许集合以外的改动时（登记提交无法与他人改动隔离）。条件恢复后用同一 `PHASE` 把 `Lifecycle` 改回 `in-progress`（提交信息写 `unblock`），再从中断处继续。

**开工门（`bash` 运行，`CARD` 为本卡 ID）：** 脚本先 fetch，并断言工作区干净、`HEAD` 等于 `origin/main`（或者是父提交为 `origin/main`、只改本文件与 `plan-status.md` 的单父提交，也就是计划目录推送脚本推送前重跑本门时的开工登记），所以扫描的是远端最新的计划文本；然后做四件事，任一不满足即非零退出，本卡保持 `pending`，不写 `in-progress`、不提交开工登记。

2. 自检：卡外的 `Lifecycle / Acceptance` 行（加粗或不加粗）若是 `in-progress` 或 `blocked` 也算失败；卡内第一行之后若还有加粗的活动 `Lifecycle / Acceptance` 字段行，同样失败。这两种情况说明有标题格式不同的卡没被切出来。卡内不加粗的历史日志行（例如 `plan-20260904.md:4665`）不计。
3. issues/1040–1057 的其它计划中，任何一张卡不是 `pending`（Acceptance 半边不是 `locally-accepted` 或 `remote-pending`），也不是 `done` / `complete`，都失败（全串行，`plan-status.md` 第六节 DEP-I1040-1049-REL）；这一项比第 1 项更严，`released`、`deferred`、`blocked` 的豁免形态与无法解析的卡在家族内一律失败。
