## 文档职责

修复「从未配置 cloud 的仓库仍按 cloud 语义报警并计费」的三类缺陷：object-index 记账的失败诊断与措辞、缺少 cloud 配置时的稳定错误码与类别及提示，以及每次 object-index 记账失败时固定约 9 秒的重试预算。交付物包括 `src/cli.rs` 的诊断接线与回放文案、`src/command/cloud.rs` 的配置探针与共享键清单、`src/utils/error.rs` 与 `src/command/cloud/sync.rs` 的失败分类、`src/utils/client_storage.rs` 的重试策略、对应测试、EN/zh-CN/开发文档、`docs/error-codes.md`、`COMPATIBILITY.md`、网站页，以及七张卡各自的独立版本发布。

### 适用范围

- 未配置 cloud（`LIBRA_D1_*` 与 `LIBRA_STORAGE_*` 七个必需键在 env 与 `vault.env.*` 均缺失）的仓库中，每次 `commit` 等写对象命令因 object-index 写入失败而留下的 background drain 警告、`--exit-code-on-warning` 造成的退出码 9，以及随后只读命令预检回放失败时的 `durable cloud object-index repair is still pending` 警告措辞。
- `libra cloud sync` / `libra cloud restore` 在缺少 cloud 凭据时的稳定错误码、类别、结构细节与 hint；`cloud sync` 在失败前是否已经输出 `Starting cloud sync...` 进度行，以及是否发出 `cloud_sync.start` JSON 事件。
- object-index 记账的单条重试循环与批量回放循环的重试上限（当前 `INDEX_UPDATE_MAX_ATTEMPTS = 12`、`100 * attempt` 线性退避）。
- 上述行为的 EN、zh-CN、开发文档、`docs/error-codes.md`、`docs/development/cli-error-contract-design.md`、`COMPATIBILITY.md` 与网站 `/mnt/data/gitmono/libra-backend` 的对应页。

### 非目标

- **不跳过 object-index 入队或 marker 写入。** `object_index` 既是 `cloud sync` 的对象身份来源（`src/command/cloud/snapshot.rs:1195-1240` 只冻结 `is_synced = 0` 行），也是 agent capture/清理的完整性依据。按「未配置 cloud 就不记账」处理会让配置 cloud 之前写入的对象静默不进入后续备份，属数据丢失级风险。本计划只修诊断、错误分类与重试预算，不改记账本身的无条件性。
- **不让 `cloud sync` 在没有配置时以退出码 0/1「成功」返回。** 未完成的同步不得被脚本当成成功；保持 fail-closed，只把错误码换成不再声称「认证失败」的配置类码。
- **不改全局配置读取判定。** `CLOUD_GLOBAL_CONFIG_KEYS`（`src/cli.rs:83`）驱动的 `command_may_read_global_config`（`src/cli.rs:2743-2754`）与 schema 强制策略（`src/cli.rs:2725-2730`）保持逐字不变；探针的 7 键清单独立维护，合并两份清单登记为 `DEFER-I1063-05`。
- 不改 marker 文件名/内容契约、[plan-20260918.md](../plan-20260918.md) 的 ADR-OI-02..05、回放分页上限、`DRAIN_BUDGET`（60 秒）、`INDEX_REPAIR_LOCK_WAIT_TIMEOUT`（10 秒 marker 锁等待）或 200 ms 单次 upsert 锁超时。
- 不改 `cloud status` 的本地口径（它在无凭据下必须继续可用），不改 D1/R2 协议、`cloud sync` 的 capture-kind 拒绝顺序、R2 对象布局或 restore 语义。
- 不在本计划内把回放推迟到前台写事务释放锁之后（Issue 建议的最后一项），见 `DEFER-I1063-01`。

### 成功定义

未配置 cloud 的仓库中，一次 object-index 写入失败不再产生 cloud 相关 stderr 警告，也不再因该后台告警使命令以退出码 9 结束；marker 与下一命令的自动回放保持不变。**边界：**「不再退出 9」只覆盖后台 drain 的告警；预检回放**失败**（确有 marker 无法回放，见 `src/cli.rs:2613-2618`）仍按 `emit_warning` 记录并可使 `--exit-code-on-warning` 退出 9（`src/cli.rs:4073-4077`）——那是「写入尚未记账」的真实信号，本计划只把它的措辞改得 cloud 中立，不消除它；配置了（或部分配置了）cloud 的仓库仍能看到可操作的 cloud 后果提示。`libra cloud sync`/`restore` 缺配置时给出新的配置类稳定码（不再用 `LBR-AUTH-001`）、指向可执行的配置动作、且在失败前不再打印 `Starting cloud sync...` 或发出 `cloud_sync.start`。object-index 记账失败的重试有明确的**单次调用睡眠预算**（默认约 2 秒，按顶层调用共享且按调用隔离，可用诊断环境变量调整），耗尽后不再退避等待，放弃时输出一次带 attempts/elapsed 的自诊断日志。七张卡各自取得适用 A/B/C/D、网站部署与最终全量证据后，本计划才可收口；产品完成不自动关闭远端 Issue。

## 已决议设计决策

### ADR-I1063-01：保留 object-index 记账与 marker 的无条件性

- **Status:** Accepted（计划设计决策，尚未实作）。
- **Context:** `object_index` 行同时服务 `cloud sync` 的对象身份冻结（`snapshot.rs:1195-1240` 只上传 `is_synced = 0` 行）与 agent capture/清理的完整性检查；marker 是「payload 已落盘、行未写入」的唯一 durability 证据。Issue 提出的第一选项是「没有 cloud 配置就不记账」。
- **Decision:** 不按 cloud 配置跳过入队、marker 或回放。缺少 cloud 配置只影响**诊断呈现**（I1063-07/01/06）与**错误分类**（I1063-02/03）；记账与回放语义保持现状，包含每条命令的预检回放、分页上限与 fail-closed。
- **Alternatives considered:** 未配置即不记账——会在用户日后配置 cloud 时静默漏备份配置前写入的对象，且破坏 agent 完整性依据；仅在 debug 级记账——同样丢失 durability 证据。
- **Consequences:** 未配置 cloud 的仓库仍会累积 `is_synced = 0` 行与（失败时）marker；`cloud status` 的本地 pending 计数继续可用，作为用户查看这些行的入口。文档须明确「记账与 cloud 无关，cloud 只是这些行的一个消费者」。
- **Revisit when:** 出现独立的「本地完整性账本」取代 `object_index` 的迁移计划，或维护者接受配置前对象不进入备份的语义。

### ADR-I1063-02：单点 cloud 配置探针与四态判定，仅抑制「云后果」措辞

- **Status:** Accepted（计划设计决策，尚未实作）。
- **Context:** 诊断侧完全没有配置感知，导致未配置仓库也收到「`cloud sync` 会 fail-closed」的死路提示；`validate_cloud_backup_env` 的 7 键清单与诊断探针若各写一份，会随 D1/R2 键演进而漂移。`CLOUD_GLOBAL_CONFIG_KEYS`（`src/cli.rs:83`）虽然也列 D1 键，但它参与全局配置读取判定（`command_may_read_global_config`，`src/cli.rs:2743-2754`，影响 `src/cli.rs:2725-2730` 的 schema 强制），把 R2 键并进去会改变 cloud 命令的 fail-closed 判定——本计划明确不改这条路径。
- **Decision:** 在 `src/command/cloud.rs` 建立探针与单一权威键清单：`CLOUD_D1_REQUIRED_KEYS`（3 键）、`CLOUD_R2_REQUIRED_KEYS`（4 键）与合并视图 `CLOUD_BACKUP_REQUIRED_KEYS`（7 键，顺序与 `validate_cloud_backup_env` 现状一致），以及 `cloud_backup_configuration() -> CloudBackupConfiguration`，逐键按 env → `vault.env.*`（经 `config::resolve_env_for_target` + `LocalIdentityTarget::ExplicitDb`）解析并返回 `Configured` / `PartiallyConfigured` / `NotConfigured` / `Unknown`（I1063-07）。**判定以 `cloud sync` 的真实前置为准：7 个键全部可解析 → `Configured`；至少 1 个但不足 7 个 → `PartiallyConfigured`；0 个 → `NotConfigured`；解析过程出错或无仓库库路径 → `Unknown`。** 只看 D1 3 键会把「D1 齐全但 R2 缺失」误判为 `Configured`，使 `cloud sync` 必然失败却仍承诺云路径可用，故不采用。`validate_cloud_backup_env` 用同一常量生成清单（保持既有顺序与措辞，`skip_r2` 取前 3 键）；`CLOUD_GLOBAL_CONFIG_KEYS` 与全局配置读取判定逐字不变。诊断侧（I1063-01）：仅 `NotConfigured` 把 background drain 的两条 post-envelope 警告（超时与失败计数）降为一次 `tracing::warn!`（不写 stderr、不记 `record_warning_message`、因而不再计入 `--exit-code-on-warning`），`Configured`/`PartiallyConfigured`/`Unknown` 保留原警告；预检回放消息在所有状态下保留（它意味着确有 marker 未能记账，不是配置噪声），措辞 cloud 中立并给出下一步（I1063-06）；该路径仍走 `utils::error::emit_warning`（`src/cli.rs:2594-2598`、`:2613-2618`），因此仍可使 `--exit-code-on-warning` 退出 9（`src/cli.rs:4073-4077`），本计划不消除这一诊断。探针只在实际失败/超时路径调用（成功排空时零额外 I/O）。
- **Alternatives considered:** 在诊断处直接读 `std::env` 只看 env 层——漏掉 `vault.env.*` 用户；让 `client_storage` 自己判断——把 UI 义务塞进存储层且难以单测；探针失败按 `NotConfigured` 静默——会在配置库不可读时隐藏真实 warning，违反 GC-07；复用 `CLOUD_GLOBAL_CONFIG_KEYS`——会把诊断探针绑到全局配置 fail-closed 判定上。
- **Consequences:** 需要在 `report_background_index_update_outcome` 增加判定参数并更新其单测；`PartiallyConfigured` 保留完整警告，避免半配置状态下丢掉可执行提示。按 7 键判定会让「只配了 D1」的仓库落到 `PartiallyConfigured` 并保留警告——这正是想要的：该仓库的 `cloud sync` 确实会失败，只是不再通过后台记账路径抱怨。fail-open 分支必须记 `tracing::warn!`，且文档写明「未配置时不显示云后果提示」。两份清单的合并延后为 `DEFER-I1063-05`。
- **Revisit when:** 出现第二个 cloud 配置来源（如 per-repo 远端 profile），或维护者要求把探针结果暴露为机器可读字段（见 `DEFER-I1063-02`）。

### ADR-I1063-03：缺配置改用新的配置类稳定码 `LBR-CLOUD-001`

- **Status:** Accepted（计划设计决策，尚未实作）。
- **Context:** 缺配置在当前实现中是 `CliError::auth` + `LBR-AUTH-001`（auth 类别、退出 128、fine-grained 6），使脚本无法区分「凭据错误」与「从未配置」。`src/utils/error.rs:181-188` 规定新增码需改 4 处并同步 `docs/error-codes.md` 与 `docs/development/cli-error-contract-design.md`。hint 现状只有「设置变量后重试」，且朴素写法 `libra config set --local vault.env.<KEY> <value>` 会把密钥留在 shell 历史与进程 argv 中，与 `src/command/config.rs:75-76` 的交互/`--stdin` 口径冲突。
- **Decision:** 分两步落地，各占一张卡。**I1063-02（码登记）**：新增 `StableErrorCode::CloudNotConfigured`，`as_str = "LBR-CLOUD-001"`，`category = CliErrorCategory::Config`（默认退出 128、fine-grained 8），`description` 说明「cloud backup 未配置：所需 D1/R2 键在 env 与 `vault.env.*` 均缺失」，按上述四步流程登记并钉测。**I1063-03（映射与文案）**：`CloudError::MissingEnv` 改为 `CliError::fatal(message).with_stable_code(CloudNotConfigured)`，保留 `fatal:` 前缀、消息文本 `missing cloud configuration for {operation}: <keys>`、`missing_keys`/`raw_detail` 结构细节与 note 追加；hint 给出**不回显密钥**的动作：`libra config set --local vault.env.<KEY>`（交互输入）或 `printf '%s' "$SECRET" | libra config set --stdin --local vault.env.<KEY>`，并说明 cloud 为可选且 `libra cloud status` 无需凭据；同卡修正 `docs/commands/cloud.md` 与网站页「缺凭据 = `LBR-CLI-002`」的矛盾。**I1063-04** 单独把 `progress.on_starting()` 移到 `validate_cloud_backup_env(false).await?` 之后（capture-kind 拒绝仍最早）。拆分理由：码登记、失败契约、进度顺序是三个可独立失败并可独立回滚的公开行为面，合卡会使单卡独立判据超过 G-03 上限。
- **Alternatives considered:** 复用 `LBR-CONFIG-001`——其语义是「配置库 schema 过新」，混用会误导；Issue 建议的 `LBR-CLOUD-003`——`LBR-CLOUD-001` 为本族首个码，无需跳号；`LBR-CLI-002`（文档当前写法）——与代码事实不符且属参数错误类别。
- **Consequences:** 这是公开契约变化（因此 02/03 记 M）：脚本若匹配 `LBR-AUTH-001` → auth 分支需更新；`docs/commands/cloud.md`/zh-CN/开发文档/`docs/error-codes.md`/`docs/development/cli-error-contract-design.md`/`COMPATIBILITY.md`/网站页必须同卡改，Wave 5 三个 live-gated 断言与 `command_test` 的 cloud 断言同步更新。退出码仍为 128，不引入新的退出码族。
- **Revisit when:** 需要区分「完全未配置」与「部分配置」时，可在同一 `LBR-CLOUD` 族新增码（走新的计划，不在本卡临时加）。

### ADR-I1063-04：墙钟重试预算替代固定次数，退避有界且自诊断

- **Status:** Accepted（计划设计决策，尚未实作）。
- **Context:** 12 × 200 ms 尝试 + 100·n ms 退避的理论上限约 9 秒，慢盘实测单条 6.4–9.3 秒、批量回放 6.7 秒；`INDEX_UPDATE_MAX_ATTEMPTS` 是次数而非时间，磁盘越慢总时长越大。Issue 要求「可配置预算或推迟回放」，并要自诊断耗时。逐对象各自计时的预算仍不能约束一次命令的总等待（N 个对象 × 2 秒），因此预算必须按**调用**而非按对象计量。现有 `IndexWorkScope`（`src/utils/client_storage.rs:1128-1147`）已按顶层调用隔离 `failures`/`pending` 计数，由 `with_background_index_failure_scope`（`:2146-2152`，调用点 `src/cli.rs:3355-3359`）在每次 CLI 调用新建；但 `current_index_work_scope()`（`:866-871`）在无 task-local 时回退**进程级** `UNSCOPED_INDEX_WORK_SCOPE`，且入队消息 `IndexUpdateMsg`（`:2606-2617`）只 clone 两个计数器——把预算状态放进这两个容器会分别导致「同进程的库调用共享已耗尽 deadline」与「后台消费任务看不到预算」。
- **Decision:** 预算按**每次顶层调用**计量，载体是既有 `IndexWorkScope`：
  1. 新增 `RetryBudgetHandle { budget_ms: u64, deadline: Arc<OnceLock<Instant>> }`，`RetryBudgetHandle::from_env()` 读取 `LIBRA_OBJECT_INDEX_RETRY_BUDGET_MS`（默认 2000 ms，clamp 到 `0..=60_000`，非法值回落默认并记一次 `tracing::warn!`）并惰性初始化 deadline。
  2. `IndexWorkScope` 增加 `retry_budget: Option<RetryBudgetHandle>`；新增 `IndexWorkScope::for_invocation()` 返回 `Some(RetryBudgetHandle::from_env())`，由 `with_background_index_failure_scope`（CLI 每次调用的入口，`src/cli.rs:3356`）使用，因此每次调用拿到**新** budget 与新 deadline，env 也在那时重读一次。`IndexWorkScope::new()` 保持 `retry_budget: None`，因为进程级 `UNSCOPED_INDEX_WORK_SCOPE` 也用它构造。
  3. 进程级 `UNSCOPED_INDEX_WORK_SCOPE` 的 `retry_budget` 恒为 `None`：直接调用 `update_object_index`/`update_object_index_batch` 的库调用者在**该次顶层记账调用入口**取 `RetryBudgetHandle::from_env()`（每次调用新 deadline、重读 env），不使用任何进程级静态缓存，因此不会继承上一次调用的耗尽预算。计数器语义不变（仍按既有 fallback 共享）。
  4. `IndexUpdateMsg` 增加 `retry_budget: RetryBudgetHandle`，入队时从 `current_index_work_scope().retry_budget`（或第 3 条的按调用句柄）clone 进去，后台消费任务因此与入队调用**共享同一 deadline**，不会各自再起一份预算。
  5. 单条与批量两个循环内 N 个对象共用同一 deadline，不叠加为 N × 预算。退避 `min(50 ms · 2^(n-1), 400 ms)` 加 ≤25% 抖动，每次 sleep 取 `min(退避值, 剩余预算)`，剩余为 0 时不再 sleep。
  6. 预算耗尽后：剩余对象各允许**一次**无退避尝试（单次尝试上界是既有 200 ms busy timeout），随后立即放弃并保留 marker——拒绝/锁竞争场景下尝试是瞬时的，实测 6 对象总耗时从 39.9 秒降到约 2 秒。放弃时只记一次 `tracing::warn!`（字段含 attempts、elapsed_ms、budget_ms、失败对象数、失败 marker 数与最后一次错误），每次重试的 `tracing::debug!` 保留。返回的错误串与 marker 行为完全不变（`failed to reconcile {n} durable object-index repair marker(s) in …`），`DRAIN_BUDGET`、200 ms 单次 upsert 锁超时、`INDEX_REPAIR_LOCK_WAIT_TIMEOUT`（10 秒 marker 锁等待，与 upsert 重试是两套机制）与 ADR-OI-02..05 契约不动。
- **Alternatives considered:** 保留次数上限只缩短退避——慢盘下仍然是不可预测的墙钟；把预算写死 2 秒、不设环境变量——Issue 明确要求可调，且极慢文件系统用户需要延长窗口；进程级静态 `OnceLock<Instant>` 或静态读 env——同进程第二次调用会继承已耗尽 deadline 与过期配置；推迟回放到锁释放后——见 `DEFER-I1063-01`。
- **Consequences:** 承诺的边界是「单命令累计**退避睡眠** ≤ 预算」，不是「命令总时长 ≤ 预算」——每对象最后那次尝试仍受 200 ms busy timeout 约束，且 `DRAIN_BUDGET` 仍是后台排空的总闸；性能摘要与测试断言都按这个边界写，避免不可证明的承诺。默认预算下 marker 更容易残留，但残留是设计内的 durability 证据，由下一条命令回放；文档须说明「预算耗尽不是数据丢失，而是延后记账」，并说明该环境变量属诊断/高级 knob。新增的可配置面使本卡按 G-04 记 M（一处配置面变化）。
- **Revisit when:** 出现跨进程共享的记账队列或后台常驻 worker，使「下一条命令回放」不再是主要恢复路径。

### ADR-I1063-05：诊断措辞与错误码分层，不复用同一个「cloud 已配置」假设

- **Status:** Accepted（计划设计决策，尚未实作）。
- **Context:** 症状同时出现在「写对象的后台记账」（`src/cli.rs` 的 drain 与预检回放）与「用户显式运行的 `cloud sync`/`restore`」。两者对「cloud 是否配置」的依赖不同：前者只是记账失败，后者才能真正失败。
- **Decision:** 按调用者分层：用户显式运行 cloud 命令时，缺配置是**命令失败**（`LBR-CLOUD-001`，I1063-02/03）；仓库内后台记账/回放失败是**本地 durability 事件**，措辞只说「本地 object-index 记账未完成、marker 已保留、下一条命令会重试」，只有 cloud 已（部分）配置时才附加「`cloud sync` 在修复前会 fail-closed」（I1063-01/06）。两处共享同一探针与键清单，但文案与码不互相冒充。
- **Alternatives considered:** 统一用一条措辞——会在其中一侧必然失真；让后台路径也返回 `LBR-CLOUD-001`——后台失败不是命令返回值，会破坏既有退出码与 warning 语义。
- **Consequences:** 需要维护两份文案并各自有测试；文档须同时说明两条路径的差别，避免用户把后台警告当成 cloud 命令错误。
- **Revisit when:** 引入统一的「本地 durability」错误族，能把 marker 残留升级为一等状态时。

- 每卡推进时同批更新本文与 [plan-status.md](../plan-status.md)，新记录使用 `YYYY-MM-DD HH:MM:SS UTC`；所有测试摘要、SHA、run ID、审查与失败只写入本文「实施证据汇总」，不新建证据文件或目录。
- 开工前刷新 HEAD、Issue、源码/测试 target、`plan-status.md` 中在途版本面写者与网站状态；若现状已修复，只补缺失测试/文档并按实际差异重核卡粒度，不重复实现。
- 采用普通版本化交付，非 v2.16 具名 code-only；产品卡、计划完成与远端 Issue 关闭是三个不同动作。

## 全局工程约束

继承模板 GC-01～GC-13、ER-01～ER-14 与 G-01～G-11。GC-13 **N/A**：七张卡都不改 SQLite schema、迁移、bootstrap、schema top-up、兼容检查或迁移 fixture；本计划只读配置值并调整既有 `object_index` 写入的重试时序，句柄、连接构造与 200 ms 锁超时不变。另有：

1. 不得削弱 marker 契约：不回退 `persist_index_repair_marker`、不回退回放幂等/接管锁/分页上限，不把「预算耗尽」当作成功；`update_object_index_*` 的错误串必须保持现有文本形态（下游按它做诊断）。
2. 探针失败按 GC-07 显式 fail-open：保留原有警告并记 `tracing::warn!`，不得静默；探针不得读取真实用户配置库以外的作用域，不得把凭据值写日志。
3. `CLOUD_GLOBAL_CONFIG_KEYS`、`command_may_read_global_config` 与 `enforce_global_config_schema_policy` 的判定逐字不变；`compat_global_config_schema_future` 必须保持通过。
4. 新生产码不得新增无解释的 `unwrap` / `expect` / `panic!`；环境变量解析、配置读取与 DB 错误须带上下文；`compat_client_storage_production_unwrap_guard` 与 `compat_util_production_unwrap_guard` 必须保持通过。
5. 测试以子进程 + 显式 cwd 建独立临时仓库并清理 `LIBRA_D1_*`/`LIBRA_STORAGE_*` 继承环境；凡读写进程 env 的用例（探针、`LIBRA_OBJECT_INDEX_RETRY_BUDGET_MS`、cloud 键注入）一律标 `#[serial(env)]`；集成用例的标注登记在 `tests/SERIAL_REGISTRY.tsv`，`src/` 内联用例的标注登记在 `tests/SRC_SERIAL_REGISTRY.tsv`（两处皆由 `compat_serial_registry` 重跑分类器校验），任一文件改动后执行 `sh tests/NEXTEST_GROUPS.sh` 重生成 `.config/nextest.toml`；不新增 test target 时不改 `Cargo.toml` 的 `[[test]]`。
6. 诊断断言只断言本计划引入的措辞与码，不断言与 cloud 无关的既有输出；退出码断言使用 `--exit-code-on-warning` 显式开关，避免把默认退出码当契约。
7. 用户可见提示不得把密钥放进 argv 示例：文档与 hint 一律使用交互输入或 `--stdin`（对齐 `src/command/config.rs:75-76`）。
