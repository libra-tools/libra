### 适用范围

- `libra update-index` 的以下表面：
  - `--cacheinfo` 的 Git 参数语法：三个位置参数的旧式 `--cacheinfo <mode> <object> <path>`（正文场景 5，评论 10 的 TC-2076/3166/3169/3197）、新旧两式的判定规则、参数不足与 `--cacheinfo=<值>` 的用法错误、令牌解析失败的诊断；
  - `--cacheinfo` 的 mode 取值按 Git `create_ce_mode` 规范化（`0644` → `100644` 等，TC-2076 使用 `0644`）；
  - `--verbose` 对 `--cacheinfo` 条目输出 `add '<path>'`（TC-3166/3169）；
  - 保存 index 前拒绝 null 对象 id（全零 OID）条目（TC-3169 的 `--cacheinfo does not accept blob null sha1`）；
  - 位置路径与 `--stdin` 从工作树重新暂存时清除 intent-to-add 位（`--again` 复用同一路径，见 ADR-UX-07）；
  - `--again`（正文场景 7，TC-3163/3167）。
- 对应文档：`docs/commands/update-index.md`、`docs/commands/zh-CN/update-index.md`、由同步脚本生成的网站页 `../libra-backend/apps/tanstack-app/content/docs/commands/update-index.en.md`、开发文档 `docs/development/commands/update-index.md`、`COMPATIBILITY.md` 第 242 行 `update-index` 行（原地改写，不增删行）；UX-01、UX-02 另改 `docs/error-codes.md` 第 167–173 行之后的退出码例外说明；UX-04 另改 `docs/development/commands/_compatibility.md` 第 286 行（#479 DEFER-01 注记）与 [`issues/479.md`](479.md) DEFER-01 行（`1a238f7` 第 1270 行；工作树含他人未提交改动时为第 1295 行）的承接说明。
- 测试：`tests/command/update_index_test.rs`（`command_test` 目标）。

### 非目标

- 不实现 `--assume-unchanged`/`--no-assume-unchanged` 及其在 `status`/`diff`/`add`/`commit -a`/`grep`/`ls-files` 中的生效（正文场景 6，TC-1590/1593）：ADR-UX-05 显式归类为不支持并写明原因（与 issues/637 的遗留 `CE_VALID` 位冲突、跨多命令且 `grep.rs` 由 [`issues/535.md`](535.md) 锁定），登记 DEFER-UX-01；#540 因此保持 OPEN（DEP-UX-05）。
- 不实现 `--unresolve`：它属 #540 范围，但 Libra 不记录 resolve-undo 扩展，显式延后（DEFER-UX-02，#540 为此保持 OPEN）；也不实现 `--again` 的短名 `-g`（DEFER-UX-03）。
- 不改 `--cacheinfo` 写入时的扩展标志与高阶段语义（Git 的 `add_index_entry` 不继承 skip-worktree/intent-to-add、写 stage 0 时删除同名 1–3 阶段；Libra 继承两位且保留高阶段，探针 #17、#18），也不改位置路径对未合并路径的处理（探针 #19）：DEFER-UX-04，建议另立 issue（DEP-UX-08）。
- 不改位置路径相对仓库根而非当前目录解析的既有行为（探针 #20，DEFER-UX-05）；`--again` 的 pathspec 按 Git 相对当前目录解析（ADR-UX-06），不受此影响。
- 不改 index 路径校验与 Git `verify_path` 的差异（`./x`、`.git/x` 等，探针 #11，DEFER-UX-06），也不改 `--index-info` 的 mode 白名单（DEFER-UX-07）。
- 不改 `--verbose` 对 skip-worktree 条目的输出差异（Git 输出 `add '<path>'`，Libra 不输出或输出 `remove '<path>'`，探针 #21，DEFER-UX-08）。
- 不支持 Git 测试专用环境变量 `GIT_ALLOW_NULL_SHA1`（DEFER-UX-09）。
- 不修挡住部分 #540 引用用例的其它命令缺口：全局 `-C`（[#686](https://github.com/libra-tools/libra/issues/686)，TC-0375/2530）、`checkout --theirs`（[#703](https://github.com/libra-tools/libra/issues/703)）、`merge --no-commit` 快进（[#992](https://github.com/libra-tools/libra/issues/992)）、成功路径 stdout 噪声（[#659](https://github.com/libra-tools/libra/issues/659)）、`add --chmod` 稀疏条目（[#667](https://github.com/libra-tools/libra/issues/667)）、`diff --stat` 的 `Bin`（[#830](https://github.com/libra-tools/libra/issues/830)）、`pull --rebase` 冲突提示文案（尚无 issue）。只登记依赖（DEP-UX-07），不把这些用例记为通过。
- 不改 Libra 全局错误输出合同（`Error-Code:` 行与 JSON 行）。上游用例中以 `test_cmp` 比较完整 stderr 的，会继续因这两行失败。
- 计划完成不以关闭 #540 为条件；#540 的回复与关闭见 DEP-UX-05。

### 成功定义

- #540 中仍能复现的各项按 Git 处理：
  - `--cacheinfo <mode> <object> <path>` 可用，新旧两式按 Git 的判定规则选取；参数不足与 `--cacheinfo=<值>` 按 Git 以 129 拒绝；令牌非法以 `fatal: git update-index: --cacheinfo cannot add <令牌>` 拒绝；
  - mode 按 Git 规范化；`--verbose` 为 `--cacheinfo` 条目输出 `add '<path>'`；
  - index 中出现全零对象 id 时拒绝保存（128，index 字节不变）；
  - `--again` 只重新暂存与 `HEAD` 不同的 stage-0 条目，按 Git 消费其后全部参数作为 pathspec；
  - 位置路径与 `--stdin` 重新暂存清除 intent-to-add 位。
- `--assume-unchanged` 与 `--unresolve` 继续不公开，并在 EN/zh-CN/网站文档与 `COMPATIBILITY.md` 中写明原因与承接位置。
- 每项行为有 `command_test` 中的具名用例；期望值取自本计划「行为探针」表，或由测试在夹具内用 `libra hash-object` 现算。
- EN、zh-CN、网站页、开发文档、`COMPATIBILITY.md` 第 242 行与实现一致，`--help` 同步。
- 六张实现卡各自完成独立发布切片（ER-08），全部卡 `done` / `complete`，计划收口点 CLOSE-540 全绿。
- UX-05 已把 libra-testcases 维护者公开发布的复跑结果逐行写入本计划，并为仍失败的用例写明阻塞方。

### ADR-UX-01：范围以 #540 为准，探针新发现的缺口只登记

- **Status:** Accepted
- **Context:** #540 正文场景 1–4 已由 issues/479 交付（探针 #23）；维护者 2026-11-01 的评论说明本 issue 只为 479 的 DEFER-01/02 保持 OPEN；2026-11-03 的评论补了 6 个 TC。探针另发现 `update-index` 的若干同文件缺口（探针 #17–#22）。
- **Decision:**
  - 处理：旧式 `--cacheinfo` 及其参数语法（UX-01）、mode 规范化（UX-06）、`--verbose` 报告（UX-07）；null oid 拒绝（UX-02，TC-3169 需要）；`--again`（UX-04）。
  - 吸收：位置路径与 `--stdin` 重新暂存清除 intent-to-add（UX-03）。理由：`--again` 逐条复用位置路径的处理，不先修正就会把 intent-to-add 条目暂存成与 Git 不同的状态（探针 #16、#22）。
  - 归类：`--assume-unchanged` 显式不支持（ADR-UX-05）；`--unresolve` 属 #540 保持 OPEN 的范围（维护者 2026-11-01 评论点名 479 的 DEFER-01 `--unresolve`/`--again`），但 Libra 不记录 resolve-undo 数据、无从恢复，本计划显式延后（DEFER-UX-02），#540 因此继续为它保持 OPEN；`-g` 延后（DEFER-UX-03）。
  - 其余探针发现（探针 #17–#21、#12 中的 `.` 组件）只登记 DEFER-UX-04..08，并建议另立 issue（DEP-UX-08）。

- **Consequences:** #540 在本计划完成后仍保持 OPEN（DEFER-UX-01）。
- **Revisit when:** 维护者为 DEFER-UX-04..08 立 issue 时，由新计划承接，并在开工前与本计划的写集串行。

### ADR-UX-02：`--cacheinfo` 的参数语法

- **Status:** Accepted
- **Context:** Git 的 `cacheinfo_callback`（`builtin/update-index.c:814-840`）是低层回调，按下一参数的形状决定消费 1 个还是 3 个参数；`PARSE_OPT_NOARG` 禁止 `--cacheinfo=<值>`（探针 #7–#13）。Libra 的 clap 字段每次只取一个值，漫游器也只取下一个令牌（`update_index.rs:425-436`）。
- **Decision:**
  - **clap 层：** `cacheinfo` 字段改为接受 0 或 1 个值并允许以 `-` 开头的值（`num_args = 0..=1`、`allow_hyphen_values = true`），只做表面校验；旧式的第 2、3 个令牌在 clap 层落入位置参数 `paths`。实际消费由漫游器决定（GC-UX-01）。
  - **漫游器可测与先行：** 把 `ordered_operations` 中「令牌序列 → 操作序列」的部分提取为纯函数（同时更正一个既有错误：根命令的 `--color` 为 `num_args = 0..=1`、`require_equals = true`，裸 `--color` 不带值（`src/cli.rs:264-272`），漫游器却把它的下一个令牌当作值跳过（`update_index.rs:392`）；改为裸 `--color` 不消费令牌，`--color=<v>` 照旧；另一个既有遗漏：根命令的 `--json` 同为 `num_args = 0..=1`、`require_equals = true`（`src/cli.rs:239-249`），漫游器的全局旗标清单有 `-J` 与 `--json=…` 却没有裸 `--json`（`update_index.rs:372-391`），会把它当作路径；改为裸 `--json` 作为全局旗标跳过） `ordered_operations_from(tokens: &[String]) -> CliResult<Vec<Op>>`（`ordered_operations` 只负责从 `std::env::args()` 取出子命令之后的令牌再调用它），以便单元测试；`execute_safe` 改为先完成漫游、再按 `--index-file` 选择并加载 index。因此漫游阶段的一切拒绝都发生在选择或读取任何 index 之前。
  - **漫游器：** 遇到令牌 `--cacheinfo` 时，设其后剩余令牌为 `T1, T2, …`：
    1. 若 `T1` 是新式，即依次为：可选的 ASCII 空白（空格、`\t`、`\n`、`\v`、`\f`、`\r`）、可选的 `+`、一个或多个 `0-7` 数字（值不超过 `u32::MAX`）、`,`、恰为当前 hash 十六进制长度的十六进制数字（大小写均可）、`,`、其余全部为路径（可为空）——则消费 1 个令牌。
    2. 否则，若剩余令牌少于 3 个，为用法拒绝（GC-UX-05 U 型）`option 'cacheinfo' expects <mode>,<sha1>,<path>`。
    3. 否则消费 3 个令牌 `M`、`H`、`P`。若 `H` 或 `P` 以 `-` 开头，为 U 型拒绝 `option 'cacheinfo' operand '<令牌>' starts with '-'; use --cacheinfo <mode>,<object>,<path>`（理由：clap 已把可识别的选项（如 `--index-file=<f>`、`--verbose`、全局 `--json`）当作选项生效，漫游器若再把它当作路径就会出现「选项与操作数两用」，例如把写入目标改到另一个 index；Git 无此问题，这是有意差异，文档写明）。否则 `M` 须为上式的 mode 部分（不含 `,`），`H` 须恰为当前 hash 十六进制长度的十六进制数字，否则为 C 型拒绝，令牌分别为 `M`、`H`。`M` 以 `-` 开头时不会被 clap 当作选项（它是 `--cacheinfo` 的值），按 C 型处理（与 Git 一致）。
  - **令牌 `--cacheinfo=<值>`：** 按 Git 一律为 U 型拒绝 ``option `cacheinfo' takes no value``（Libra 文档从未写过该形式）。
  - **条目检查：** 解析成功后依次检查 mode 与路径（沿用 `validate_index_path`）；失败为 C 型拒绝，令牌为路径 `P`（新式为逗号后的路径部分），与 Git `add_cacheinfo` 失败时 `die` 输出路径一致。mode 检查在 UX-01 中仍是既有的四值白名单（失败提示 `unsupported mode <八进制值> (expected 100644, 100755, 120000 or 160000)`），由 UX-06 按 ADR-UX-03 换为规范化。
  - **C 型消息与提示：** 消息 `git update-index: --cacheinfo cannot add <令牌>`；提示按原因取一条：`invalid mode '<令牌>'`、`invalid object id '<令牌>' (expected <n> hex digits)`（`<n>` 为当前 hash 十六进制长度）、`invalid path '<令牌>' (empty, absolute, drive-letter or '..' components are not allowed)`、UX-01 的白名单提示（见上一条），以及 UX-06 起的 `unsupported mode <八进制值> (directory entries cannot be registered)`。
  - **保持 Libra 既有宽松：** `--cacheinfo` 登记 index 中不存在的路径不要求 `--add`（探针 #2；Libra 文档示例与既有用例依赖这一点，Git 脚本总是给出 `--add`，不受影响）。
  - **有意差异（文档写明）：**
    - Git 新式的 mode 部分按 `strtoul` 还接受 `-0`（值为 0）；Libra 两式都拒绝含 `-` 的 mode。
    - Git 旧式 oid 令牌只读前 `<n>` 位、忽略尾随字符（探针 #11）；Libra 要求令牌恰为 `<n>` 位。
    - 恰为 `040000` 的 mode：Git 写出稀疏目录条目（探针 #6），其它目录类型被规范为 gitlink；Libra 对类型位为 `040000` 的 mode 一律 C 型拒绝。
    - 旧式第 2、3 个令牌以 `-` 开头时：不可识别的（如 `-x`）由 clap 报 129 `unexpected argument`；可识别的由漫游器按上文 U 型拒绝。两种情况都不写任何 index；需要这类 oid/路径时改用新式。
- **Alternatives considered:** 只给 clap 字段 `num_args = 1..=3`：会把新式之后的位置路径吞进 `--cacheinfo`，`--cacheinfo m,o,p file` 不再暂存 `file`。保留 `--cacheinfo=`：Git 拒绝，且未见任何 Libra 使用。要求 `--add`：会打破 Libra 文档示例（`docs/commands/update-index.md:109`、`docs/commands/write-tree.md:67`）与既有用例。
- **Consequences:** 单独出现的非法新式值由 128 改为 129（探针 #8），既有用例 `invalid_cacheinfo_object_id_is_an_error` 由 UX-01 删除并由门族替代。旧式三令牌形式与 mode 规范化、`--verbose` 报告是三个可独立恢复的行为，分属 UX-01、UX-06、UX-07（G-01）。
- **Revisit when:** 漫游器改为完整的 Git 式选项解析器时。

### ADR-UX-03：mode 按 Git `create_ce_mode` 规范化

- **Status:** Accepted
- **Context:** `create_ce_mode`（`object.h:134-144`）：类型位为链接 → `120000`；恰为 `040000` → 稀疏目录；目录或 gitlink 类型 → `160000`；其余（含无类型位、FIFO 等）→ 属主执行位置位为 `100755`，否则 `100644`。探针 #5 逐项确认。
- **Decision:**（由 UX-06 交付）新增私有函数 `canonical_cacheinfo_mode(m: u32) -> Result<u32, String>`，替换 UX-01 留下的四值白名单，对新旧两式都生效：`m & 0o170000` 为 `0o120000` → `0o120000`；为 `0o160000` → `0o160000`；为 `0o040000` → C 型拒绝（ADR-UX-02 的有意差异）；其余 → `m & 0o100 != 0` 时 `0o100755`，否则 `0o100644`。只用于 `--cacheinfo`；`--index-info` 的白名单不变（DEFER-UX-07）。
- **Alternatives considered:** 维持四值白名单：TC-2076 失败。
- **Consequences:** 既有用例 `invalid_cacheinfo_mode_is_an_error`（断言 `100600` 被拒）与 UX-01 的过渡门 `ux01_mode_outside_whitelist__*` 由 UX-06 删除并由其门族替代。
- **Revisit when:** `--index-info` 对齐时，两处改为共用该函数。

### ADR-UX-04：保存前拒绝全零对象 id

- **Status:** Accepted
- **Context:** Git 在写 index 时对每个全零 oid 条目报 `cache entry has null sha1: <name>`，最终 `fatal: Unable to write new index file`，退出 128，不改 index（`read-cache.c:2915-2926`，探针 #14、#15）；`--verbose` 行已在写入前输出。Libra 无此检查。`CliError` 只能输出一行主消息，Git 的多行 `error:` 无法逐行复刻。
- **Decision:**
  - 在 `execute_safe` 的 `index.save` 之前，按 index 顺序检查 0–3 全部阶段的条目；对象 id 的每一位都是 `0`（按当前 hash 长度）即为全零。
  - 存在全零条目时返回 Z 型拒绝（GC-UX-05）：`CliError::fatal(msg).with_stable_code(StableErrorCode::CliInvalidTarget).with_exit_code(128).with_hint(<恢复提示>)`。
    - 消息 `msg` 为 `Unable to write new index file: cache entry has null sha1: <路径 1>, <路径 2>, …`：按 index 顺序列出**全部**含全零 oid 的路径（同名多阶段只列一次），以 `, ` 分隔。只用一条主消息与一条提示，因为 `CliError::with_hint` 最多保留两条、第三条起静默丢弃（`src/utils/error.rs:964-984`），按条目逐条写提示无法保证完整；消息长度与全零条目数成正比，与 Git 每个条目一行 `error:` 的输出量同阶，而列全路径是一次调用完成恢复的前提（见下条）。
    - 恢复提示：未给 `--index-file` 时为 `remove them in one call: libra update-index --force-remove -- <path>...`；给了 `--index-file=<f>`（或 `--index-file <f>`）时为 `remove them in one call: libra update-index --index-file=<f> --force-remove -- <path>...`，`<f>` 取自 argv；整个 `--index-file=<f>` 令牌按 POSIX shell 规则输出：只含 `[A-Za-z0-9_@%+=:,./-]` 时原样，否则用单引号包住、内部的 `'` 写作 `'\''`（例如 `'--index-file=scratch copy.idx'`），保证复制执行时作用于被检查的那个 index。`--` 之后的参数一律按路径处理（漫游器的 `--` 分支，`update_index.rs:393-401`），因此以 `-` 开头的路径（例如名为 `--skip-worktree` 的条目）不会被当作选项；`<path>...` 是占位符，由用户换成消息中列出的路径（`update-index` 的位置路径按字面解析，不做 pathspec 匹配），含空格或 shell 特殊字符的路径需按同样的规则加引号。整份 index 的检查意味着必须在**同一次**调用里移除全部全零条目（只删一部分时，剩余条目仍使保存失败），因此提示写 `<path>...`，消息列出全部路径。
  - 检查覆盖本次调用之前已存在的全零条目（与 Git 一致）。`--index-file` 指定的临时 index 同样适用。
  - 不支持 `GIT_ALLOW_NULL_SHA1`（DEFER-UX-09）。
- **Alternatives considered:** 只检查本次写入的条目：Git 检查全部条目，且旧版 Libra 写出的全零条目会继续留在 index 中。在 `--cacheinfo` 解析时就拒绝：`--verbose` 不会先输出 `add '<path>'`，TC-3169 的 stdout 断言失败，且漏掉 `--index-info`。
- **Consequences:** 有意差异：Git 在 index 未变化时不写盘，因此在已含全零条目的 index 上执行无操作的调用（如只有 `--refresh` 且无变化）会退出 0；Libra 每次都保存，因此也会拒绝。恢复路径是在一次调用中对全部全零路径执行 `--force-remove`（UX-02 的成功门覆盖默认 index、两个全零条目与 `--index-file`）。
- **Revisit when:** `update-index` 改为只在 index 变化时保存。

### ADR-UX-05：`--assume-unchanged` 继续显式不支持

- **Status:** Accepted
- **Context:**
  - Git 的 `CE_VALID` 让 `status`、`diff`、`diff-files`、`add -u`、`commit -a`、`grep` 工作树搜索与 `refresh` 都把条目视为未修改；Libra 这些命令各自比较工作树（`status.rs`、`diff/compare.rs`、`add.rs`、`refresh.rs`、`ls_files.rs`、`grep.rs`），没有共享的「是否视为已修改」入口。
  - issues/637 之前的 Libra 在**每个**新条目上写 `CE_VALID`；现行实现把它当作遗留位忽略，并由 `--refresh` 清除（`docs/commands/update-index.md:158-178`；`src/utils/index_ext.rs:110-127`）。一旦让 Libra 尊重该位，这类旧 index 中的全部修改都会被隐藏，`commit -a` 漏提交，`switch`/`checkout` 的覆盖保护失效。
  - `grep.rs` 由 issues/535 锁定到 GP-10 `done`（535 DEP-GP-03）。
- **Decision:** 本计划不公开 `--assume-unchanged`/`--no-assume-unchanged`（继续 129）。UX-04 把 EN/zh-CN/网站文档与 `COMPATIBILITY.md:242` 的延后说明改写为：不支持、原因（遗留 `CE_VALID` 位与跨命令语义）、承接位置 DEFER-UX-01。
- **Alternatives considered:** 只设置与清除位、不在任何命令中生效：选项看似可用、实际无效，且 `--refresh` 会把位清掉；TC-1593 仍失败。完整实现：需要先给遗留位一个可判别的迁移方案，再改六个以上命令，并与 535 串行，超出 #540 范围。
- **Consequences:** TC-1590、TC-1593 保持 FAIL；#540 保持 OPEN；535 的 GP-11 按 DEP-UX-03 记为受阻。
- **Revisit when:** 另立计划，先交付遗留 `CE_VALID` 位的判别与迁移，再实现生效语义。

### ADR-UX-06：`--again` 的语义

- **Status:** Accepted
- **Context:** Git `do_reupdate`（`builtin/update-index.c:666-724`）与 `reupdate_callback`（`:894-910`），探针 #16。
- **Decision:**
  - **形式：** 只提供长名 `--again`；短名 `-g` 延后（DEFER-UX-03：漫游器不展开短选项簇，`-qg` 这类簇会被误当作路径）。clap 字段为 `again: Option<Vec<String>>`，`num_args = 0..`、`allow_hyphen_values = true`，只做表面校验。
  - **参数：** 漫游器遇到 `--again` 时，把其后全部令牌（含 `--`、以 `-` 开头的令牌）作为 pathspec 并结束漫游；`--again` 之前的操作按原顺序先执行。令牌以 `--again=` 开头时（clap 的值型字段会接受这种写法），漫游器在选择 index 之前返回 U 型拒绝 ``option `again' takes no value``（与 Git 的 `PARSE_OPT_NOARG` 一致，探针 #30），不得把它当作路径。
  - **pathspec：** 经 `PathspecSet::from_workdir(<令牌>, <当前目录>, <工作树根>)` 解析；无令牌且当前目录不是工作树根时，以 `["."]`（相对当前目录）解析，即 Git 的 `PATHSPEC_PREFER_CWD`；无令牌且在根目录时不过滤。任一令牌为空串时，在解析与匹配之前返回 UF 型拒绝 `empty string is not a valid pathspec. please use . instead if you meant to match all paths`（`LBR-CLI-003`，128，无提示；Git `pathspec.c:639-641` 同文，探针 #30）——否则 Libra 的 `PathspecSet` 会把空串解析为当前目录、匹配全部条目。解析失败为 P 型拒绝：`UnsupportedMagic`/`InvalidPattern` 用 `LBR-CLI-002`，提示 `use supported magic: top, exclude, icase, literal, glob`；`OutsideRepository` 用 `LBR-CLI-003`，提示 `all pathspecs must stay within the repository working tree`；消息为 `PathspecError` 的显示文本，退出码一律 128（Git 为 128）。
  - **HEAD：** `Head::current_commit_result()`：`Ok(None)`（未出生）→ 全部候选；`Ok(Some(c))` → `load_commit_with_storage(<本地存储>, c)` 取得根树 id，之后对每个候选路径按路径分量从根树逐级查找 `(mode, oid)`，已读取的树按 id 缓存在本次调用内；只读取候选路径经过的树，pathspec 之外的子树不读取（Git `read_one_ent` 也是逐路径查找）。读取用 `ClientStorage::try_init_local(path::objects())` 构造的本地存储，配合既有的 `load_commit_with_storage`/`load_tree_with_storage`（`src/utils/object_ext.rs:96-125`；该存储忽略云配置，不改进程级读取策略，因此也无需恢复）：`--again` 对 `HEAD` 提交与树的**读取**只用本地对象库，不访问分层存储的远端；`HEAD` 对象只在远端时按下文 R 类拒绝（有意差异：`status`、`restore` 在 `Auto` 策略下会回源）。这一保证只覆盖 `HEAD` 读取：候选的重新暂存仍走 `process_one_path` 的既有路径——`blob.try_save()` 经已配置的存储写对象（分层存储时 `TieredStorage::put` 会写远端，`src/utils/storage/tiered.rs:278`），`ClientStorage::put` 记录对象索引（`src/utils/client_storage.rs:2550`）——与位置路径暂存完全相同，本计划不改。实际运行中，操作中间件在命令执行前已把工作树中变化的文件内容写入本地对象库（`src/internal/operation/snapshot.rs:609`），因此候选的 `blob.try_save()` 通常在本地命中、只补对象索引（`src/utils/object_ext.rs:308`、`src/utils/storage/tiered.rs:592`），位置路径同样如此。为了在测试中走到「对象缺失 → `put` 持久化」与「持久化失败」两条路径，UX-04 在 `stage_working_tree_path` 加两个 debug 构建、`LIBRA_TEST=1` 时才生效的故障注入点（写法同 `src/command/tag.rs:889-902`）：`LIBRA_TEST_UPDATE_INDEX_EVICT_BLOB=1` 在 `try_save` 之前删除该 blob 的本地松散对象文件（使保存走 `exist_checked == false` 的 `put` 分支），并在 `try_save` 返回 `Ok` 之后、保存 index 与命令后快照之前，用已配置的存储（`util::objects_storage()?.exist_checked`）复核该对象，存在时向 stderr 输出一行 `update-index test: persisted <oid>`，不存在时以 `failed to store object for '<path>': LIBRA_TEST_UPDATE_INDEX_EVICT_BLOB found <oid> missing after save`（`LBR-IO-002`）失败——命令后快照（`src/internal/operation/middleware.rs:685`）会重新写出缺失的 blob，所以只能在它之前观测；`put` 在同一调用内登记对象索引（`src/utils/client_storage.rs:2550-2560`），`Ok` 即包含该登记；`LIBRA_TEST_UPDATE_INDEX_FAIL_PERSIST=1` 以 `failed to store object for '<path>': LIBRA_TEST_UPDATE_INDEX_FAIL_PERSIST failpoint`（`LBR-IO-002`，128）代替 `try_save`。位置路径与 `--again` 共用这一函数，故障注入对两者等同。`Err(e)` → S 型拒绝 `failed to resolve HEAD: <e>`（`LBR-REPO-002`，128）；提交读取失败 → H 型拒绝 `unable to read HEAD commit <提交 id>`；根树或候选路径经过的任一子树读取失败（缺失、损坏）→ H 型拒绝 `unable to read the tree of HEAD commit <提交 id>`（提交读取失败时没有树 id 可报；为与之统一，树失败也只带提交 id，底层错误经 `tracing` 记录）。两者均为 `LBR-REPO-002`、128，提示 `the HEAD objects must be in the local object store; run 'libra fsck' to inspect it`。有意差异：Git 在对象缺失时把条目当作「与 HEAD 不同」继续，Libra fail-closed。
  - **候选：** 在执行 `--again` 那一刻的 index 中，按 index 顺序取 stage-0 条目（只看条目自身的阶段，与 Git `builtin/update-index.c:693` 相同：同名另有 1–3 阶段时，stage-0 条目照常参与；只有 1–3 阶段、没有 stage 0 的路径不是候选），匹配 pathspec，且 `HEAD` 中无同名条目、或 mode 不同、或 oid 不同。先固定候选名单，再逐个处理。
  - **处理：** 每个候选调用 `process_one_path`，flag 状态为 `--again` 所在位置的漫游器状态，并做两处调整：`chmod` 置空（Git 的 `do_reupdate` 只调 `update_one`，不调 `chmod_path`）；`add` 置为真。后者只影响 `--remove` 的分流：候选都已在 index 中，`add` 本身不改变任何候选的结果，但使 `--remove` 按 Git 的 `allow_remove` 语义只删除工作树中缺失的条目、重新暂存仍存在的条目（与 Libra 位置路径「单独 `--remove` 一律删除」的既有行为不同，探针 #16 与 t2101 #3）。为此修正 `process_one_path` 中 `--add` 与 `--remove` 同在时的存在性判断（`update_index.rs:581`，现为 `symlink_metadata().is_ok()`，任何错误都当作「缺失」）：`Ok` 为存在；`NotFound`/`NotADirectory` 为缺失；其它错误（权限、I/O、过深的链接等）为 S 型拒绝 `cannot stat '<path>': <错误>`（`LBR-IO-001`，128），不删除条目（Git `process_lstat_error` 同样只把 `ENOENT`/`ENOTDIR` 当作缺失，`builtin/update-index.c:269`）。这一修正同时作用于位置路径的 `--add --remove`，属同一 `update_one` 语义。`--force-remove`、`--skip-worktree`/`--no-skip-worktree`、`--info-only`、`--verbose` 照常生效。
  - **失败：** 任一候选失败即返回错误、不保存 index（GC-UX-02）——包括此前已在内存中成功处理的候选与 `--again` 之前的 argv 操作；工作树文件缺失且未给 `--remove` 时沿用位置路径既有的 `fatal: cannot stage '<path>': <OS 错误>`（S 型，`LBR-CLI-003`，128）。
  - **输出：** `--json` 的 `updated`/`removed` 计入 `--again` 处理的条目。
  - **错误渲染与输出模式一致：** clap 把 `--again` 之后的 `--json`、`--machine` 等当作 `--again` 的值，成功路径因此不进入机器输出；但任何失败（包括 `execute_safe` 之前 `command_preflight` 的「不在仓库中」，`src/cli.rs:1665`）都由 `main.rs:691-704` 用 `OutputConfig::resolve_from_argv`（`src/utils/output.rs:250`）重扫原始 argv 决定渲染模式，会把这些字面 pathspec 当作输出旗标。为此修改共享的 `resolve_from_argv`：扫描中遇到子命令令牌 `update-index` 之后，按 clap 对 `update-index` 参数的归属处理——令牌 `--cacheinfo` 之后的下一个令牌是它的值（ADR-UX-02 的 `num_args = 0..=1`、`allow_hyphen_values`），直接跳过、不当作旗标；遇到令牌 `--again` 或以 `--again=` 开头的令牌即停止扫描（其后的令牌都是 `--again` 的值）；同时更正该扫描器对裸 `--color` 的既有处理（`src/utils/output.rs:303-307` 把下一个令牌当作颜色值吞掉，与根 clap 的 `require_equals` 不一致，会吞掉子命令名）：裸 `--color` 即 `always`，只有 `--color=<v>` 带值；`--again` 之前（含 `update-index` 之前）的全局旗标照常生效。错误对象本身不变（不替换为 `silent_exit`，保留稳定码、消息与提示，库调用方 `exec_async` 拿到的仍是原错误），渲染仍在应用边界进行。该函数是 GC-02 意义上的共享 helper（T-1），与 issues/536 RS-07 在同一文件串行（DEP-UX-02）。门：`ux04_trailing_machine_is_literal`、`ux04_trailing_json_is_literal`（仓库内 pathspec 失败）、`ux04_outside_repo_trailing_machine_human`（仓库外 preflight 失败）、对照 `ux04_outside_repo_global_machine_control`、`ux04_cacheinfo_operand_again_machine`（`--again` 作为 `--cacheinfo` 的值时不截断扫描）；单元门 `ux04_unit_output_stops_at_again`、`ux04_unit_output_global_before_again`、`ux04_unit_output_skips_cacheinfo_operand`；成功路径 `ux04_trailing_machine_success_stdout_empty`。`update-index -- --machine` 之类 `--` 之后的旗标在错误路径仍被当作输出旗标，这是所有命令共有的既有行为（issues/536 DEFER-RS-07 同类），本计划不改。
- **Alternatives considered:** 只比较 oid、不比较 mode：漏掉 mode 变化（Git 两者都比）。按 Git 在对象缺失时继续：会把无法读取的 HEAD 当作「全部不同」而大量重新暂存，违反 GC-07。沿用位置路径的 `--remove` 语义：t2101 #3（TC-3167）会把仍存在的 `file2` 也删掉。
- **Consequences:** skip-worktree 条目的 `--verbose` 输出沿用位置路径的既有差异（DEFER-UX-08）。
- **Revisit when:** 漫游器支持短选项簇时补 `-g`。

### ADR-UX-07：重新暂存清除 intent-to-add

- **Status:** Accepted
- **Context:** Git 的 `add_one_path` 构造新条目，intent-to-add 位不继承（探针 #22）。Libra 位置路径经 `update_preserving_file_mode`（`FlagPreservation::All`）写入；`add` 已改用清除 intent-to-add 的 `update_preserving_file_mode_except_intent`（issues/490 ADR-SW-03 的「写入真实内容即清除」规则，`src/utils/index_ext.rs:55-70`）。
- **Decision:** `process_one_path` 的工作树暂存分支（`update_index.rs:600`）改用 `update_preserving_file_mode_except_intent`。skip-worktree 位与 `core.fileMode=false` 的 mode 规则不变。覆盖位置路径、`--stdin`，以及之后的 `--again`。
- **Alternatives considered:** 只在 `--again` 内清除：同一 `update_one` 语义出现两种结果。
- **Consequences:** `update-index <intent-to-add 路径>` 之后 `status` 由 ` A` 变为 `A `，与 Git 一致。`--cacheinfo` 的扩展位语义不变（DEFER-UX-04）。
- **Revisit when:** DEFER-UX-04 承接时，`--cacheinfo` 改为与 `--index-info` 相同的新条目语义。

  ```bash
  zero_hits() {
    pattern="$1"; shift
    if rg -n -- "$pattern" "$@"; then
      echo "FAIL: forbidden pattern found"; return 1
    else
      rc=$?
      if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; return "$rc"; fi
      echo "OK: zero hits"
    fi
  }
  ```

- **GC-UX-05 拒绝门族：** 本计划每条新增或新可达的失败路径都按下表展开成一组门。每个门是一个独立命名的测试函数，只断言一个谓词，计入所在卡的 G-03 分子（由 EX-UX-01 承载超限）。测试函数由 UX-01 在 `tests/command/update_index_test.rs` 新增的宏 `ux_refusal_gates!` 生成（模块内 `macro_rules!`，不导出；UX-02、UX-04 复用），命名为 `<拒绝 ID>__<后缀>`，完整路径 `command::update_index_test::<名>`（`tests/command_test.rs` 以 `command` 模块挂载 `tests/command/mod.rs`）。单门执行一律用 `source .env.test && cargo nextest run --config-file "$NEXTEST_NOJUNIT_CFG" --test command_test --no-tests=fail -E 'test(=command::update_index_test::<名>)'`（零匹配即失败；不用 `cargo test … -- --exact`，后者名字不全时匹配 0 个用例仍退出 0）。三种输出模式的通道见探针 #26。每个门在新建的夹具中执行一次被测 argv（`__json` 与 `__machine_*` 另建夹具重跑，argv 前加全局 `--json`/`--machine`）。
  - **后缀定义：**
    - `__msg`：stderr 第 1 行等于 `<前缀>: <消息>`（S 型的 N 类为「以卡内该行给出的前缀开头」，前缀取自拒绝表的「消息」列，如 `fatal: cannot stage 'file1': ` 或 `fatal: cannot stat 'zdir/f': `；宏按行参数化，不写死前缀）；
    - `__code`：stderr 第 2 行等于 `Error-Code: <码>`；
    - `__exit`：退出码等于卡内给出的值；
    - `__stdout`：stdout 为 0 字节；
    - `__index`：执行前后 `.libra/index` 的存在性与 SHA-256 相同；
    - `__alt_index`：argv 中 `--index-file=<f>` 指定的文件执行前后的存在性与 SHA-256 相同（夹具在卡内写明执行前该文件「不存在」或「存在」）；
    - `__hint`：stderr 中以 `Hint: ` 开头的行组成的有序列表等于卡内给出的提示列表（每条加 `Hint: ` 前缀）；
    - `__json`：以 `libra --json <argv>` 重跑，stderr 解析出的对象等于卡内给出的期望对象；
    - `__machine_lines`：以 `libra --machine <argv>` 重跑，stderr 恰为一行；
    - `__machine_json`：同一次 `--machine` 运行，该行解析出的对象等于 `__json` 的期望对象。
  - **U 型**（用法拒绝）：构造 `CliError::command_usage(msg)`（默认 `LBR-CLI-002`，不覆盖退出码）。8 个门：`__msg`（`error: <msg>`）、`__code`（`LBR-CLI-002`）、`__exit`（129）、`__stdout`、`__index`、`__json`、`__machine_lines`、`__machine_json`；期望对象 `{"ok":false,"error_code":"LBR-CLI-002","category":"cli","exit_code":129,"severity":"error","message":<msg>}`。
  - **H 型**（带提示的 `fatal`，含 C、Z、P、R 四类）：构造 `CliError::fatal(msg).with_stable_code(<码>).with_exit_code(128)` 加卡内给出的提示。9 个门：`__msg`（`fatal: <msg>`）、`__code`、`__exit`（128）、`__stdout`、`__index`、`__hint`、`__json`、`__machine_lines`、`__machine_json`；期望对象 `{"ok":false,"error_code":<码>,"category":<类>,"exit_code":128,"severity":"fatal","message":<msg>,"hints":[<提示…>]}`，其中 `LBR-CLI-002`/`LBR-CLI-003` 的类为 `cli`，`LBR-REPO-002` 的类为 `repo`。
    - C 类：`--cacheinfo` 令牌或条目失败，码 `LBR-CLI-002`（ADR-UX-02）；
    - Z 类：全零 oid，码 `LBR-CLI-003`（ADR-UX-04）；
    - P 类：`--again` 的 pathspec 解析失败，码按 ADR-UX-06；
    - R 类：`--again` 读取 `HEAD` 的提交或树失败，码 `LBR-REPO-002`。
  - **UF 型**（不带提示的 `fatal`）：构造 `CliError::fatal(msg).with_stable_code(<码>).with_exit_code(128)`。8 个门，后缀与 U 型相同（`__msg` 为 `fatal: <msg>`，`__exit` 为 128）；期望对象 `{"ok":false,"error_code":<码>,"category":"cli","exit_code":128,"severity":"fatal","message":<msg>}`。门集合用 `gates_u`。
  - **UA 型 / HA 型**：argv 含 `--index-file=<f>` 的 U 型 / H 型拒绝，在对应门族上再加 `__alt_index`，分别为 9 / 10 个门。
  - **S 型**（短门族）：5 个门：`__msg`、`__code`、`__exit`（128）、`__stdout`、`__index`。用于两类：F 类为经故障注入的 `HEAD` 解析失败（消息含注入标记，证明注入点被触达；不比较 JSON，因为它与 R 类经同一渲染）；N 类为新可达的工作树读取拒绝——既有的 `cannot stage` 与 UX-04 新增的 `cannot stat`（消息含操作系统错误文本，只比较前缀）。
  - **门集合核对（shell 门）：** 每张含门族的卡另有一个「门集合相等」门。它是 shell 门，不是 Rust 测试：在仓库根目录新开 `bash -euo pipefail` 进程，先定义下列函数，再执行卡内给出的 `gate_set …` 调用，退出 0 即通过。期望集合只含测试门，不含门集合门本身；集合为空、列举失败或集合不等都非 0 退出。本门只断言「集合相等」一个谓词，计 1 项。

    gates_h() { for id in "$@"; do for x in msg code exit stdout index hint json machine_lines machine_json; do echo "${id}__${x}"; done; done; }

### 任务卡粒度规则（强制）

本计划完整采用模板 G-01..G-11。每张实现卡只有一个行为轴与一个恢复动作；实现、测试、文档、兼容矩阵在同卡交付。AC 按独立可失败谓词计数：同一命令的「输出序列相等」视为一个谓词；GC-UX-05 的每个门各计一项。含拒绝门族的卡由 EX-UX-01 承载超限，其门族在卡内「判据规范（非计数正文）」块逐门枚举。ER-04 强制门与 ER-06/ER-06a 同卡文档门（含 GC-UX-06）不计入 G-03。

#### 字段全局默认与例外

- **Release boundary 默认：** `independent`（完整 C 组，含 `patch + 1` 与 `gh` 发布）
- **Task type 默认：** `implementation`
- **Estimated scope 默认：** `M`（每张实现卡都有一处公开行为或接口变化）
- **Rollback mode 默认：** `immutable-release`。
  - 发布前：以单一 revert 回退本卡提交。
  - 发布后：只能以新的 `patch + 1` 前滚修复。
  - 降级指引：可用 `install.sh -v v<上一版本>`（`install.sh:265` 的 `-v`/`--version`，或 `:243`、`:258` 的 `LIBRA_VERSION`）或 `install.ps1` 重装上一版本。
  - 兼容窗口：本计划只改变 `update-index` 的参数解析、输出与写入前检查，不改变 index 或对象的存储格式；新旧二进制可在同一仓库互换使用（旧二进制仍会接受全零 oid 与旧 mode 白名单，不会读坏新二进制写出的 index）。
- **Migration and rollback 默认：** `N/A`（无 schema 或数据迁移）
- **Security and privacy 默认：** 继承 GC-07、GC-11
- **Performance budget 默认：** 继承 GC-10
- **Version increment 默认：** `patch`
- **C/D coverage from 默认：** `self`
- **Release write set 默认：** `Inherited`，即 `compat_version_surface_sync` 报告的版本面集合（`Cargo.toml`、`install.sh`、`install.ps1`），加工具链刷新的 `Cargo.lock` 与 release artifact。

### Task UX-01：`--cacheinfo` 的旧式三参数形式与参数语法

**Task type:** `implementation`

**Lifecycle / Acceptance:** `pending` / 空

**Description:** 按 ADR-UX-02 让 `--cacheinfo` 的参数语法与 Git 一致：接受旧式三参数形式，按 Git 规则在新旧两式间选择；参数不足、`--cacheinfo=` 与以 `-` 开头的旧式操作数为用法错误；令牌或条目失败为 `fatal: git update-index: --cacheinfo cannot add <令牌>`。mode 仍用既有四值白名单（规范化由 UX-06 承接）。为此把漫游器提取为可单元测试的纯函数，并让漫游在选择与加载 index 之前完成。本卡同时新增 GC-UX-05 的 `ux_refusal_gates!` 宏、夹具 `F-BASE` 与 index 快照 helper，供后续各卡复用，并删除一条与新合同相反的旧用例。唯一行为轴是 `--cacheinfo` 的参数消费与解析诊断。（R1 后拆出 UX-06、UX-07。）

**Out of scope:**
- mode 规范化：由 UX-06 承接。
- `--verbose` 对 `--cacheinfo` 条目的报告：由 UX-07 承接。
- 全零 oid 的拒绝：由 UX-02 承接（本卡之后 `--cacheinfo 100644 $ZERO file` 仍会被保存）。
- `--cacheinfo` 写入的扩展位与高阶段语义：DEFER-UX-04；`--index-info` 的 mode 白名单：DEFER-UX-07；路径校验与 Git `verify_path` 的差异：DEFER-UX-06。
