## 文档职责

### 适用范围

让 `fsck --progress` / `--no-progress` 按 Git 的布尔形式工作：研究沿用 `src/cli.rs` 的参数改写机制，并让 fsck 的进度输出服从明确的偏好。Issue 要求覆盖 TC-3074（t5319 #46）与 TC-3075（#47）；按用户选择 B，Libra 轨只适配测试对象目录，Git 原始控制不变。multi-pack-index 校验和前序测试的真实产物仍须形成可执行承接卡，旧的延后条目不是 Issue 范围裁定。

### 非目标

不改变全局 progress MODE 对其它命令的意义。既有对象目录进度保持 stdout 是当前候选方案；TC-3074 要求的 MIDX 验证进度在 stderr，须单独设计并验收。

### 成功定义

`fsck --no-progress` 不再被 clap 拒绝并抑制适用进度行，`fsck --progress <oid>` 不把对象 ID 当 MODE，最后一个布尔 flag 生效；固定 Git 的原始 TC-3074/3075 控制与按 ADR-I1046-02 适配对象目录的 Libra 轨均在最终树 PASS。前序 MIDX 产物、校验与隔离证据须在完整计划中可执行地承接；适配轨不得报告为未修改的 Libra 轨。

## 已决议设计决策

### ADR-I1046-01: fsck 复用 index-pack 的布尔改写

- **Status:** 待重审；Claude R4 发现 progress 偏好、参数作用域及验证计数不一致。以下为修订草案，须补齐测试和完整 Issue 承接。
- **Context:** 全局 `--progress` 需要 MODE，Git 的 fsck 形式是布尔。`src/cli.rs` 已为 index-pack 实现「裸 flag 改写成全局 MODE」的机制并有单测；在 `FsckArgs` 里再加同名 `progress` 字段会与全局 arg 的 id 与类型冲突（clap 按 id 把全局值复制进子命令，`clap_builder` 的 `arg_matcher.rs:53-91`）。
- **Decision（草案）:** 参数改写须区分子命令：仅 fsck 的多个裸 `--progress` / `--no-progress` 按最后一个生效；index-pack 维持现有逐个改写，重复值仍由 clap 拒绝。`FsckArgs` 不添加同名全局参数 ID；`fsck --progress <oid>` 的对象 ID 必须保留为位置参数。是否抑制 `fsck.rs:1528-1545` 的进度须看用户显式的 `OutputConfig.progress_preference`，不能只看 `output.progress`：非 TTY 的 `auto` 可能解析成 `None`（`src/utils/output.rs:204-232`）。参数传递、`--verbose`、同层与跨层重复选项，以及 `--` 之后不改写，均须以具名测试和文档锁定。根级 MODE 与子命令级选项并存时不能一律宣称报错；R4 核对到子命令级值会覆盖根级值，同层重复才报 129。
- **传递与 verbose（候选，待测试及重审）：** 不新增进程级可变开关。`execute_safe` 将 `output.progress_preference` 逐调用传入 `run_fsck`，再经 `check_all_objects` 传给 `check_directories`；旧 `execute` 入口传 `ProgressPreference::Auto` 保持默认行为（调用路径分别见 `fsck.rs:774-790,859-862,1043-1048,1199,1229,1496`）。显式 `None` 只抑制进度行 `Checking object directories: ...` 与 `Checking objects: ...`，不抑制 `--verbose` 的 `Checking object directory` 诊断或错误；原 JSON 的 stdout 抑制合同仍适用。`Auto` 维持 Libra 的现有默认输出，不能因非 TTY 下解析出的 `ProgressMode::None` 静默消失。MIDX 进度输出在后续 MIDX 承接内另按 stderr 与 `--verbose` 验收，不得把这里的 stdout 差异写成 Git 行为。2026-11-07 在隔离临时 Git 仓库实测 `--verbose --no-progress` 和 `--verbose --progress` 都保留 verbose 的 `Checking object directory`，无 verbose 的 `--no-progress` 无该行；测试只支持这几个输入，完整语义仍须与固定 Git 控制构建对照。
- **待补验证：** 同一提交树上分别断言非 TTY 默认、`--no-progress`、`--progress`、`--verbose --no-progress`、JSON/machine 与直接 `execute` 的行为；另外单独验证根级与子命令级覆盖、同层冲突、`--` 之后参数、OID 未被吞掉，以及 index-pack 重复 flag 维持原来的 129。每个独立验收谓词和测试门按 G-03 如实计数；这些新增门不能挤进旧卡的八条清单而假装仍为 `8/8`，须先按行为轴重新拆分或取得模板规定的具名 waiver。
- **Alternatives considered:** 给 `FsckArgs` 加两个 bool（与全局 `progress` 的 id 冲突，或要另起长名，不再是 Git 的形式）；给 fsck 增加 `--progress <MODE>`（TC 不会传 MODE）。
- **Consequences:** 进度行仍在 stdout（Git 在 stderr），文档登记为差异；index-pack 保持逐个改写、不去重（`index-pack --progress --no-progress` 仍退出 129），由现有单测与一条覆盖重复 flag 的新单测守护；`fsck --progress <MODE>` 的分离值写法不再可用，登记为破坏性差异。
- **Revisit when:** fsck 实现 multi-pack-index 校验（DEFER-I1046-MIDX）或进度改到 stderr。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1046-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

第三段，CI 通过后发布。脚本先从状态文件取回第二段记录的两个 run，重新向 GitHub 查询它们的结论、head SHA、分支与事件，必须是 success、本卡 SHA、候选分支、push，并逐个核对 run 内每个 job 都是 success（`base.yml` 的 8 个 job 在 `release/**` 上都没有跳过条件），所以漏跑或错序执行第二段时不会建 tag。本段开头先以 `WHEN=stage3` 执行外部前置检查（从本文件抽出原样运行），第一段开头同样以 `WHEN=stage1` 执行，所以这两次检查不靠执行者记得。随后确认本卡 SHA 仍在远端 `main` 上。本段可原样重跑：远端已有 `v$VERSION` 时，只有它指向本卡 SHA 且对应 Release 存在，才视为上一次第三段已成功（例如 `gh release create` 在服务端成功后客户端报错，或建 tag 后、写状态文件前中断），补记 `TAG` 后结束；tag 指向别的提交，或只有 tag 没有 Release，都停止报告，不改写 tag。远端还没有该 tag 时，候选分支必须仍指向本卡 SHA，前一个 patch 版本 `v<VERSION 的 patch − 1>` 必须已有 tag 且它的 `release.yml` run 都已结束（tag 已建而 release 仍在上传时 CDN 还是更旧的版本，两个发布会互相干扰；本族只做 patch + 1，修复模式沿用同一版本，所以前一版本就是 bump 前的基线；它没有 tag 说明有更早的发布未完成，`refuse_older_cdn` 会让两个发布互相干扰），另有两项检查与 `.github/workflows/release.yml:351-386` 的 `refuse_older_cdn` 对应：远端不存在版本号大于 `v$VERSION` 的 `vX.Y.Z` tag；`https://download.libra.tools/install.sh` 与 `install.ps1` 返回 200、能取出版本，且版本都小于 `v$VERSION`。等待 CI 的几个小时里其它计划可能已发布更高版本，此时 `gh release create` 会留下孤立 tag，而 `upload-install-scripts` 会拒绝上传。任一项不满足就停止，不建 tag：版本被抢先时按修复模式之外的正常路径，在新基线上以新的 C 组提交前滚（本卡版本号作废，记入「实施证据」）。`gh release create` 报错时先按同样规则复核远端，确认已发布才继续。

1. 扫描 `docs/development/plan` 下全部计划（本文件、`plan-status.md`、`plan-template.md` 除外），按 `##`、`###`、`####` 三级的 `Task ` 标题切卡。任何处于 `in-progress` 或 `blocked` 的卡，只要 Implementation write set 命中本计划写集，或根本没有 Implementation write set 字段，或该字段为空，就是活动写者。写集取从 `**Implementation write set:**` 起、到下一个加粗字段或标题之前的整段，换行后的列表也算在内；写集文字提到 Deliverables（例如「同 Deliverables」）时，同卡 `**Deliverables:**` 字段的内容一并计入；解析后既没有反引号中的路径、也不以 `N/A` 开头的写集，无法证明不相交，同样算活动写者。活动与否按白名单判定，不按黑名单：卡内第一条加粗 `Lifecycle / Acceptance` 字段行的首词（去掉反引号）是 `pending`、`done`、`released`、`deferred`、`废弃`、`取消` 或 `合并回`，且第一个括号之前的 Acceptance 半边不是 `locally-accepted` 或 `remote-pending` 时，该卡不活动；其余一律算活动卡，包括 `in-progress`、`blocked`、写在 Lifecycle 位上的 `locally-accepted`（2026-11-07 的实例：`plan-20260926.md:972`、`plan-20261018-grok-capture.md:486` 等，以及远端 `5ea34fd` 中旧文本的 I1052-00）、`planned`、`done` / `remote-pending`、大小写或连字符不规范的写法（如 `In-Progress`、`in_progress`）、空首词，以及没有可解析字段行的卡。`blocked` 卡只在字段行以两种固定形态之一开头时不算活动：`blocked（superseded：`，或 `` `blocked` / 空（ `` 之后 20 字以内出现「本卡已正式延后」（2026-11-07 符合的是 `plan-20260825.md:643`、`:1003`、`:1094` 与 `plan-20260729.md:7578`）；行内其它位置出现 `superseded` 或「已正式延后」不算。脚本扫描之前先用十条样例行自测这一判定（覆盖上述活动与不活动形态），任一判定与预期不符即非零退出。命中有四种方式：正文匹配本计划写集文件的模式（行号的 `:217` 与「（第 217 行）」两种写法都能匹配）；`COMPATIBILITY.md` 的行号区间（如 `:200-230`、「第 200–230 行」）覆盖本计划登记的行；反引号中的通配写集（如 `src/command/*.rs`，花括号 `{a,b}` 先展开）或目录写集（如 `docs/commands/`）覆盖本计划的任一文件（网站页按 `../libra-backend/`、`/Volumes/Sea/libra-backend/` 两种前缀归一后比较）；写集里出现不带数字行号的 `COMPATIBILITY.md`、且同一写集提到本计划的命令名（`fsck`，按完整命令名匹配）时也算命中；只写文件名或写别的命令行（例如「`COMPATIBILITY.md` 的 fetch 行」）的写集改的是其它命令的行，与本计划登记的行不相交。它若插入或删除行，让本计划登记的行号漂移，开工检查与暂存守卫的行身份检查（行首前缀在全文恰好命中一次且位于登记行号）会失败并停止，按 ER-10 修订行号，所以不需要在开工门里把它当作写者；
2. 自检：卡外的 `Lifecycle / Acceptance` 行（加粗或不加粗）若是 `in-progress` 或 `blocked` 也算失败；卡内第一行之后若还有加粗的活动 `Lifecycle / Acceptance` 字段行，同样失败。这两种情况说明有标题格式不同的卡没被切出来。卡内不加粗的历史日志行（例如 `plan-20260904.md:4665`）不计。
3. issues/1040–1057 的其它计划中，任何一张卡不是 `pending`（Acceptance 半边不是 `locally-accepted` 或 `remote-pending`），也不是 `done` / `complete`，都失败（全串行，`plan-status.md` 第六节 DEP-I1040-1049-REL）；这一项比第 1 项更严，`released`、`deferred`、`blocked` 的豁免形态与无法解析的卡在家族内一律失败。
