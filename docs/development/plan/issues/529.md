## 文档职责

本文处理 Issue #529 在当前 `main` 上仍成立的 `format-patch` 与 Git 契约差异。目标：#529 正文和评论中列出、且仍能复现的每一项，要么对齐 Git，要么显式归类为不支持并写进文档；同时给出 #529 引用的上游用例如何复核。

新建或推进本计划时，必须在同一变更中更新 [`plan-status.md`](../plan-status.md)（状态、版本/提交、`YYYY-MM-DD HH:MM:SS UTC`）。

### 适用范围

- `libra format-patch` 的以下表面：
  - `-N`/`--no-numbered` 下的文件名；
  - `-n`/`-N` 的主题计数；
  - `-k` 与 `-n`/`--rfc`/`--subject-prefix` 的互斥；
  - 主题前缀的组合（空前缀、`--rfc=-<text>` 后置标记、cover letter 的 RFC 标记）；
  - 补丁正文的默认重命名检测，以及 `-M`/`--find-renames`/`--no-renames`；
  - `--numstat`；
  - `--output=<file>`，以及 `--stdout`/`--output`/`-o` 三者互斥；
  - `--no-cover-letter`，以及 `--interdiff`/`--range-diff` 的 cover letter 三态与前置条件诊断；
  - `--from`/`--signoff` 的提交者身份来源。
- 对应文档：`docs/commands/format-patch.md`、`docs/commands/zh-CN/format-patch.md`、由同步脚本生成的网站页 `../libra-backend/apps/tanstack-app/content/docs/commands/format-patch.en.md`、开发文档 `docs/development/commands/format-patch.md`，以及 `COMPATIBILITY.md` 第 224 行 `format-patch` 行（原地改写，不增删行）。
- 2026-10-22 已交付、但文档仍写旧口径的空系列契约，以及 zh-CN 的 `-k`、`-p` 行的文档纠正。
- 测试：`tests/command/format_patch_test.rs`（`command_test` 目标）、`tests/compat/format_patch_flag_surface.rs`、`tests/compat/format_patch_mail_roundtrip_test.rs`。

### 非目标

- 不改默认主题编号策略（Git `format.numbered=auto` 会给多补丁加 `[PATCH n/m]`），也不实现 `format.numbered` 配置：由 [#896](https://github.com/libra-tools/libra/issues/896) 承接（DEP-FP-02）。
- 不实现 `--interdiff`/`--range-diff` 的输出：由 [#898](https://github.com/libra-tools/libra/issues/898) 承接（DEP-FP-04）。本计划只做三态前置条件诊断，加上显式不支持分类（ADR-FP-05）。
- 下列 #880–#917 系列中与 #529 不同轴的问题不在范围内：
  - `-o` 模式文件清单写 stderr、文件名丢失 reroll 前缀（[#901](https://github.com/libra-tools/libra/issues/901)）；
  - [#904](https://github.com/libra-tools/libra/issues/904) 中除重命名三个选项以外的 diff 选项（`-U`、`--diff-filter`、`--full-diff`）；
  - 默认 `Message-ID` 线程化（[#917](https://github.com/libra-tools/libra/issues/917)）；
  - mbox `From ` 魔术日期（[#893](https://github.com/libra-tools/libra/issues/893)）；
  - 总是输出 MIME 头（[#897](https://github.com/libra-tools/libra/issues/897)）；
  - `format.coverLetter`（[#900](https://github.com/libra-tools/libra/issues/900)）；
  - cover letter 的 diffstat（[#905](https://github.com/libra-tools/libra/issues/905)）；
  - `--no-from`/`format.from`（[#915](https://github.com/libra-tools/libra/issues/915)）；
  - 其余同类 issue。
- 不实现全局 `-c <key>=<value>`（[#557](https://github.com/libra-tools/libra/issues/557)）、`diff-tree` 缺口（[#555](https://github.com/libra-tools/libra/issues/555)）、`am` 侧缺口（[#547](https://github.com/libra-tools/libra/issues/547)）。这些缺口挡住了部分 #529 引用的上游用例；本计划只登记依赖（DEP-FP-05），不把这些用例记为通过。
- 不改共享 diff 引擎的 hunk 头（DEFER-FP-01），也不改共享 stat 渲染器的版式（DEFER-FP-02）。
- 不改 `libra commit` 自身的身份解析（DEFER-FP-04）。
- 不改 Libra 全局错误输出合同（`Error-Code:` 行与各稳定码的退出码）。
- 计划完成不以关闭 #529 为条件；#529 的关闭条件见 DEP-FP-07。

### 成功定义

- #529 中仍能复现的各项全部按 Git 处理：
  - `-N` 不再改变文件名；
  - 主题计数的宽度与 Git 一致；
  - `-k` 冲突、空前缀、`--rfc=-<text>` 与 Git 一致；
  - 补丁正文默认检测重命名，`-M`/`--find-renames`/`--no-renames` 可用；
  - `--numstat`、`--output`、`--no-cover-letter` 可用；
  - `--interdiff`/`--range-diff` 先按三态做前置条件诊断，再归类为不支持；
  - 裸 `--from` 与 `--signoff` 按 Git 规则取提交者身份。
- 每项行为有 `command_test` 或 compat 目标中的具名用例。期望字节取自本计划「行为探针」表，或与 `libra diff` 同源渲染逐字节比较。
- EN、zh-CN、网站页、开发文档与 `COMPATIBILITY.md` 第 224 行与实现一致，`--help` 文案同步。
- 十二张实现卡各自完成独立发布切片（ER-08），全部卡 `done` / `complete`，计划收口点 CLOSE-529 全绿。
- FP-12 已把 libra-testcases 维护者公开发布的复跑结果逐行写入本计划。

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改变语义。

### ADR-FP-01：范围以 #529 为准，同轴问题一并修复

- **Status:** Accepted
- **Context:** 2026-11-02 起，同一次测试扫描又拆出 #880–#917 共约 37 个 `format-patch` issue，其中部分与 #529 的缺口落在同一段代码、同一行为轴上。
- **Decision:** 只处理 #529 正文与评论中当前仍能复现的项。与这些项同轴且改同一段代码的三个 issue 在对应卡内一并修复：#880（计数宽度）、#888（`-k` 互斥）、#881（`--signoff` 身份）。其它 issue 不扩入。
- **Alternatives considered:** 一份计划吞下全部 #880–#917：范围失控，且多项依赖尚未实现的全局 `-c`。完全不碰同轴 issue：同一函数会被两份计划先后改写，制造 I–I 冲突。
- **Consequences:** #896、#901、#904、#898 的后续计划须在本计划释放写集后再改 `format_patch.rs`（DEP-FP-01..04）。
- **Revisit when:** 开工时发现某个同轴 issue 已被其它计划认领。

### ADR-FP-02：`-N` 只影响主题，文件名总带 `NNNN-` 前缀

- **Status:** Accepted
- **Context:** 2026-10-22 的实现把 `-N` 理解为去掉文件名前缀，并写进了三份文档。Git 2.54.0 探针 #1 表明：`-N` 下文件名仍是 `0001-3.patch`；Git 文档对 `-N` 的说明是「Name output in [PATCH] format」。t4151 的 6 个用例依赖这种文件名。
- **Decision:**
  - 文件名只由 `--numbered-files`、`--suffix`、`--filename-max-length`、`--start-number` 决定，与 `-n`/`-N` 无关（FP-01）。
  - `-N` 取消全部主题计数，包括 cover letter（FP-02）。
  - 主题计数宽度取显示总数（`start + count - 1`）的十进制位数，不设下限（FP-02）。
  - 默认情况（既无 `-n` 也无 `-N`）保持现状：只在 `--cover-letter` 时计数。默认策略由 #896 处理。
- **Alternatives considered:** 保留 2026-10-22 的语义，并文档化为有意差异：t4151 与依赖 Git 文件名的脚本会持续失败，Libra 侧没有收益。
- **Consequences:** 这是对外行为变化。依赖 `-N` 产出无前缀文件名的调用者需要自行重命名；`--numbered-files` 只产出纯数字文件名，只有调用者接受纯数字时才可替代。文档与 `COMPATIBILITY.md` 同卡写明。
- **Revisit when:** 无。

### ADR-FP-03：补丁正文复用 `libra diff` 的重命名检测，默认值跟随 `diff.renames`

- **Status:** Accepted
- **Context:**
  - Git 的 `format-patch` 默认检测重命名，受 `diff.renames` 控制（探针 #16）；t4150 显式使用 `-M`。
  - `libra diff` 已默认检测重命名，并解析 `diff.renames`。
  - `format-patch` 却走另一条不检测重命名的 `log` 渲染路径。
- **Decision:**
  - **默认检测（FP-05）：** 补丁正文与 diffstat 改由 `libra diff` 的引擎生成：父提交对本提交的 `DiffOutput`，经 `apply_rename_detection`；正文用 `format_unified_diff` 渲染，stat 用 `format_diff_stat_output` 渲染。默认阈值与 `libra diff <parent> <commit>` 相同。
  - **参数（FP-06）：** `-M[<n>]`、`--find-renames[=<n>]`、`--no-renames` 的阈值解析与 `libra diff` 相同（`parse_rename_score`）。不同之处在于：裸 `-M` 不吞下一个参数——Git 用 `PARSE_OPT_OPTARG`，值必须紧贴选项，所以 `-M lorem` 中的 `lorem` 是修订。
  - **保持不变：** `--histogram`、`--full-index`、`--src-prefix`/`--dst-prefix` 继续生效；`--ignore-if-in-upstream` 与 `--base` 的 patch-id 计算路径不改。
- **Alternatives considered:** 在 `log::generate_diff_with_options` 里再写一套重命名检测：违反 GC-02。只接受 `-M`、默认不检测：与 Git 和 `libra diff` 的默认都不一致。
- **Consequences:**
  - 默认输出变化：纯重命名不再输出两段完整内容。`git am` 与 `libra am` 都接受 `rename from/to`（`COMPATIBILITY.md:183`）。
  - stat 改用 `libra diff` 渲染器的版式。该渲染器与 Git 仍有差异（DEFER-FP-02）；本计划以「与 `libra diff --stat` 逐字节相同」为判据，不宣称与 Git 逐字节相同。
  - 需要把 `render` 模块与上述函数的可见性提升为 `pub(crate)`，并在 `compare.rs` 增加一个「提交对父提交」的 `pub(crate)` 入口，属 T-1。
- **Revisit when:** 共享 stat 渲染器另立计划修正时，本计划的判据随之对齐。

### ADR-FP-04：用法冲突用 `fatal` 加 `LBR-CLI-002`

- **Status:** Accepted
- **Context:**
  - Git 对 `-k` 冲突、输出目的地互斥、interdiff 前置条件等，都以 `die()` 输出 `fatal: …` 并退出 128。
  - Libra 的 `command_usage` 输出 `error:` 前缀（`src/utils/error.rs:819-827`、`:1191-1193`），手动加 `fatal:` 会得到 `error: fatal: …`。
  - `libra diff` 的非法重命名阈值已有先例：`CliError::fatal(..).with_stable_code(StableErrorCode::CliInvalidArguments)`，输出 `fatal: …`，退出 129。
- **Decision:** 本计划新增的全部用法冲突与前置条件错误都用 `CliError::fatal(<Git 原文去掉 "fatal: " 前缀>).with_stable_code(StableErrorCode::CliInvalidArguments)`，即 GC-FP-05 的 U 型拒绝。Git 的 128 与 Libra 的 129 之差写入文档错误表。
- **Alternatives considered:** 像 `update-ref` 那样为 `format-patch` 另设 128 例外：扩大错误码合同的例外面，收益只是退出码数值。新增错误种类：属全局错误 API 变化，超出本计划。
- **Consequences:** 上游用例中 `test_must_fail` 成立。用 `test_cmp` 比较整个 stderr 的用例仍会因 `Error-Code:` 行而失败，这是全局合同，不在本计划修。
- **Revisit when:** 全局错误输出合同变化。

### ADR-FP-05：cover letter 三态，`--interdiff`/`--range-diff` 先诊断再拒绝

- **Status:** Accepted
- **Context:** Git 区分三种状态：未指定、显式启用、显式禁用 cover letter。在未指定的情况下，`--interdiff`/`--range-diff` 加多补丁会隐式开启 cover letter（探针 #25）；只有显式禁用时才报前置条件错误（探针 #27、#28）。`--interdiff` 的输出由 #898 承接。
- **Decision:**
  - **三态：** 最终状态由 `--cover-letter`/`--no-cover-letter` 中最后出现的一个决定，都没给即为「未指定」。「未指定」时：给了 `--commit-list-format` 即隐含启用（FP-13，Git 2.54 探针确认）；否则在未给 `--interdiff`/`--range-diff` 时等同于禁用。
  - **前置条件：** 给了 `--interdiff`/`--range-diff`、系列多于一个补丁、且状态为显式禁用时，按 GC-FP-05 的 U 型拒绝报 `--interdiff requires --cover-letter or single patch`（`--range-diff` 同理）。
  - **其余组合：** 前置条件成立的其余情况，即系列只有一个补丁、或显式启用、或未指定（隐式启用），一律按 GC-FP-05 的 X 型拒绝，提示指向 #898。
  - 所有失败都发生在任何写入之前。
- **Alternatives considered:** 继续让 clap 报 unexpected argument：用例凑巧失败，原因却是错的。只看最终布尔值：会把「未指定 + 多补丁」误判为缺少 cover letter。
- **Consequences:** #898 接手时，只替换「不支持」分支，三态与前置条件诊断保留。
- **Revisit when:** #898 开工。

### ADR-FP-06：期望值来源

- **Status:** Accepted
- **Context:** CI 有 `git`，`compat_format_patch_mail_roundtrip` 已调用真实 Git，但 Git 版本不固定。
- **Decision:**
  - `command_test` 用例把期望字节写成测试内的字面量，来源是本计划「行为探针」表。
  - 正文与 stat 中由 diff 引擎生成的部分，以「与 `libra diff` 对应输出逐字节相同」为判据（ADR-FP-03）。
  - 只有 `compat_format_patch_mail_roundtrip` 中的 `git am` 往返需要真实 Git。

- **Consequences:** Git 行为变化时需要人工更新字面量。
- **Revisit when:** Git 改变上述任一输出。

### ADR-FP-07：提交者身份按 Git 规则在 `format-patch` 内解析

- **Status:** Accepted
- **Context:**
  - Git 的提交者身份规则（探针 #29–#32、#34–#37；`git/ident.c` v2.50.0）：
    - 名字：`GIT_COMMITTER_NAME` 只要已设置（含空值）就采用；未设置时取配置 `user.name`；名字为空时以 `empty ident name (for <email>) not allowed` 失败。
    - 邮箱：`GIT_COMMITTER_EMAIL` 只要已设置（含空值）就采用，空值输出 `<>`；未设置时取 `user.email`；仍无时，若 `user.useConfigOnly` 未开启则取 `EMAIL`，开启时以 `no email was given and auto-detection is disabled` 失败。
    - `GIT_AUTHOR_*` 不是提交者身份来源。
    - 都没有时 Git 会自动探测系统身份。
  - `libra commit::resolve_committer_identity` 会回退到 `GIT_AUTHOR_*`，且在 `useConfigOnly` 时跳过环境变量（`src/command/commit.rs:707-760`），与 Git 不同。
- **Decision:** 在 `format_patch.rs` 内实现一个私有的提交者身份解析，替换 `resolve_signoff_identity`，供裸 `--from`、cover letter 的裸 `--from` 与 `--signoff` 共用。规则与上面 Git 的规则相同，只有一处有意差异：Libra 不做系统身份自动探测，最终缺名字或邮箱时沿用现有 `identity unknown: …` 错误。三类失败都构造为 `CliError::fatal(msg).with_stable_code(StableErrorCode::CliInvalidTarget)`（GC-FP-05 F 型），消息分别为 `identity unknown: <现有细节>`、`empty ident name (for <email>) not allowed`、`no email was given and auto-detection is disabled`。配置读取沿用本文件现有的严格级联读取。Git 的 `committer.name`/`committer.email` 配置不在范围（DEFER-FP-05）。
- **Alternatives considered:** 复用 `commit::resolve_committer_identity`：会把 `libra commit` 与 Git 的两处差异带进 `format-patch`。修改 `commit` 的解析：改变 `libra commit` 的行为，超出 #529 范围。
- **Consequences:** 存在两个身份解析，GC-02 的例外理由是两者语义不同；`libra commit` 的差异登记为 DEFER-FP-04。
- **Revisit when:** `libra commit` 的身份解析对齐 Git 时，合并为一个共享 helper。

## 全局工程约束

本计划完整继承模板 GC-01..GC-13，另加以下约束：

- **GC-FP-01 单一事实源：** 重命名检测、正文、diffstat 与 numstat 只经 `src/command/diff/` 的共享入口。允许的改动只有三类：把既有函数或模块的可见性提升到 `pub(crate)`；新增提交对父提交的 `pub(crate)` 入口（FP-05）；把 numstat 分支提取为纯渲染函数，并让 `libra diff` 自身改为调用它（FP-07）。不得复制函数体。身份解析按 ADR-FP-07 留在 `format_patch.rs` 内。
- **GC-FP-02 零写入：** 每张卡新增的冲突、前置条件与参数错误检查，都必须在以下任一动作之前完成：创建输出目录、写任何补丁文件、向 stdout 写补丁。
- **GC-FP-03 零命中守卫：** Verification 中凡标「零命中」的命令，都在 `bash` 中先定义下列函数再调用。该函数按模板对 `rg` 退出码三分支判定，已于 2026-11-04 在 `bash -e` 与 `zsh -e` 下验证三条分支：

  ```bash
  zero_hits() {
    pattern="$1"; shift
    if rg -n -- "$pattern" "$@"; then
      echo "FAIL: forbidden pattern found"; return 1
    else
      rc=$?
      if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; return "$rc"; fi
      echo "OK: zero hits"
    fi
  }
  ```

- **GC-FP-04 测试隔离：**
  - 新用例全部用 `tempdir()` 仓库与显式 cwd。
  - 环境变量只给子进程设置，不改测试进程环境，因此不需要 `#[serial(env)]`。
  - 断言身份的用例，子进程同时把 `HOME`、`XDG_CONFIG_HOME`、`LIBRA_CONFIG_GLOBAL_DB`、`LIBRA_CONFIG_SYSTEM_DB` 指向该用例的临时目录，并清除未显式设置的 `GIT_AUTHOR_*`、`GIT_COMMITTER_*`、`EMAIL`、`LIBRA_COMMITTER_*`，避免读到操作者的真实身份（GC-13 的测试隔离要求）。
- **GC-FP-05 拒绝门族：** 本计划每条新增的失败路径（拒绝）都按下表展开成一组门。每个门是一个独立命名的测试函数，只断言一个谓词，计入所在卡的 G-03 分子（由 EX-FP-01 承载超限）。测试函数由 FP-03 在 `tests/command/format_patch_test.rs` 新增的宏 `refusal_gates!` 生成。完整测试名为 `command::format_patch_test::<拒绝 ID>__<后缀>`（`tests/command_test.rs` 以 `command` 模块挂载 `tests/command/mod.rs`），单门执行命令为 `source .env.test && cargo nextest run --test command_test --no-tests=fail -E 'test(=command::format_patch_test::<门名>)'`：零匹配即失败。2026-11-04 的探针确认了 Libra 三种输出模式的通道：人读模式 stderr 先是人读行、再是 `Error-Code:` 行；`--json` 在 stderr 输出美化 JSON；`--machine` 在 stderr 输出单行 JSON；三种模式 stdout 都为空。
  - **U 型（用法拒绝，ADR-FP-04）：** 构造 `CliError::fatal(msg).with_stable_code(StableErrorCode::CliInvalidArguments)`。7 个门：
    - `__msg`：stderr 第 1 行等于 `fatal: <msg>`；
    - `__code`：stderr 第 2 行等于 `Error-Code: LBR-CLI-002`；
    - `__exit`：退出码为 129；
    - `__stdout`：stdout 为 0 字节；
    - `__fs`：快照不变。快照为测试 cwd 下全部相对路径与内容 SHA-256 的有序列表，加上 argv 中命名的每个输出路径（`-o` 目录、`--output` 文件）的存在性与内容 SHA-256。输出路径的初始状态是每条拒绝的夹具参数，在卡内拒绝表的「夹具」列写明：`absent`（执行前不存在，执行后仍不存在）；`sentinel`（执行前 `--output` 目标是内容为 `sentinel` 的文件，或 `-o` 目标是只含文件 `keep`（内容 `sentinel`）的目录，执行后不变）；`none`（argv 不含输出路径，只比较 cwd）。argv 原样执行，不为夹具添加任何参数；
    - `__json`：以 `--json` 重跑，stderr 解析出的 JSON 对象等于 `{"ok":false,"error_code":"LBR-CLI-002","category":"cli","exit_code":129,"severity":"fatal","message":<msg>}`（无 `hints` 字段）；
    - `__machine`：以 `--machine` 重跑，stderr 恰为一行，解析出的对象与 `__json` 的期望对象相等。
  - **X 型（显式不支持）：** 沿用 `--relative` 的写法，构造 `CliError::failure(msg).with_stable_code(StableErrorCode::Unsupported).with_hint(hint)`。8 个门：与 U 型相同的 7 个门，但 `__msg` 期望 `error: <msg>`，`__code` 期望 `Error-Code: LBR-UNSUPPORTED-001`，`__exit` 期望 128，JSON 期望对象为 `{"ok":false,"error_code":"LBR-UNSUPPORTED-001","category":"internal","exit_code":128,"severity":"error","message":<msg>,"hints":[<hint>]}`（2026-11-04 `--relative` 探针的实际形状）；另加 `__hint`：stderr 中恰有一行等于 `Hint: <hint>`。本计划的 X 型 `hint` 固定为 `see https://github.com/libra-tools/libra/issues/898`。
  - **F 型（身份失败，ADR-FP-07）：** 构造 `CliError::fatal(msg).with_stable_code(StableErrorCode::CliInvalidTarget)`（沿用现有 `IdentityMissing` 映射）。7 个门：与 U 型相同，但 `__code` 期望 `Error-Code: LBR-CLI-003`，JSON 的 `error_code` 为 `LBR-CLI-003`、`category` 为 `cli`、`exit_code` 为 129。
  - **门集合核对（shell 门）：** 每张含门族的卡另有一个「门集合相等」门。它是 shell 门，不是 Rust 测试：在仓库根目录新开 `bash -euo pipefail` 进程，先定义下列函数，再执行卡内给出的 `gate_set …` 调用，退出 0 即通过。期望集合只含测试门，不含门集合门本身；集合为空、列举失败或集合不等都非 0 退出。

    ```bash
    source .env.test
    gates_u() { for id in "$@"; do for x in msg code exit stdout fs json machine; do echo "${id}__${x}"; done; done; }
    gates_x() { for id in "$@"; do for x in msg code exit stdout fs json machine hint; do echo "${id}__${x}"; done; done; }
    gate_set() {
      local prefix="$1"; shift
      test "$#" -gt 0
      local listing actual expected
      listing="$(cargo test --test command_test -- --list "command::format_patch_test::${prefix}")"
      actual="$(printf '%s\n' "$listing" | sed -n 's/: test$//p' | sort)"
      expected="$(printf 'command::format_patch_test::%s\n' "$@" | sort)"
      test -n "$actual"
      test "$actual" = "$expected"
    }
    ```
