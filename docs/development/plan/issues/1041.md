## 已决议设计决策

### ADR-I1041-01: 只复用解码函数

- **Status:** Accepted
- **Context:** add 已经用 `decode_c_quoted`。restore 另写一套会分叉。
- **Decision:** 换行模式的每一非空行调用 `decode_c_quoted`。`Ok(None)` 表示未加引号。错误整批失败，不还原本批任何路径。NUL 模式保持字节切分。
- **Alternatives considered:** 把 add 的私有切分函数改成 pub。那会让本卡写 `add.rs`，而引号轴本身不需要。
- **Consequences:** 空的解码结果按空路径丢掉，不变成整树。
- **Revisit when:** 两处切分规则再次分叉。

### ADR-I1041-02: staged 清除 intent-to-add 位

- **Status:** Accepted
- **Context:** `git rm --cached` 之后路径不在 index，但仍在 HEAD。
- **Decision:** 候选并集已经存在（`restore.rs:789-799`）。缺口是 `git rm --cached` 之后 `add -N` 留下的 intent-to-add 位：`update_preserving_flags` 会保留它，`diff --cached` 仍像 deleted。`--staged` 从 HEAD 恢复匹配路径时清掉该位；即使对象 ID 与 HEAD 相同，也不得因为 `restore.rs:906` 的内容未变分支跳过清位。不新增缺失路径的第二套并集。
- **Alternatives considered:** 把路径从 index 删掉再当缺失路径加回来。issue 写的是 index 停在 DA，路径还在。
- **Consequences:** worktree-only 路径不走这个并集。
- **Revisit when:** overlay 模式需要不同并集。

### ADR-I1041-03: 结尾换行只保留一份

- **Status:** Accepted
- **Context:** payload 与额外 eol 叠加出空行，`test_cmp` 失败。
- **Decision:** 正文为空或已以 `\n` 结尾时不再追加（Windows 上 `eol` 是 `\r\n`，`restore.rs:1716`，不能按所选 eol 判定，否则 LF 结尾的 blob 仍多一行）。非空正文没有结尾换行时追加一个所选 eol。deleted 占位同样处理。
- **Alternatives considered:** 改成行级 merge。issue 写明状态正确，只是空行。
- **Consequences:** `restore.rs:2919-2922` 的现有单测期望已经符合这一规则，不需要改。
- **Revisit when:** 要输出 Git 的行级冲突块。

### ADR-I1041-04: resolve-undo 记录放在工作树级边车，带身份校验后才消费

- **Status:** 待重设计；Claude R7 发现 A→B→A 同字节重写与绕锁写者。以下指纹草案不是可实施方案，不得实施。
- **Context:** Git 在 `add` 解决冲突时把原三侧写进 index 的 REUC 扩展；`restore --merge` 消费后 index 只剩 stage 1–3、记录删除；checkout、merge、read-tree 会清空记录（`builtin/checkout.c:889`、`builtin/merge.c:1493`、`builtin/read-tree.c:207`、`merge.c:48`）。当前依赖 `git-internal 0.10.4` 的 crate 内 `src/internal/index.rs:417-434` 读取时丢弃可选扩展，`Index::save` 重写时也不保留；该路径属于 Cargo registry 的依赖源码，不是本仓库文件。当前依赖因此不能直接保存 REUC。index 是工作树级的（`src/utils/path.rs:23-36`）。
- **Decision:**
  1. **位置与格式：** 边车路径是 `path::index()` 同目录下的 `resolve-undo`（每个工作树一份，不在 common storage）。内容是 JSON：`{"version":1,"records":[{"path":…,"head":…,"index_sha256":…,"resolved":{"mode":…,"oid":…},"stages":{"1":{…},"2":{…},"3":{…}}}]}`，`head` 是写入时 HEAD 的提交 OID（unborn 时为全零），`index_sha256` 是 `index.save` 成功之后读取的实际 index 字节的 SHA-256，`resolved` 是 `add` 写下的 stage 0 条目，`stages` 只含实际存在的阶段。新模块 `src/utils/resolve_undo.rs` 负责读写。记录不绑定 merge-state，index 每次 `save` 后的原始字节都由它自己指纹化；因此任意命令只要不改写 index，就不影响记录，任何重写 index 的 reset、merge、read-tree、update-index、commit -a 或 rebase 都会使记录失效。
  2. **写入（`add`）：** 采集点是 `stage_a_file` 的 `FileStatus::Modified` 分支（`src/command/add.rs:2915`，TC-2631 的 `add file` 走这里）；`New` 分支里的 `clear_conflict_stages`（`:2882`）只在没有任何阶段时进入，恒为空操作，不作为采集点。`add --resolved` 的 `stage_resolved_path`（`:964`）与删除解决路径（`remove_all_stages` `:841`，调用点 `:939`、`:2921`）不记录，登记为差异。只在 `index.save` 成功之后，读取最终 index 原始字节并计算 `index_sha256`，读入现有边车、删除 `index_sha256` 不等于当前 index 的记录、替换这些路径的记录，用 `atomic_write::write_atomic` 原子写回。`index.save` 失败时不碰边车。边车写失败时 `add` 仍成功（index 已保存），不打印警告，旧边车因原子写保持完整；边车是恢复用的内部记录，读写失败对 `add` 的用户可见行为没有影响。`add` 和 `restore --merge` 都在 `WorkspaceMutation` 的 `operation-v2.lock` 租约内执行 index 和边车的检查、修改与发布；参与该租约的写者不会在两步之间插入。未持锁的外部 index 写者可能并发覆盖 index，以下失效协议将其视为失效而非恢复。
  3. **消费（`restore --worktree --merge <path>`）：** 只在 index 中该路径没有 stage 1–3 时读取。读取当前 index 原始字节，记录有效当且仅当 `head` 等于当前 HEAD、`index_sha256` 等于当前 index 指纹，且 index 的 stage 0 条目存在、mode 与 OID 都等于 `resolved`。有效时：删除 stage 0、写回记录里的 stage 1–3、按 I1041-03 的规则物化冲突标记、保存 index，然后从边车删除该记录（原子写；这一步失败只打印警告，残留记录因 stage 0 已不存在且 index 字节已变而不再有效）。无效（陈旧）时忽略并删除该记录，行为与现在相同（`pathspec did not match`）。index 中仍有阶段时完全不读边车。以 `filter_paths` 对有效记录做 pathspec 匹配，并在任何 index 或工作树写入之前用 `preflight_conflict_merge_worktree` 检查全部命中路径；`restore_conflict_stage` 不支持的有效 gitlink 路径在预检失败，不写任何东西。
  4. **失效与上限：** 用 index 原始字节指纹而不是 HEAD 或 merge-state 令牌判定失效，因此解决结果恰等于 HEAD blob、随后 `reset --hard` 或 `merge --abort` 时也不能复活冲突。任何其它 index 重写同样失效，即使 stat 或内容碰巧相同。损坏或超过 16777216 字节的边车当作无记录并打印警告；合法但失效的匹配记录被删除。边车保存于 index 同目录，`commit --dry-run -a` 的 `with_index_override` 使其与预览 index 配对，绝不写入真实工作树的边车。
  5. **崩溃窗口：** `index.save` 之后、边车写入之前中断：没有记录，`restore --merge` 回到现在的报错，不会损坏 index。`restore` 保存 index 之后、删除记录之前中断：残留记录因 stage 0 已不存在而无效。
- **Alternatives considered:** 给 index 文件尾追加 REUC（当前 `Index::save` 会丢掉，`Index::load` 不返回）；在 switch、merge、reset 等命令的相应操作点显式清边车；或绑定 merge-state 令牌。后两种方案尚未证明能覆盖所有 index 写入。**撤销旧推断：** 内容指纹不能识别同字节重写或 A→B→A，不能证明任意重写都会失效；仍需覆盖所有写者的协议和恢复测试。
- **Consequences:** 真实 Git 读不到这份记录；提交之后不能再 `restore --merge` 已解决的路径（Git 可以），文档写明。DEFER-I1041-REUC 等待 git-internal 能往返可选扩展。

#### 失效机制的写入点核对

**D 取自发布候选分支，不承接其它提交。** 第一段把同一个 SHA 同时推到 `main` 与 `release/v<VERSION>`。`base.yml` 的 push 触发是 `branches: [main, 'release/**']`，注释写明「Release candidates must finish even while main continues advancing」（`.github/workflows/base.yml:3-5`），`cancel-in-progress` 只对 PR 与 `refs/heads/main` 生效（`:13-15`）；`.github/workflows/codeql.yml:16` 的 push 同样包含 `release/**`；`cancel-superseded-main.yml` 只在 `main` 上触发、只取消 `main` 的 run；`release.yml` 只由 `v*` tag 触发，推候选分支不会发布任何东西。仓库先例：`release/v0.30.155` 上 SHA `3462306b` 的 base run 41976607602（约 178 分钟）与 CodeQL run 41976607585 在 2026-11-05 都是 success，该分支事后已删除（2026-11-07 查询远端为 404）；更早有 `release/v0.30.92`。所以第二段只认候选分支上 head SHA 等于本卡 SHA 的 run，正是 ER-04 D 的「同一 head SHA」，没有偏离，也不承接任何后继提交的结论。候选分支是发布授权范围内的远端 ref，不是功能分支，不开 PR，第四段在 release 全部成功后删除它。

上游前进时不用 `libra pull` 制造合并提交。若 C 组提交之后、第一段推送之前 `origin/main` 前进，按以下步骤恢复，每步失败都停止：
1. 此时工作区必须干净（本卡改动都已在 C 组提交里，工作区独占检查保证没有他人改动）。执行 `libra rebase origin/main`。它失败时执行 `libra rebase --abort`：abort 成功说明 rebase 遇到冲突，版本面冲突按第 2 步处理，其它冲突手工 rebase：`plan-status.md` 与 `COMPATIBILITY.md` 这类按行登记的文件以 `origin/main` 的版本为底、只重放本卡的行，其它文件按双方语义合并；abort 失败说明 rebase 根本没有开始（例如工作区不干净），按错误信息处理，不计入恢复次数。
2. 版本面冲突（上游改了版本）：`libra reset --mixed HEAD^` 撤销本卡尚未推送的 C 组提交，同时清空暂存区（只涉及本卡自己的改动；`--soft` 会把本卡改动留在暂存区，之后的工作区独占检查与暂存守卫都会拒绝，2026-11-07 在隔离仓库实测两者差别），`libra restore --source HEAD --worktree Cargo.toml Cargo.lock install.sh install.ps1` 把四个版本面文件恢复为此时 `HEAD`（本卡原基线）的内容，使随后的 `pull --ff-only --autostash` 无冲突地带入上游的新版本，然后从生命周期第 3 步的第 1 小步重新开始（外部前置检查与工作区独占检查、`pull --ff-only --autostash`、窗口检查、在上游版本上 bump、C 组全套）。
3. rebase 成功后，以 `PHASE=c` 运行提交后范围检查，并核对 `libra diff --name-only HEAD^ HEAD` 与 rebase 前 `libra diff --name-only "$C_COMMIT^" "$C_COMMIT"` 的路径集合相同，防止重放丢文件；再运行 bump 前窗口检查（它接受父提交为 `origin/main` 的本卡提交）与版本面内容检查（`VSRC=head`）。
4. 先运行「C 组结论携带检查」。上游增量只含文件名未被 `tests/`、`src/`、`build.rs` 与 `.github/` 引用的计划文件，以及增删行不含测试读取模式的 `plan-status.md` 改动时，C 组结论随重放携带：该检查在新树上重跑窗口检查与版本面内容检查并写下携带标记。其它任何增量（包括改到 `tests/compat/agent_architecture_guard.rs:8181-8215` 读取的 `plan-status.md` 行，以及被测试读取的计划文件：`tests/session_capture_docs_contract.rs:10` 与 `tests/opencode_hook_contract_test.rs:24` 编入其它计划文件）都以 C 组运行器在重放后的树上整套重跑本卡全部门与 C 组脚本（含双环境全量 nextest）；此时工作区干净，被测的树就是 `HEAD`。
5. 只在本文件「实施证据」更新 C 组收据（仓库里没有构建或测试读取 `docs/development/plan/issues/`），以 `PHASE=amend` 运行暂存守卫（它只允许本文件，并要求运行器为重放后的树写下的通过标记，或指向当前 `HEAD` 的携带标记），执行 `libra commit --amend -S --no-edit`：`libra rebase` 会把旧提交的 `gpgsig` 头逐字节复制到重放后的提交上（2026-11-07 在 0.30.157 与 0.30.158 上实测），但树与父提交已变，这个签名已经失效，所以签名头存在不代表签名有效，必须用 `-S` 重新签名；随后运行的「记录 C_COMMIT」会比较新旧两个提交的 `gpgsig` 块，相同就失败；原提交信息里的 `Signed-off-by` 随重放保留，不再加 `-s`（加了会出现两行，2026-11-07 已实测）。
6. 以 `PHASE=c` 再跑提交后范围检查，运行「记录 C_COMMIT」脚本，然后重新执行第一段。

需要整套重跑的恢复同一张卡最多 3 次（携带不计次数，但每次携带之后都要重新执行第一段）；第 4 次需要整套重跑时停止，把卡保持在 `in-progress` / `locally-accepted`，在「实施证据」记录每次的上游增量，并向用户报告，由用户决定是否协调其它写者暂停推送。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1041-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

```bash

A/B 全部通过后，`Acceptance` 写 `locally-accepted`（留在工作区，随 C 组提交一起提交），再做 ER-05 review 直到 PASS。有 C 组提交的卡在 PASS 后先运行「ER-05 审查摘要」，再把 `<CARD>:ER05_SESSION=`、`<CARD>:ER05_OUTPUT_SHA256=`、`<CARD>:ER05_VERDICT=PASS`、`<CARD>:ER05_REVIEWED=` 四行写入「实施证据」（行首是卡 ID 与冒号，每个键恰好一行；重审 PASS 时替换旧值，历次结论记在评审日志），`ER05_REVIEWED` 的值就是该脚本的输出，即审查时产品改动的摘要。`PHASE=c` 的暂存守卫在 bump 之后的树上重算同一摘要并要求相等：C 组失败后在写集内修改产品文件，或修复模式改动产品文件，摘要都会变化，必须重新审查并替换这四行。
3. C 组：
   1. 以 `WHEN=stage1` 执行外部前置检查（网站等发布前置要在本卡改动提交之前满足；失败时本卡改动尚未提交，按第 8 步以 `PHASE=blocked` 登记并推送，前置恢复后从这里继续），再以 `MODE=check` 运行工作区独占检查（它同时要求暂存区为空）。
   2. 执行 bump 前窗口检查。`HEAD` 落后于 `origin/main` 时，先执行 `libra pull --ff-only --autostash`（第 1 小步的工作区独占检查已保证工作区里只有本卡允许集合内的改动，所以 autostash 只暂存本卡自己的改动；恢复冲突时，`plan-status.md` 与 `COMPATIBILITY.md` 这类按行登记的文件以 `origin/main` 的版本为底、只重放本卡的行，不把旧行与新行同时保留，其它文件按双方语义手工合并，并从 A/B 重新开始），再重跑窗口检查。窗口检查通过后，在未 bump 的树上运行版本面 parity 预检 `source .env.test && cargo nextest run --no-tests=fail --test compat_version_surface_sync`，失败即停、不 bump。
   3. bump 只改 `Cargo.toml`、`install.sh`、`install.ps1` 的版本行（修复模式不 bump，见第 6 步），随后执行一次 `cargo build`，由工具链刷新 `Cargo.lock`（不手改）；然后执行版本面内容检查（`VSRC=worktree`）与精确句预检（有网站面的卡）。
   4. 把 `plan-status.md` 本计划行写成「C 组进行中」的最终措辞（`agent_architecture_guard` 会读取该文件，所以它必须在快照之前定稿）。
   5. 运行 C 组运行器。它从本文件按固定锚点抽出本卡全部 Verification 门块与 C 组 fail-closed 脚本，然后依次以 `MODE=snapshot` 运行工作区独占检查（记录 `HEAD`、改动路径集合与每个改动文件的 SHA-256；本文件除外，仓库里没有任何构建或测试读取 `docs/development/plan/issues/`，2026-11-07 已用 `rg` 核对）、运行门块脚本、以新的 `bash` 进程运行 C 组脚本、以 `MODE=verify` 运行工作区独占检查。四步都通过后才写入通过标记，标记绑定快照文件、门块脚本与 C 组脚本三者的 SHA-256；任一门失败就没有标记。
   6. 在本文件「实施证据」写入 C 组收据（版本号、各门结论与计数、C 组脚本打印的 release 二进制 SHA-256、通过标记的三行；ER-05 的四行已在第 2 步写入）。卡字段保持 `in-progress` / `locally-accepted`。
   7. 以 `PHASE=c` 运行暂存守卫（它再次核对快照，并要求通过标记与重新抽出的脚本一致），执行 `libra commit -S -s -m "<type>(<scope>): <summary> (#1041)"`（`-S` 用仓库 vault key 强制签名，不得用 `--no-gpg-sign`），以 `PHASE=c` 运行提交后范围检查，再运行「记录 C_COMMIT」脚本。推送前 `origin/main` 前进时，按发布四段开头的恢复步骤处理。
4. 第一段起的推送、候选分支、tag 与 release 都是对外动作，只在本卡获得执行授权后进行；`release.yml` 使用的 environments 在 2026-11-07 核对时都没有保护规则，不需要人工审批。第一段之前再以 `WHEN=stage1` 执行一次外部前置检查：这时 C 组提交已在本地、尚未推送，检查失败只停止并报告，不做 `blocked` 登记（登记提交只能连同未过 D 的 C 组提交一起推送），本卡保持 `in-progress` / `locally-accepted`，前置恢复后重跑本检查与第一段。通过后执行发布四段的第一段，它把同一个 SHA 推到 `main` 与发布候选分支 `release/v<VERSION>`，并把 SHA 与版本写入状态文件。第一段成功后立即做 `remote-pending` 登记：把本卡 `Acceptance` 改为 `remote-pending`，在「实施证据」写入 `<CARD>:C_COMMIT=`、`<CARD>:PUSHED_SHA=`、`<CARD>:VERSION=` 三行（行首是卡 ID 与冒号，值与状态文件相同；同一计划有多张卡时按卡区分）与推送 UTC，同步 `plan-status.md` 本计划行，以 `PHASE=remote` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): record $CARD push (#1041)"`，以 `PHASE=remote` 运行提交后范围检查与计划目录推送脚本。这笔提交让 `main` 前进、取消 `main` 上本卡 SHA 的 run，但不影响 D：D 只取候选分支上 head SHA 等于本卡 SHA 的 run，`base.yml` 对 `release/**` 不取消进行中的 run，`cancel-superseded-main.yml` 只处理 `main`。
5. 依次执行第二至四段（第三段自己以 `WHEN=stage3` 执行外部前置检查），第四段确认 release 五个 job 全部成功之后执行网站三段（有网站面的计划；网站段一要求状态文件里已有 `RELEASE_RUN`）。
6. 修复模式：第二段在建 tag 之前以失败结论退出（本卡 SHA 在候选分支上的 run 重跑一次后仍失败；本卡版本 V 已在 main、但没有 tag），本卡保持 `in-progress` / `remote-pending`，不改写 tag，也不再 bump：在本卡写集内做修复，以 `MODE=repair` 重走第 3 步（窗口检查改为要求 `origin/main` 的版本就是状态文件里的 V、V 没有 tag、且上一次的 `PUSHED_SHA` 是 `origin/main` 的祖先；版本面内容检查要求四个版本面文件不变），再以 `MODE=repair` 执行第一段（版本必须等于父提交的版本且仍无 tag；候选分支 `release/v<V>` 必须已存在且是修复 SHA 的祖先，修复 SHA 以快进推上该分支）；第三段在修复 SHA 上建 V 的 tag。失败收据与修复提交写入「实施证据」。tag 建成之后 release 失败时，tag 不改写；先删除 V 的候选分支（尖端必须是 V 的 `PUSHED_SHA`，用 `gh api -X DELETE repos/libra-tools/libra/git/refs/heads/release/v<V>`，删除后回读为 404，删除结果写入「实施证据」），再按正常模式在 V 之上 bump 到 V+1 前滚修复（V 已有 tag，窗口检查放行），V+1 使用新的候选分支。本卡的 `Rollback mode` 是 `immutable-release`：tag 与 Release 建立后不改写，修复只发新版本前滚；C 组提交推送之前的撤销按第 9 步放弃处理，不是第二种恢复模式。
7. 终止链：本卡全部 D 都通过后，才把卡改为 `done` / `complete`。在「实施证据」写入 `<CARD>:CI_BASE_RUN=`、`<CARD>:CI_CODEQL_RUN=`（候选分支 `release/v<VERSION>` 上 head SHA 为 `PUSHED_SHA` 的 run）、`<CARD>:TAG=`、`<CARD>:RELEASE_RUN=`、`<CARD>:CANDIDATE_DELETED=yes`、`<CARD>:ROLLBACK_VERIFIED=`（第四段降级演练装上并核对的上一发布版本）各一行，有网站面的卡另写 `<CARD>:SITE_SHA=` 与 `<CARD>:SITE_VERIFIED=`，值都与状态文件相同；五个 release job 的结论与网站部署 ID 以文字记录（无网站面的计划写 N/A），同步 `plan-status.md` 本计划行。以 `PHASE=terminal` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): record $CARD delivery (#1041)"`，以 `PHASE=terminal` 运行提交后范围检查与计划目录推送脚本。按 v2.14，它自身的 base/CodeQL 结论由下一次 `plan-status.md` 例行同步补记，不另开提交，也不重启终止链。
8. `blocked` 登记与解除：已 `in-progress` 的卡遇到本卡自身的 ER-10 故障（工作区只含本卡允许集合内的改动），或第 3 步第 1 小步、第三段之前的外部前置检查失败时，把本卡 `Lifecycle` 改为 `blocked`，`Acceptance` 保持 `HEAD` 已提交的值（A/B 之后工作区里尚未提交的 `locally-accepted` 先改回 `HEAD` 的值、解除后再写回，未提交的验收结论不随登记提交公开；暂存守卫按这一点核对），写明原因与解除条件，同步 `plan-status.md` 本计划行，以 `PHASE=blocked` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): block $CARD (#1041)"`，以 `PHASE=blocked` 运行提交后范围检查与计划目录推送脚本，其它计划的开工门由此看到它。`PHASE=blocked` 只暂存本文件与 `plan-status.md`，允许本卡写集内尚未提交的改动留在工作区。两种情况不登记、只停止并向用户报告，本卡保持 `in-progress`（对其它计划的开工门同样算活动写者）：C 组提交已在本地而尚未推送时（见第 4 步；计划目录推送脚本也会拒绝父提交不在远端 `main` 上的登记提交）；工作区出现本卡允许集合以外的改动时（登记提交无法与他人改动隔离）。条件恢复后用同一 `PHASE` 把 `Lifecycle` 改回 `in-progress`（提交信息写 `unblock`），再从中断处继续。
9. 放弃（释放家族串行锁）：本卡还没有任何推送到远端 `main` 的 C 组提交（状态文件没有 `PUSHED_SHA`），而外部前置长期不可用或用户决定改期时，可以放弃本卡：本地已有未推送的 C 组提交时先 `libra reset --mixed HEAD^` 撤销它；再用 `libra restore` 逐个撤销本卡写集内产品文件与版本面文件的改动、删除本卡新建的未跟踪文件（只限本卡允许集合内的路径）；`plan-status.md` 不整文件还原，只把本计划行改回；然后把 `Lifecycle / Acceptance` 改回 `pending` / 空并写明原因，同步 `plan-status.md` 本计划行，以 `PHASE=abandon` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): abandon $CARD (#1041)"`，以 `PHASE=abandon` 运行提交后范围检查与计划目录推送脚本。「没有推送过」不只看可丢弃的本地状态文件：`PHASE=abandon` 的暂存守卫先 fetch，并向 GitHub 核对状态文件里的 `C_COMMIT`（若有）不在远端 `main` 上、`origin/main` 的版本仍等于当前 `HEAD`（撤销后的基线）的版本、下一 patch 版本的候选分支 `release/v<下一版本>` 与 tag `v<下一版本>` 都不存在；任一不满足（例如推送已经落地而状态文件还没写下 `PUSHED_SHA`）就拒绝放弃。已经推送过的卡不能放弃，只能按第 6 步修复或前滚。

**记录 C_COMMIT（`bash` 运行；C 组提交与提交后范围检查之后运行，rebase 恢复的 amend 之后再运行一次）：**

```bash

state_get() { if [ -f "$STATE" ]; then awk -v k="$1" 'index($0, k "=") == 1 { v = substr($0, length(k) + 2) } END { print v }' "$STATE"; fi; }
state_put() { mkdir -p "$STATE_DIR"; touch "$STATE"; awk -v k="$1" 'index($0, k "=") != 1' "$STATE" > "$STATE.tmp"; printf '%s=%s\n' "$1" "$2" >> "$STATE.tmp"; mv "$STATE.tmp" "$STATE"; }
gpgsig_digest() { libra cat-file -p "$1" | awk '/^gpgsig /{ f = 1; print; next } f && /^ /{ print; next } f { exit }' | shasum -a 256 | cut -d' ' -f1; }
sha=$(libra rev-parse HEAD)
test -n "$sha"
previous=$(state_get C_COMMIT)
if [ -n "$previous" ] && [ "$previous" != "$sha" ] && [ "$(gpgsig_digest "$sha")" = "$(gpgsig_digest "$previous")" ]; then
  echo "HEAD carries the signature of $previous: libra rebase copies gpgsig verbatim and the copy is no longer valid; run libra commit --amend -S --no-edit first" >&2
  exit 1
fi
state_put C_COMMIT "$sha"
echo "C_COMMIT=$sha"
```

**C 组运行器（`bash` 运行，`CARD` 为本卡 ID）：** 从本文件按下列固定锚点抽出脚本，所以执行的就是本文件里经过审查的门块，不靠执行者逐段复制。抽取规则：锚点在全文（或标注为本卡范围时在本卡 `Task` 标题到下一个 `Task` 标题之间）必须恰好出现一次，取它之后的第一个 `bash` 代码块，锚点与代码块之间不得隔着标题。Verification 门块按顺序拼成一个门块脚本，开头是 `set -eo pipefail`，块与块之间插入 `set +u`，在同一个 shell 里执行，所以前置块定义的函数可供后面的门块使用；C 组 fail-closed 脚本单独成一个脚本，在门块脚本通过之后以新的 `bash` 进程运行，门块里 TC 的 `export`（`LIBRA_BIN`、`TC_*`、`GIT_*` 等）因此不会带进 C 组的全量测试。任何一条命令失败，所在脚本立即非零退出，运行器随之停止。锚点只在正文里查找：代码块、「评审结论与修订记录」节与「实施证据」节都不参与匹配，所以脚本自身、日志与收据里出现同样的文字不会造成歧义。各卡的门块锚点及顺序就是下面脚本里 JSON 配置的 `gates`（`card` 表示只在本卡范围内查找），C 组脚本的锚点是 `c`。有 C 组提交的卡，门块脚本先跑 bump 前窗口检查、版本面内容检查（脚本开头导出 `VSRC=worktree`）与有网站面的卡的精确句预检，再跑本卡的 Verification 门块，所以这三项也由通过标记绑定，漏跑会被暂存守卫发现。运行器只接受 `MODE` 为 `normal`（缺省）或 `repair`，并原样传给门块脚本；工作区独占检查用的 `MODE=snapshot`、`MODE=verify` 由运行器在调用时单独设置。`no_c` 列出的卡没有 C 组提交，运行器拒绝它们，它们的门块只由 `PHASE=accept` 的暂存守卫重跑。
