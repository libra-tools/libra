## 文档职责

本文处理 Issue #539 在当前 `main` 上仍成立的 `rev-parse` 与 Git 契约差异。核对结论：场景 1 的真实失败是 `rev-parse --short <完整对象 ID>` 与 `rev-parse --verify <完整对象 ID>` 在对象未写入对象库时被拒（「inflate」字样是 issue 生成器从另一用例的测试体中误取的签名，见事实基线），与 #839 同轴同代码；场景 2 中普通名字的示例（注释 tag、`:<path>`、`HEAD:<path>`、`HEAD`）在当前版本都已能解析，原失败归属其它 issue；gitlink 示例（TC-3170，`rev-parse :submodule`）属 D 类子模块、已转 SKIP，未证明已修复，仍为显式不支持。目标：让单修订模式按 Git 的对象名语义接受完整长度对象 ID，并让 `--short` 为不存在的对象给出 Git 相同的缩写；把映射到 #539 与 #839 的 88 个上游用例在新版本上的结论与归属记录在案。

### 适用范围

- `libra rev-parse` 的单修订模式（`--verify`、`--short[=<n>]`，以及二者与 `--default`、全局 `--quiet`、`--json` 的组合）对**完整长度对象 ID** 的解析：不再要求对象存在（正文场景 1；#839）。
- `--short` 对不存在于对象库的对象的缩写：取「不短于请求长度、且没有任何现存对象共享」的最短前缀（Git `find_unique_abbrev`）。
- `--short` 的前缀查询改用会报告目录与 pack 索引读取失败的 `ClientStorage::search_checked`：查询不完整时失败，不再把读取失败当作零命中而输出缩写。
- 公开文档显式归类 #539 映射用例涉及、但本计划不实现的 `rev-parse` 形式（`--all`、`--exclude`、`--exclude-hidden`、`--git-path`、`--show-object-format`、`--show-ref-storage-format`、对称差 `A...B`，以及无参数时与 Git 的输出差异），满足 #539 验收第 3 条（RP-00）。
- 随附改写：`src/utils/util.rs` 中 `require_object_exists_typed` 的文档注释（只改注释）；既有守卫 `compat_rev_parse_peel_selectors` 中与新合同相反的一条断言；`plumbing_exit_contract_test` 中 `rev-parse` 的 MissingObject 行。
- 对应文档：`docs/commands/rev-parse.md`、`docs/commands/zh-CN/rev-parse.md`、由同步脚本生成的网站页 `../libra-backend/apps/tanstack-app/content/docs/commands/rev-parse.en.md`、开发文档 `docs/development/commands/rev-parse.md`、`COMPATIBILITY.md` 第 217 行 `rev-parse` 主能力行（原地改写，不增删行）。
- 测试：`tests/command/rev_parse_test.rs`（`command_test` 目标）新增用例；`tests/command/plumbing_exit_contract_test.rs` 改一行；`tests/compat/rev_parse_peel_selectors_test.rs` 改一条断言。
- 上游复核：88 个映射 TC 的公开复跑结果（RP-02）。

### 非目标

### 成功定义

- `rev-parse --verify <完整对象 ID>`、`--short[=<n>] <完整对象 ID>`、`--default <完整对象 ID> --verify` 在对象未写入时按 Git 输出（SHA-1 与 SHA-256 仓库各自的 hex 长度），大写输入输出为小写，全局 `--quiet` 下退出 0。
- `--short` 对不存在的对象给出的长度等于 Git：现存对象共享更长前缀时向后延长，否则取请求长度。
- 读取对象内容的形式（`^{object}`、`^0`、`<id>:<path>`）与非完整长度的十六进制串仍按 Git 失败，既有文案不变；`--short` 的前缀查询遇到读取失败时以非 0 退出，不输出缩写。
- EN、zh-CN、网站页、开发文档、`COMPATIBILITY.md:217` 与实现一致，并显式列出本计划不实现的 `rev-parse` 形式及其跟踪 issue（RP-00）。

### ADR-RP-02：单修订模式按 Git 的对象名语义，不另行证明对象存在

- **Status:** Accepted
- **Context:** Git 的 `--verify` 只要求恰好一个参数能被 `repo_get_oid_with_flags` 解析为对象名；完整长度十六进制不查对象库，`--short` 隐含 `--verify`（`builtin/rev-parse.c` @ 6de20f6092 `:856-864`、`:882-893`、`:1153-1192`；探针 #1–#8、#15）。需要读取对象的形式（peel、父提交、tree path）在对象缺失时失败（探针 #12）。Libra 在共享解析器之外为 `--verify`/`--short` 加了一层 `require_object_exists_typed`（`rev_parse.rs:643-651`），这是唯一的差异来源。
- **Decision:**
  - 删除 `resolve_rev_parse` 中 `--verify`/`--short` 的 `require_object_exists_typed` 调用；单修订模式的成败只由共享解析器决定。refs、reflog、tag ref 的既有引用校验、peel、父提交导航与 tree path 均在解析器内读取对象，行为不变。
  - `util::require_object_exists_typed` 的函数体与签名不变（`tag` 目标解析、533 TG-01 的 `--points-at` 继续使用），只把注释改为「需要证明完整长度对象 ID 存在的调用方使用（例如 `tag` 的目标解析）」。
  - 文档写明：完整长度对象 ID 在 `--verify`/`--short` 下不检查对象是否存在，需要时用 `<id>^{object}`。
  - 该决定同样作用于 `AUTO_MERGE` 等经解析器投影为完整 ID 的名字：与 Git 读 ref 值时不验证对象一致。
- **Alternatives considered:** 只对 `--short` 放开、`--verify` 继续证明存在：与 Git 不一致，且 Git 的 `--verify` 对完整长度十六进制同样不查对象库（`builtin/rev-parse.c` @ 6de20f6092 `:856-864`、`:1153-1192`；探针 #3–#6），只放开 `--short` 会让两个单修订模式对同一输入给出不同结论。在共享解析器中加选项：解析器本就不检查完整 ID 的存在性，加选项无意义且会把本计划拉进 `util.rs` 的行为改动。
- **Consequences:** 依赖旧行为把 `--verify` 当作存在性检查的脚本会放行不存在的 ID；文档与兼容矩阵写明替代写法（风险登记）。`COMPATIBILITY.md:217` 中「`--verify` proves the resolved object exists」删除。
- **Revisit when:** 无。

### ADR-RP-03：`--short` 的缩写判据按 Git `find_unique_abbrev`

- **Status:** Accepted
- **Context:** Git 的缩写从请求长度起，若有现存对象与目标共享更长前缀，就延长到「共享长度 + 1」，目标是否存在不影响计算（探针 #10–#11）。Libra 的判据要求命中恰为目标本身（`rev_parse.rs:892`），不存在的目标永远不满足。
- **Decision:**
  - 在 `resolve_short_commit` 内把判据改为「该长度下所有命中都等于目标（含零命中）」，起始长度（请求值，缺省 7）与上限（hex 长度）不变；不新增函数。已存在的目标在任何长度下的结果与今天相同（命中集合只含目标本身时两种判据等价，含重复项时新判据同样成立）。
  - 新判据把「零命中」当作唯一，因此查询必须是完整的：前缀查询由 `storage.search_result(prefix)` 改为 `storage.search_checked(prefix)`（`ClientStorage` 既有的 `pub async fn`，目录、条目或 pack 索引读取失败返回错误，`NotFound` 才视为空；`am` 已用它）。读取失败沿用 `resolve_short_commit` 既有的 `IoReadFailed` 构造，再经单修订模式既有的改写（`rev_parse.rs:311-331`）报告为 `fatal: Needed a single revision (could not resolve '<spec>')`、`LBR-CLI-003`、128；全局 `--quiet` 下静默退出 1。该改写掩盖底层错误类别是既有行为，与 `--short=abc` 的掩盖同源，登记 DEFER-RP-01。
  - `--short` 对已存在对象的路径同样改用 `search_checked`：今天读取失败时会退到输出完整 ID，改后以上述错误失败。这是 Libra 有意更严格的失败策略：Git @ 6de20f6092 的松散对象枚举（`odb/source-loose.c:51-58` 丢弃 `for_each_file_in_obj_subdir()` 的错误）在目录枚举失败后仍会继续算出缩写，Libra 不跟随这一点，以免输出被遮蔽对象冲突的缩写。
- **Alternatives considered:** 改用 `util::find_unique_abbrev_typed`：其为私有、起始长度固定为 7，复用需改 `util.rs` 的签名，与 DEP-RP-02 的写者冲突；登记 DEFER-RP-06。
- **Consequences:** `--short=<n>` 的长度规范化（`n < 4`、非数字、重复）仍为现状（DEFER-RP-01）。新增一条可达的失败路径（前缀查询读取失败），按 GC-RP-05 展开为 8 个门。共享解析器 `resolve_hash_atom_typed` 的前缀查询同样吞掉读取失败（探针 #27），不在本计划（DEFER-RP-07）。
- **Revisit when:** DEFER-RP-01 或 DEFER-RP-06 重启。

### ADR-RP-04：退出码契约表的 `rev-parse` MissingObject 行改用 `^{object}`

- **Status:** Accepted
- **Context:** `plumbing_exit_contract_test` 要求每个 plumbing 命令有 MissingObject 行或 N/A 登记（`:767-787`）；现行行 `rev-parse --verify 1111…1` 期望 128（`:325-332`），与 ADR-RP-02 相反。Git 对 `--verify <不存在的 ID>^{object}` 退出 128（探针 #12）。
- **Decision:** 该行的参数改为 `["rev-parse", "--verify", "1111…1^{object}"]`，标签改为 `rev-parse --verify absent object ^{object}`，期望不变（128、`LBR-CLI-003`）。其余行不动。
- **Alternatives considered:** 把 `rev-parse` 的 MissingObject 登记为 N/A：Git 有明确的缺失对象失败形式，登记 N/A 会削弱契约。
- **Consequences:** `plumbing_exit_codes_json_matches_human` 与 `plumbing_exit_codes_are_deterministic` 同时覆盖新行。
- **Revisit when:** 无。

### ADR-RP-05：期望值来源

- **Status:** Accepted
- **Context:** CI 有 `git`，但版本不固定；本计划的期望值都与对象内容无关的提交时间无关（夹具不提交）。
- **Decision:** `command_test` 用例的期望字节写成测试内字面量，来源是本计划「行为探针」表；测试运行时不调用 Git。夹具不创建提交，对象集完全确定（探针 #24），避免随机提交 ID 与 `4e7f` 前缀碰撞。
- **Alternatives considered:** 在有提交的仓库中测试：提交 ID 随时间变化，`--short=4` 的期望可能因偶然碰撞而波动。
- **Consequences:** Git 改变上述输出时需人工更新字面量。
- **Revisit when:** Git 改变任一输出。

      echo "FAIL: forbidden pattern found"; return 1
    else
      rc=$?

    fi

  - **拒绝门族（新可达的失败路径）：** 本计划只新增一条可达的失败路径（`--short` 的前缀查询读取失败，ADR-RP-03）。它按下列 8 个门展开，门名为 `<拒绝 ID>__<后缀>`，每个门在新建的夹具中运行一次被测 argv（`__json`、`__machine_*` 在 argv 前插入对应全局参数后另建夹具重跑）。通道见 Libra 的既有错误渲染与 `rev-parse` 的既有静默合同：人读模式 stdout 为空，stderr 为 `fatal: <msg>`、`Error-Code: <码>`、紧凑 JSON 行；`--json` 为 stderr 上的美化 JSON；`--machine` 隐含 `--quiet`（`src/utils/output.rs:170-182`），单修订模式在 quiet 下以 `CliError::silent_exit(1)` 静默退出（`rev_parse.rs:318-321`；2026-11-04 探针：`libra --machine rev-parse --verify nope` 退出 1，stdout 与 stderr 均为 0 字节），本计划保留该合同：
    - `__msg`：stderr 第 1 行等于 `fatal: <msg>`；
    - `__code`：stderr 第 2 行等于 `Error-Code: LBR-CLI-003`；
    - `__exit`：退出码为 128；
