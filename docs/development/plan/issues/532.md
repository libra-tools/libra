## 文档职责

本文处理 Issue #532（及其吸收的 #998）在当前 `main` 上仍成立的 `libra pull` 与 Git 契约差异。目标：#532 正文与评论、#998 正文与评论中列出、且仍能复现的每一项，要么对齐 Git，要么显式归类为不支持并写进文档，要么登记为依赖其它 issue 的 DEP；同时给出被引用上游用例的复核方法。

新建或推进本计划时，必须在同一变更中更新 [`plan-status.md`](../plan-status.md)（状态、版本/提交、`YYYY-MM-DD HH:MM:SS UTC`）。

### 适用范围

- `libra pull` 的以下表面：
  - 显式 `<repository> <refspec>` 下 rebase 的目标解析（#998 第二项）；
  - 集成方式的选择：`--rebase`/`--no-rebase` 与 `--ff`/`--no-ff`/`--ff-only` 的优先级、`--ff`/`--no-ff`/`--ff-only` 之间最后者生效、`pull.rebase`/`branch.<name>.rebase`/`pull.ff` 与命令行参数的优先级、`--squash`/`--no-commit`/`--commit` 在 rebase 模式下的处理；
  - `--rebase[=<mode>]`/`-r[=<mode>]` 的取值文法，以及 `interactive`/`i` 模式；
  - 未出生分支上的 rebase 模式拉取，以及「索引已有暂存内容」时的拒绝；
  - 人读输出通道（fetch 报告与 rebase 完成摘要走 stderr，merge 摘要走 stdout，首次拉取不打印 merge 摘要）；
  - `-v`/`--verbose` 与 `-q`/`--quiet` 的顺序语义；
  - `--log[=<n>]`/`--no-log` 与 `merge.log`；
  - `--verify-signatures`/`--no-verify-signatures` 与 `merge.verifySignatures`，以及 rebase 模式下的警告；
  - 匿名仓库参数（本地路径、`file://`）不带 refspec 时取远端 `HEAD`；
  - 分离 HEAD 上的 merge 模式拉取与无目标时的 Git 式提示；
  - merge 快进路径向 stdout 泄漏的 `Updated <n> path(s) from HEAD` 行（`libra merge` 与 `libra pull` 共用）。
- 对应文档：`docs/commands/pull.md`、`docs/commands/zh-CN/pull.md`、由同步脚本生成的网站页 `../libra-backend/apps/tanstack-app/content/docs/commands/pull.en.md`、开发文档 `docs/development/commands/pull.md`，以及 `COMPATIBILITY.md` 第 225 行 `pull` 行（原地改写，不增删行）。
- 测试：`tests/command/pull_test.rs`（`command_test` 目标，模块路径 `command::pull_test`）、`tests/compat/pull_strategy_flags_surface.rs`、`tests/compat/config_defaults_semantics_test.rs`、`tests/compat/config_defaults_edge_cases_test.rs`；PL-12 另含 `tests/command/merge_test.rs`。

### 成功定义

- #532 与 #998 中仍能复现、且不依赖其它 issue 的各项全部按 Git 处理：
  - `pull --rebase . side`、`pull --rebase <path> <branch>` 正常 rebase；
  - `--ff-only` 不论顺序压过 `--rebase`；`--rebase` 压过 `--ff`/`--no-ff`；`--ff`/`--no-ff`/`--ff-only` 最后者生效；`pull.rebase=true` 压过 `--ff`/`--no-ff`；命令行的 `--rebase`/`--no-rebase` 压过 `pull.ff=only`；
  - `--rebase=<mode>` 接受 Git 的布尔值与 `interactive`/`i`，`merges`/`m` 显式拒绝为不支持；
  - 未出生分支上的 `--rebase` 拉取成功；索引已有暂存内容时按 Git 文案拒绝；
  - fetch 报告走 stderr，首次拉取不在 stdout 打印任何内容；
  - `-v`/`--verbose` 可用，且与 `-q` 按 Git 的顺序规则组合；
  - `--log[=<n>]`/`--no-log`、`merge.log` 生效；
  - `--verify-signatures`/`--no-verify-signatures`、`merge.verifySignatures` 生效，rebase 模式下给出 Git 的警告；
  - 匿名仓库不带 refspec 时取远端 `HEAD`；
  - 分离 HEAD 上 merge 模式拉取成功，无目标时给出 Git 式提示。
- 每项行为都有 `command_test` 或 compat 目标中的具名用例；期望值取自本计划「行为探针」表（ADR-PL-10）。
- EN、zh-CN、网站页、开发文档与 `COMPATIBILITY.md` 第 225 行与实现一致，`--help` 文案同步。
- 十四张实现卡各自完成独立发布切片（ER-08），全部卡 `done` / `complete`，计划收口点 CLOSE-532 全绿。

### ADR-PL-02：集成方式的选择算法按 Git `builtin/pull.c`

- **Status:** Accepted
- **Context:** Git 的规则（`builtin/pull.c:1048-1068`、`:1146-1176`，钉住树 `6de20f6092`）：
  1. 命令行 `--rebase[=…]`/`--no-rebase` 最后者生效，得到 `opt_rebase`（未给则「未指定」）；`--ff`/`--no-ff`/`--ff-only` 最后者生效，得到 `opt_ff`（未给则「未指定」）。
  2. `opt_ff` 未指定时取 `pull.ff`；若此时 `opt_rebase` 来自命令行（任何值，包括 `--no-rebase`）且 `pull.ff=only`，则改为 `--ff`。
  3. `opt_rebase` 未指定时取 `branch.<name>.rebase`、`pull.rebase`，默认 false。
  4. `opt_ff` 为 `--ff-only` 时：历史分叉则拒绝；否则强制 merge 模式（快进）。
  5. 其余情况：rebase 模式只看 `opt_rebase`，`--ff`/`--no-ff` 与 `--squash`/`--no-commit`/`--commit` 对 rebase 不起作用；merge 模式按 `opt_ff` 与 merge 专用旗标执行。
  6. 分叉且两者都未指定时拒绝（`Need to specify how to reconcile divergent branches.`）。
- **Decision:** `resolve_effective_pull_options` 按第 1–5 步重写（PL-02 实现第 1、4、5 步中与命令行相关的部分，PL-03 实现第 2、3 步与 merge 专用旗标）。第 4 步的「分叉」判定不在 pull 层重复计算：`--ff-only` 生效时把模式定为 merge 并传 `ff_only=true`，由 merge 现有的快进检查拒绝（拒绝文案归 #1002）。「请求的 rebase」（第 3 步之后、第 4 步 `--ff-only` 折叠之前的值）与「实际分派」分开保存：请求 rebase 时，fetch 之前先做 Git 的 rebase 预检（`builtin/pull.c:1079-1089`）：未出生分支且索引非空则拒绝（PL-05）；否则未给 `--autostash` 时工作树或索引有已跟踪改动即拒绝（PL-15）——即使随后 `--ff-only` 把分派折叠为 merge 也照样预检。第 5 步中 Git 的「rebase 模式且可快进时改跑 `merge --ff-only`」（`builtin/pull.c:1172-1176`）照做（PL-15）：fetch 之后、调用 rebase 之前，用 `crate::internal::merge_base::is_ancestor(HEAD, 目标)`（`src/internal/merge_base.rs:555`）判定，可快进（含已最新）时走 merge 路径并传 `ff_only=true`，同时把 `--squash`/`--no-commit`/`--commit` 原样传给 merge（Git 在 `run_merge` 中转发它们，`--squash` 因此只暂存不移动 HEAD），该路径也执行 merge 的签名校验（ADR-PL-09）与快进输出，JSON 输出 `merge` 对象而不再是 `rebase.status = "fast-forwarded"`；不可快进时（分叉，或上游是 HEAD 的真祖先即本地领先，`builtin/pull.c:1146-1177`）才调用 rebase，此时 merge 专用旗标被忽略；本地领先时 rebase 为空操作（`rebase.status = "already-up-to-date"`）。第 6 步不实现（DEFER-PL-02）。
- **Alternatives considered:** 保留 clap 冲突、只放开个别组合：顺序相关的组合（`--ff-only --rebase` 与 `--rebase --ff-only`）无法用静态冲突表达。
- **Consequences:** `--squash --rebase` 等组合从「拒绝」变为「真正 rebase 时忽略、可快进时转给 merge」，与 Git 一致；rebase 模式下可快进或已最新的拉取在 JSON 中由 `rebase` 对象改为 `merge` 对象（2026-11-04 核对：没有断言 `fast-forwarded` 的用例；`tests/command/pull_test.rs:1165` 的 `test_pull_rebase_already_up_to_date_reports_noop` 断言已最新时的 `rebase` 对象，由 PL-15 改为断言 `merge.up_to_date`）；请求 rebase 时脏工作树在 fetch 前即被拒绝（此前只有需要重放时才在 rebase 阶段拒绝）；文档写明。`resolved_pull_mode`（测试用）同步。
- **Revisit when:** 决定实现第 6 步时。

### ADR-PL-03：`--rebase[=<mode>]` 的取值文法

- **Status:** Accepted
- **Context:** Git 用 `PARSE_OPT_OPTARG` 解析 `--rebase`/`-r`（`builtin/pull.c:890-893`）：长选项的值必须用 `=` 紧贴，短选项取同一记号的剩余部分（`parse-options.c:432`）；取值规则见 `rebase.c` 的 `rebase_parse_value`：先按 Git 布尔解析（大小写不敏感，空串为 false），再精确匹配 `merges`/`m`、`interactive`/`i`；`preserve`/`p` 先报一行 `'preserve' superseded by 'merges'`，与其它值一样以 `invalid value for '--rebase': '<值>'` 失败，退出 129，发生在 fetch 之前（探针 #16、#17）。
- **Decision:**
  - 长选项 `--rebase` 改为可选值参数：`num_args = 0..=1`、`require_equals = true`、`default_missing_value = "true"`，与 `--no-rebase` 互为最后者生效；裸 `--rebase` 不吞下一个位置参数。
  - 短选项 `-r` 按 Git 的短选项可选值规则（`parse-options.c` 中 `PARSE_OPT_OPTARG` 的短选项取同一记号的剩余部分为值）：`-r` 单独出现时无值；`-r<剩余>`（如 `-ri`、`-rtrue`、`-rv`）把剩余部分整体作为值（`-rv` 因此是非法值 `v`，不是 `-r -v`）；捆绑记号中 `r` 之前只能是本命令的无值短选项 `q`、`v`，`r` 之后的剩余部分同样是值（`-qri` 为 `-q` 加值 `i`）。实现为 `src/cli.rs` argv 改写链中的 `rewrite_pull_args`（PL-04 新增，只在子命令为 `pull`、只扫描 `--` 之前的记号）：把上述记号改写为 `--rebase` 或 `--rebase=<剩余>`，`q`/`v` 原样保留为独立记号，交给 PL-07 处理顺序。
  - 新增一个解析函数，供命令行值与 `branch.<name>.rebase`/`pull.rebase` 共用，返回 `False`/`True`/`Merges`/`Interactive`/`Invalid`。
  - 命令行 `Invalid`（含 `preserve`/`p`）：U 型拒绝，消息 `invalid value for '--rebase': '<值>'`。不复刻 `preserve` 的前置说明行（有意差异，写入文档）。
  - 命令行 `Merges`：X 型拒绝（DEFER-PL-05）。
  - 命令行 `Interactive`：PL-04 先按 X 型拒绝，PL-13 接通交互 rebase 后改为支持。
  - 配置值的拒绝合同不变（现有 `bad config value …`/`unsupported config value …`，`LBR-CLI-002`）：共用解析器带「来源」参数，配置值为空串时仍按现有合同拒绝（`tests/compat/config_defaults_semantics_test.rs:541` 的 `pull_rebase_empty_config_is_usage_error_before_fetch` 不变），只有命令行 `--rebase=` 的空值按 Git 视为 false；只在 PL-13 把配置的 `interactive`/`i` 改为支持。
- **Alternatives considered:** 用 clap 的 `value_parser` 枚举：clap 的报错文案与 Git 不同，且无法与配置共用。
- **Consequences:** `merges`/`interactive` 改为大小写敏感（与 Git 一致），配置中 `Merges` 从「不支持」变为「无效值」，两者都是 `LBR-CLI-002`，退出码不变。
- **Revisit when:** 实现 rebase-merges 时。

### ADR-PL-04：拒绝的构造与退出码

- **Status:** Accepted
- **Context:** Git 的参数错误多为 `error:` 加 129；状态错误为 `fatal:` 加 128；无目标的提示块为无前缀加 1。Libra 的退出码由稳定码决定（`src/utils/error.rs:1038-1046`）。
- **Decision:** 本计划新增的失败路径只用 GC-PL-05 列出的六种类型。退出码与 Git 不同的地方（无目标提示块 Git 为 1、Libra 为 128；fetch 后才失败的 `--log=x` Libra 在 fetch 前失败）写入文档错误表。
- **Alternatives considered:** 用 `with_exit_code` 覆盖为 Git 的 1：扩大错误码合同的例外面；`issues/480.md` ADR-HP-02 已对同类情况保留 Libra 退出码。
- **Consequences:** 比较整个 stderr 的上游用例仍会因 `Error-Code:` 行失败，这是全局合同。
- **Revisit when:** 全局错误输出合同变化。

### ADR-PL-05：人读输出通道

- **Status:** Accepted
- **Context:** Git 的 `pull` 把 fetch 报告（`From …` 与 ref 行）与 rebase 进度、完成提示写 stderr，把 merge 摘要（`Updating …`、`Fast-forward`、`Merge made by …`、diffstat、`Already up to date.`）写 stdout；首次拉取到未出生分支（`pull_into_void`）不写 merge 摘要（探针 #3、#41）。
- **Decision:** `render_pull_output` 改为：`From <url>` 与 ref 更新行写 stderr；rebase 的 `completed` 摘要写 stderr；merge 摘要与 rebase 的 `fast-forwarded`/已最新摘要仍写 stdout；`merge.old_commit` 为 `null` 时不写任何 merge 摘要。各行文字不变（DEFER-PL-08）。`--quiet`、`--json`、`--machine` 的行为不变。hook 的输出不经过 `render_pull_output`，不受影响（探针 #41）。
- **Alternatives considered:** 同时把文字改成 Git 的（`* branch side -> FETCH_HEAD`、`Successfully rebased and updated refs/heads/main.`）：牵涉 fetch 的报告格式与 #976，另立。
- **Consequences:** 脚本若从 stdout 读 `From` 行需改读 stderr；文档写明。
- **Revisit when:** fetch 报告格式另立计划对齐时。

### ADR-PL-06：`-v` 与 `-q` 的顺序

- **Status:** Accepted
- **Context:** Git 的 `OPT__VERBOSITY`：`-v` 在当前值为负时置 1，否则加 1；`-q` 在当前值为正时置 −1，否则减 1；最终值小于 0 为静默，大于 0 为详细（探针 #6、#7）。Libra 的 `-q` 是全局布尔旗标，clap 不保留它与子命令参数的相对顺序（`src/cli.rs:285-286`）。
- **Decision:** 在 `parse_async_scoped` 已有的 argv 改写链中扩展 PL-04 新增的 `rewrite_pull_args`：仅当子命令为 `pull` 时，按出现顺序扫描 `pull` 之前的全局 `-q`/`--quiet` 与 `pull` 之后、`--` 之前的 `-q`、`--quiet`、`-v`、`--verbose`，以及短选项捆绑中位于 `r` 之前的 `q`、`v` 字符（`r` 及其后的剩余部分按 ADR-PL-03 作为 rebase 值处理），按 Git 规则算出最终值；然后删除这些记号，最终值小于 0 时补一个 `--quiet`，大于 0 时补一个 `--verbose`。`-v`/`--verbose` 是 `PullArgs` 新增的公开选项（`ArgAction::Count`，出现在 `--help`）。其余子命令的 argv 不变。Libra 在详细级别下的输出与默认级别相同（不打印 Git 的 `= [up to date]` 行，DEFER-PL-10）。
- **Alternatives considered:** 在 `PullArgs` 声明 `-q`：与全局 `-q` 重名，clap 构建失败。用 `ArgMatches::index_of`：需要把 derive 解析改为手工取 matches，改动面更大。
- **Consequences:** 改 `src/cli.rs` 的 argv 预处理，命中 ER-13 `T-1`。
- **Revisit when:** 全局 `-q` 改为计数型时。

### ADR-PL-07：匿名仓库不带 refspec 时取远端 `HEAD`

- **Status:** Accepted
- **Context:** Git 对非配置远端（路径、URL）且不带 refspec 的 `pull`，取远端 `HEAD`（符号引用或分离 OID）写入 FETCH_HEAD 并合并（探针 #34–#36）。Libra 取当前分支名（`pull.rs:727-737`），分离 HEAD 时无名可取。Libra fetch 拒绝 `HEAD` 作为来源（探针 #37）。
- **Decision:** 在 `fetch.rs` 新增 `pub(crate) async fn fetch_remote_head_for_pull`：复用同一次 discovery，以广告中的 `HEAD` 为唯一来源，不写任何跟踪引用（计划的 `update_tracking=false`），返回 fetch 结果与 `HEAD` 的 OID；远端无 `HEAD` 时返回现有 `RemoteBranchNotFound`（`couldn't find remote ref HEAD`）。`pull` 对「匿名仓库、无 refspec」改用它，并以该 OID 作为 merge/rebase 目标；`upstream` 显示为 `<repository>/HEAD`。配置远端不带 refspec 的行为不变（DEFER-PL-07）。`libra fetch <path> HEAD` 的公开表面不变。
- **Alternatives considered:** 只解析符号 `HEAD` 指向的分支名：远端 `HEAD` 分离时仍无法拉取（t5573 的 `bad` 仓库正是如此）。
- **Consequences:** 在非默认分支上 `pull <path>` 的结果改变（拉取远端默认分支）；文档写明迁移方式（显式给 refspec）。
- **Revisit when:** #997/#976 改造 FETCH_HEAD 时，可改为统一经 FETCH_HEAD。

### ADR-PL-08：分离 HEAD

- **Status:** Accepted
- **Context:** Git 在分离 HEAD 上允许带目标的 merge 与 rebase；无目标（不带参数，或配置远端不带 refspec）时打印提示块并退出 1（探针 #38、#39）。Libra 的 merge 快进与三方合并路径已能更新分离 HEAD（`merge.rs:4757-4763`），但 rebase 拒绝分离 HEAD（探针 #40）。
- **Decision:**
  - merge 模式：带显式目标（`<repository> <refspec>`，或匿名仓库不带 refspec）时正常执行，HEAD 保持分离。
  - 无目标：A 型拒绝，提示块与 Git 相同，只把 `git pull` 换成 `libra pull`。
  - rebase 模式（`--ff-only` 生效时不算 rebase 模式）带显式目标：X 型拒绝（DEFER-PL-06）。
  - JSON 的 `branch` 字段在分离 HEAD 时为 `null`（成功时）；分支上不变。
- **Alternatives considered:** 分离 HEAD 上可快进时借 merge 快进完成 rebase：结果正确但模式与 JSON 对象不一致，留待 DEFER-PL-06 一并处理。
- **Consequences:** `PullOutput.branch` 改为 `Option<String>`（序列化在分支上不变）。
- **Revisit when:** `libra rebase` 支持分离 HEAD 时。

### ADR-PL-09：签名校验沿用 vault 模型

- **Status:** Accepted
- **Context:** Libra 的签名校验只对仓库 vault 密钥判定 Good/Unsigned/Bad（`commit.rs:3169-3177`）；默认提交带 vault 签名，`clone` 生成自己的 vault（探针 #32）。t5573 依赖 GPG 钥匙链：未签名提交、外部密钥的 bad/untrusted 签名、`gpg.minTrustLevel` 与 `has a good GPG signature` 输出。
- **Decision:** `pull` 暴露 `--verify-signatures`/`--no-verify-signatures`（最后者生效，未给时取 `merge.verifySignatures`），传给所有经 merge 的路径，包括 rebase 模式下可快进而改走 `merge --ff-only` 的情形（ADR-PL-02、PL-15，与 `builtin/pull.c:1172-1176` 一致，因此可快进的 `--rebase --verify-signatures` 同样会拒绝无签名或坏签名的目标）；只有真正执行 rebase 且命令行给了 `--verify-signatures` 时，以 `emit_warning` 输出 `ignoring --verify-signatures for rebase`（`builtin/pull.c:778-779`）。坏签名（Bad）与无签名（Unsigned）都是新可达的拒绝。签名失败沿用 merge 的错误与 `pull` 现有映射（`pull.rs:1288-1296`，加 `phase: merge`）。不实现信任级别与成功提示（DEFER-PL-01）。
- **Alternatives considered:** 引入 GPG 钥匙链：改变签名模型，超出 #532。
- **Consequences:** TC-2131–2136 在双轨下仍 FAIL（夹具中的「未签名」提交被克隆的 vault 签名，判定为 Bad；trust 级别无对应）；PL-14 如实归属到 DEFER-PL-01。TC-2138 只需旗标、配置覆盖与 PL-10/PL-11。
- **Revisit when:** Libra 引入外部签名信任配置时。

### ADR-PL-10：期望值来源

- **Status:** Accepted
- **Context:** CI 有 `git`，但版本不固定。
- **Decision:** `command_test` 用例的期望值写成测试内字面量，来源是本计划「行为探针」表与钉住的 Git 源码；不在运行时调用 Git。提交 OID 由测试夹具现场取得后比较。
- **Alternatives considered:** 运行时现场调用 Git：结果随版本漂移。
- **Consequences:** Git 行为变化时需人工更新字面量。
- **Revisit when:** Git 改变上述任一输出。

## 全局工程约束

本计划完整继承模板 GC-01..GC-13，另加以下约束：

- **GC-PL-01 单一事实源：** 集成方式只由 `resolve_effective_pull_options` 决定，测试用的 `resolved_pull_mode` 必须调用它而不是另写规则；`--rebase` 的取值与 `branch.<name>.rebase`/`pull.rebase` 共用 ADR-PL-03 的解析函数；merge、rebase、fetch 一律调用既有入口（`merge::run_merge_for_pull_with_options`、`rebase::run_rebase_for_pull` 及 PL-13 新增的交互入口、`fetch::fetch_repository_with_result` 及 PL-10 新增的 `HEAD` 入口），不在 `pull.rs` 复制它们的逻辑。`merge.log`、`merge.verifySignatures` 只经 `history_config` 读取。
- **GC-PL-02 零写入：** 不依赖远端数据的拒绝（GC-PL-05 的 U、X、S、A 型）必须在 fetch 之前、任何写入之前发生；fetch 之后的拒绝（R、M 型）不得改变 HEAD、`refs/heads/*`、索引与工作树（fetch 阶段已按既有行为写入的对象、远端跟踪引用与自动跟随的标签不在此列，与现有文档一致）。
- **GC-PL-03 零命中守卫：** Verification 中凡标「零命中」的命令，都在 `bash` 中先定义下列函数再调用。该函数按模板对 `rg` 退出码三分支判定（2026-11-04 在 `bash -e` 与 `zsh -e` 下验证三条分支）：

  ```bash
  zero_hits() {
    pattern="$1"; shift
    if rg -n -- "$pattern" "$@"; then
      echo "FAIL: forbidden pattern found"; return 1
    else
      rc=$?
      if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; return "$rc"; fi
      echo "OK: zero hits"
    fi
  }
  ```

- **GC-PL-04 测试隔离与夹具：**
  - 新用例全部用 `tempdir()` 仓库与显式 cwd，经子进程运行构建产物 `libra`；环境变量只给子进程设置，不改测试进程环境，因此不需要 `#[serial(env)]`。
  - 子进程的 `HOME`、`XDG_CONFIG_HOME`、`LIBRA_CONFIG_GLOBAL_DB`、`LIBRA_CONFIG_SYSTEM_DB` 指向该用例的临时目录（GC-13）；`GIT_EDITOR`、`VISUAL`、`GIT_SEQUENCE_EDITOR`、`EDITOR` 一律先清除，只按用例需要设置。
  - 夹具（PL-01 在 `tests/command/pull_test.rs` 新增 F1–F3 的构造函数，后续卡复用；F4 由 PL-08、F5 由 PL-09 在卡内定义并新增；卡内可在基础夹具上追加前置步骤，如「上游再前进一个提交」）：
    - **F1**：`c0`（`c0.c`）→ `side` 上 `c1`（`c1.c`）；`main` 上 `c2`（`c2.c`）；「从 c0」为 `main` 先 `reset --hard c0`，「从 c2」为 `main` 在 `c2`。仓库自身作为远端（`.`）。
    - **F2**：上游 `up`（`main` 上两个提交，另有分支 `feat` 在第一个提交上再加一个提交）与下游 `d`（`init` 后 `pull --no-rebase ../up main`，再 `remote add origin ../up`、`fetch origin` 并 `branch -u origin/main`）。
    - **F3**：只含一个提交的上游 `parent` 与刚 `init` 的空仓库。
    - **F4**：`main` 上 `initial`（`afile=original`）→ `add bfile`；`side` 自 `initial` 起有 `second commit`、`do not clobber $Dollar signs` 两个提交（与 t5524 同构）。
  - 「pull 渲染行」指 stdout 中除去整行匹配 `^Updated [0-9]+ path\(s\) from HEAD$` 以外的行（该行来自 merge 的恢复报告，PL-12 移除）。
- **GC-PL-05 拒绝门族：** 本计划每条新增或新可达的失败路径都按下表展开成一组门。每个门是一个独立命名的测试函数，只断言一个谓词，计入所在卡的 G-03 分子（由 EX-PL-01 承载超限）。测试函数由 PL-01 在 `tests/command/pull_test.rs` 新增的宏 `pull_refusal_gates!` 与状态快照 helper 生成（PL-01 是第一张含拒绝门的卡），命名为 `<卡前缀>_<拒绝名>__<后缀>`，完整路径 `command::pull_test::<名>`（`tests/command_test.rs` 以 `mod command` 挂载），单独运行一律用 `source .env.test && cargo nextest run --test command_test --no-tests=fail -E 'test(=command::pull_test::<名>)'`（零匹配即失败；不用 `cargo test … -- --exact`，后者名字不全时匹配 0 个用例仍退出 0）。三种输出模式的通道已于 2026-11-04 探针确认（探针 #45–#47）：人读模式 stderr 先是人读行，再是 `Error-Code:` 行，有提示时空一行后是 `Hint:` 行；`--json` 在 stderr 输出美化 JSON；`--machine` 在 stderr 输出单行 JSON；三种模式 stdout 都为空。
  - **状态快照**（`__state`、`__state_sentinel` 门用）：依次取 `libra rev-parse HEAD` 的 stdout 与退出码、`libra symbolic-ref HEAD` 的 stdout 与退出码、`libra show-ref` 的 stdout（U/X/S/A 型发生在 fetch 之前，取全部引用；R/M 型发生在 fetch 之后，只取 `libra show-ref --heads`——fetch 阶段按既有行为可能更新远端跟踪引用并自动跟随标签，这些属于 fetch 阶段的合法写入，不在 integration 阶段零写入的范围内；R/M 型夹具的上游在被拉取的提交上带一个轻量标签 `t-up`，以证明快照确实排除了这类写入）、`libra ls-files --stage` 的 stdout，以及工作树（不含 `.libra`）全部文件的相对路径与内容 SHA-256 的有序列表；执行被测命令前后各取一次，比较相等。
  - **未 fetch 见证（`__no_fetch`）：** 对 argv 为「匿名仓库、不带 refspec」的 fetch 前拒绝（PL-10 起此形式不写跟踪引用，快照无法发现提前 fetch），另加 `__no_fetch` 门：上游有一个下游没有的提交 `T`，拒绝后 `libra cat-file -e <T>` 在下游以非 0 退出。卡内另设一个负向对照门：同一夹具去掉拒绝条件后执行同一 argv，`libra cat-file -e <T>` 退出 0。
  - **两种夹具状态（U/X/S/A/D 型）：** `__state` 在「该 argv 会用到的远端跟踪引用不存在」的状态下执行；`__state_sentinel` 在执行前先把该跟踪引用（匿名仓库为 `refs/remotes/<匿名名>/<分支>`，配置远端为 `refs/remotes/origin/<分支>`）预先建立并记录其值（做法：先以同一仓库参数与同一分支做一次成功的 `libra fetch`；`libra update-ref` 只支持 `refs/heads/*`，不用它），断言执行后快照（含该引用的值）不变。argv 在两种状态下逐字相同。无远端引用可言的 argv（如分离 HEAD 不带参数）只有 `__state`，`__state_sentinel` 改为预置一个内容为 `sentinel` 的未跟踪文件 `pl-sentinel.txt` 并断言其内容不变。
  - **U 型（用法拒绝）：** `CliError::command_usage(msg)`（稳定码 `LBR-CLI-002`）。9 个门：`__msg`（stderr 第 1 行等于 `error: <msg>`）、`__code`（stderr 第 2 行等于 `Error-Code: LBR-CLI-002`）、`__exit`（退出码 129）、`__stdout`（stdout 为 0 字节）、`__state`、`__state_sentinel`（见上两条）、`__json`（以 `--json` 重跑，stderr 解析出的对象等于 `{"ok":false,"error_code":"LBR-CLI-002","category":"cli","exit_code":129,"severity":"error","message":<msg>}`）、`__machine_lines`（以 `--machine` 重跑，stderr 恰为一行）、`__machine_json`（同一次 `--machine` 运行，该行解析出的对象与 `__json` 的期望相等）。
  - **X 型（显式不支持）：** `CliError::failure(msg).with_stable_code(StableErrorCode::Unsupported).with_hint(hint)`。10 个门：同 U 型的 9 个，但 `__msg` 期望 `error: <msg>`、`__code` 期望 `Error-Code: LBR-UNSUPPORTED-001`、`__exit` 期望 128、JSON 期望 `{"ok":false,"error_code":"LBR-UNSUPPORTED-001","category":"internal","exit_code":128,"severity":"error","message":<msg>,"hints":[<hint>]}`；另加 `__hint`（stderr 恰有一行等于 `Hint: <hint>`）。
  - **S 型（状态拒绝）：** `CliError::fatal(msg).with_stable_code(StableErrorCode::RepoStateInvalid)`。9 个门：同 U 型，但 `__msg` 期望 `fatal: <msg>`、`__code` 期望 `Error-Code: LBR-REPO-003`、`__exit` 期望 128、JSON 期望 `{"ok":false,"error_code":"LBR-REPO-003","category":"repo","exit_code":128,"severity":"fatal","message":<msg>}`。
  - **D 型（带提示的状态拒绝）：** `CliError::failure(msg).with_stable_code(StableErrorCode::RepoStateInvalid).with_hint(hint)`。10 个门：同 X 型的 10 个，但 `__code` 期望 `Error-Code: LBR-REPO-003`、`__exit` 期望 128、JSON 期望 `{"ok":false,"error_code":"LBR-REPO-003","category":"repo","exit_code":128,"severity":"error","message":<msg>,"hints":[<hint>]}`。
  - **A 型（无前缀提示块）：** `CliError::unprefixed_failure(block).with_stable_code(StableErrorCode::RepoStateInvalid)`。9 个门：同 U 型，但 `__msg` 期望 stderr 中 `Error-Code:` 行之前的全部行依次等于 `block` 按换行切分后的各行、`__code` 期望 `Error-Code: LBR-REPO-003`、`__exit` 期望 128、JSON 期望 `{"ok":false,"error_code":"LBR-REPO-003","category":"repo","exit_code":128,"severity":"error","message":<block>}`（与探针 #45 同形）。
  - **M 型（merge 阶段签名拒绝，复用 `pull.rs:1288-1296` 的映射）：** 8 个门：同 U 型（发生在 fetch 之后，无 `__state_sentinel`），但 `__msg` 期望 `error: <msg>`、`__code` 期望 `Error-Code: LBR-REPO-003`、`__exit` 期望 128、JSON 期望 `{"ok":false,"error_code":"LBR-REPO-003","category":"repo","exit_code":128,"severity":"error","message":<msg>,"details":{"phase":"merge"}}`。
  - **R 型（新可达、但文案与稳定码归其它组件的既有拒绝）：** 4 个门：`__code`（stderr 中恰有一行等于 `Error-Code: <卡内给定码>`）、`__exit`（卡内给定退出码）、`__stdout`（0 字节）、`__state`（快照不变）。不断言文案（由所属组件或 DEP 承接）。卡内可为某条 R 型拒绝追加额外后缀（如 `__editor_ran`、`__abort_restores`），或在拒绝本身预期会留下状态（如 rebase 冲突）时以卡内声明的后缀替换 `__state`/`__stdout`；追加与替换都在卡内判据规范逐条写明，并计入分子。
  - **C 型（merge 阶段读取的配置无效或读取失败，复用 `pull.rs:1249-1255` 的既有映射）：** 无效值为 `CliError::command_usage(<history_config 原文>)`（`LBR-CLI-002`，129），读取失败为 `CliError::fatal(..)`（`LBR-IO-001`，128）；与 Git 一致，只在将要执行 merge 时（含 rebase 模式改走 merge 快进）读取并判定，命令行的覆盖旗标不豁免无效值（2026-11-04 探针：`git pull --no-rebase --no-log . side` 在 `merge.log=bogus` 时 128 `fatal: bad numeric config value …`；`--no-verify-signatures` 同理；真正 rebase 时不读）。门为 R 型 4 门加 `__msg`（无效值）；读取失败用 debug 构建专用的故障注入（沿用 `src/command/tag.rs:889-902` 的 `LIBRA_TEST=1` 加 `LIBRA_TEST_<CMD>_FAIL_…` 写法）：`LIBRA_TEST=1` 且 `LIBRA_TEST_PULL_FAIL_CONFIG_READ=<键>` 时，pull 在 merge 阶段读取该键的位置返回 `HistoryConfigError::Read { key, detail: "injected failpoint" }`，release 构建无此路径；门为 `__code`（`LBR-IO-001`）、`__exit`（128）与 `__msg`（stderr 第 1 行等于 `fatal: failed to read config '<键>': injected failpoint`，证明注入点确在新读取处），另设对照门：把变量设为无关键 `unused.key` 时同一 argv 成功（证明注入只命中指定键，且执行确实到达该读取点之后）。

    ```bash
    source .env.test
    gates_u() { for id in "$@"; do for x in msg code exit stdout state state_sentinel json machine_lines machine_json; do echo "${id}__${x}"; done; done; }
    gates_x() { for id in "$@"; do for x in msg code exit stdout state state_sentinel json machine_lines machine_json hint; do echo "${id}__${x}"; done; done; }
    gates_m() { for id in "$@"; do for x in msg code exit stdout state json machine_lines machine_json; do echo "${id}__${x}"; done; done; }
    gates_r() { for id in "$@"; do for x in code exit stdout state; do echo "${id}__${x}"; done; done; }
    gate_set() {
      local prefix="$1"; shift
      test "$#" -gt 0
      local listing actual expected
      listing="$(cargo test --test command_test -- --list "command::pull_test::${prefix}")"
      actual="$(printf '%s\n' "$listing" | sed -n 's/: test$//p' | sort)"
      expected="$(printf 'command::pull_test::%s\n' "$@" | sort)"
      test -n "$actual"
      test "$actual" = "$expected"
    ```

#### Verification 判定口径

- 「零命中」命令一律经 GC-PL-03 的 `zero_hits` 函数执行。
- 单个用例一律用 `source .env.test && cargo nextest run --test command_test --no-tests=fail -E 'test(=command::pull_test::<名>)'`（零匹配即失败）；一张卡的全部门用 `-E 'test(/^command::pull_test::<卡前缀>_/)'` 一次运行，并以 GC-PL-05「门集合核对」证明门集合恰为判据规范所列。
