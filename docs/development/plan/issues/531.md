## 文档职责

本文处理 #531 在当前 `main` 上仍能复现的 `push` 与 Git 契约差异。目标：#531 正文与评论列出、且仍能复现的每一项，要么对齐 Git，要么显式归类为不支持或有意差异并写进文档；正文场景 1 中已经不再是「`remote … not found`」、而是其它根因的上游用例，逐条转归到对应 issue。

新建或推进本计划时，必须在同一变更中更新 [`plan-status.md`](../plan-status.md)（状态、版本/提交、`YYYY-MM-DD HH:MM:SS UTC`）。

### 适用范围

- `libra push` 的以下表面：
  - 仓库参数为「未配置为远端、但在磁盘上存在」的裸名（如 `dst`、`remote-1`）时，按本地路径解析（#531 场景 1；同轴吸收 [#710](https://github.com/libra-tools/libra/issues/710)）；
  - 新增 `--all` 与其别名 `--branches`：推送全部本地分支，并带上 Git 的四选项互斥（`--delete`/`--tags`/`--all`/`--mirror`）与「`--all` 不能与 refspec 同用」（#531 场景 2、3）；
  - `-u`/`--set-upstream` 与 `--all` 同用：为每个被推送的分支设置上游，且此时可以省略仓库参数（TC-2245）；
  - Git 语法的布尔 `--progress`：强制输出 Git 风格的 `Writing objects` 行，与 `--no-progress` 按最后出现者生效（TC-2249）。自动模式（含终端，TC-2247）不改，属 DEFER-PS-07。
- 对应文档：`docs/commands/push.md`、`docs/commands/zh-CN/push.md`、由同步脚本生成的网站页 `$WEB/apps/tanstack-app/content/docs/commands/push.en.md`、开发文档 `docs/development/commands/push.md`，以及 `COMPATIBILITY.md` 第 222 行 `push` 行（原地改写，不增删行）。
- 测试：`tests/command/push_test.rs`（`command_test` 目标）、`src/internal/protocol/repository_arg.rs` 与 `src/cli.rs` 的单元测试。

### 非目标

- 未配置远端时的默认推送规则：`push <remote>` 不带 refspec、`remote.<name>.push`、`push.default`、`HEAD` 作为源、`-u :<ref>`。这些由 [#683](https://github.com/libra-tools/libra/issues/683) 承接（DEP-PS-01）；#531 正文场景 1 点名的 t5533 #21–#23（TC-2236/2237/2238）在 0.30.91 的真实根因就是 #683。
- `receive.denyCurrentBranch=warn`（[#1031](https://github.com/libra-tools/libra/issues/1031)）、`--force` 与 `--force-with-lease` 同用（[#1036](https://github.com/libra-tools/libra/issues/1036)）、`--prune` 与通配 refspec（[#877](https://github.com/libra-tools/libra/issues/877)）、`ext::`（[#1048](https://github.com/libra-tools/libra/issues/1048)）、全局 `-C`（[#686](https://github.com/libra-tools/libra/issues/686)）：只登记依赖（DEP-PS-02、DEP-PS-03），不在本计划修。
- `fetch`/`pull` 的同类裸名解析（DEFER-PS-01）；不存在的裸名改用 Git 的报错文案与退出码（DEFER-PS-02）。
- Git 的逐 ref 部分推送（同一次推送中快进的成功、非快进的拒绝、退出 1）：Libra 现有的多 ref 推送在发送前校验失败时整次不发送，发送后的失败不回滚，`--all` 沿用（DEFER-PS-03）。
- 匿名目标（路径/URL/裸名）的 `-u`，含其推送后失败的既有缺陷（DEFER-PS-09）。
- `--all` 在分离 HEAD、无任何本地分支、或仅有单个远端而未配置分支远端时的 Git 回退规则（DEFER-PS-04）。
- refspec 的 `+` 强制前缀与 `--signed=<值>`（TC-2256、TC-2257 仍受阻，DEFER-PS-05）。
- 不带仓库、也不带 `--all` 的 `push -u`（DEFER-PS-06）。
- Git 进度输出的完整还原（`Enumerating`/`Counting`/`Total` 行、百分比刷新、吞吐量；DEFER-PS-07）。
- 不含 `--all` 的既有互斥（`--delete --tags`、`--mirror --tags` 等）的报错文案改成 Git 原文（DEFER-PS-08）。
- 不改 Libra 全局错误输出合同（`Error-Code:` 行、非终端 stderr 末尾的 JSON 行、各稳定码的退出码）。
- 计划完成不以关闭 #531 或 #710 为条件；本计划只回复、不承诺关闭（DEP-PS-07）。

### 成功定义

- `libra push dst main`（`dst` 未配置为远端、但是本地仓库目录）推送成功；已配置的同名远端仍然优先。
- `--all`/`--branches` 推送全部本地分支；与 `--delete`/`--tags`/`--mirror`/refspec 同用时，按 Git 的文案拒绝，且两种拼写的输出逐字节相同。
- `push -u --all` 为每个被推送分支写上游配置，可省略仓库参数。
- `push --progress <repo> <ref>` 在非终端 stderr 上也输出 `Writing objects: 100% (<n>/<n>), done.`，与 `--no-progress` 按最后出现者生效；全局 `--progress <MODE>` 的既有写法不被破坏。
- 每项行为有 `command_test` 或单元测试中的具名门；EN、zh-CN、网站页、开发文档与 `COMPATIBILITY.md` 第 222 行与实现一致。
- 四张实现卡各自完成独立发布切片（ER-08），全部卡 `done` / `complete`，计划收口点 CLOSE-531 全绿。
- PS-05 已把 libra-testcases 维护者公开发布的复跑结果逐行写入本计划。

### ADR-PS-01：未配置的裸名在路径存在时按本地仓库解析（仅 `push`）

- **Status:** Accepted
- **Context:**
  - Git 的 `push <repo>`：先查已配置的远端或远端组；查不到就把参数整体当作 URL 或路径（`builtin/push.c:775-799` 的 `pushremote_get(repo)` 匿名远端），不要求 `./` 前缀（探针 #1）。已配置的同名远端优先（探针 #4）。
  - issues/480 ADR-HP-05 的决定是「相对路径（含 `.`、`..`）」都可作为匿名远端，但 HP-06 的实现只认带 `./`/`../` 前缀的写法，裸名 `dst` 因此落到 `RemoteNotFound`（`repository_arg.rs:17-31`）。这是该 ADR 的实现缺口。上游 t5534、t5583、t2027 都用裸名推送到本地目录。
  - `push` 现在把 `get_remote_url` 的任何 `Err`（含数据库读取失败）都当作「未配置」（`push.rs:958-973`）；若直接在此处加入「路径存在」的回退，配置读取失败时会把一个已配置的远端误导向同名本地目录。
  - 匿名目标推送后会写 `refs/remotes/<参数原文>/<b>` 行（探针 #32），`--force-with-lease` 的租约查询又会读这些行（`push.rs:1143`、`:1924-1960`）。Git 的匿名远端不写跟踪分支。
- **Decision:**
  - 在 `src/internal/protocol/repository_arg.rs` 新增 `pub fn is_existing_local_repository_arg(spec: &str) -> bool`，即 `Path::new(spec).exists()`（相对路径按进程 cwd 解析）。现有 `is_anonymous_repository_spec` 不改。
  - `push` 的仓库解析改用 `ConfigKv::remote_config`（`Result<Option<RemoteConfig>>`）：
    - `Ok(Some(cfg))` → 已配置远端（优先）；
    - `Err(e)` → 直接返回 `PushError::RepoState`（`fatal`、`LBR-REPO-002`、退出 128、提示 `try 'libra status' to verify repository state`），不做任何路径回退，也不做远端发现；
    - `Ok(None)` 时依次判定 `is_anonymous_repository_spec`、`is_existing_local_repository_arg`，命中者为匿名目标，都把原参数原样交给 `RemoteClient::from_spec_with_remote_and_confirmation`，与 `./dst` 走同一条本地路径（`fetch.rs:150-159`）；都不命中则 `RemoteNotFound`（保留编辑距离建议）。
  - 测试缝：沿用 `tag` 的仅 debug 构建失败注入先例（`tag.rs:889-902`），新增 `LIBRA_TEST=1` 加 `LIBRA_TEST_PUSH_FAIL_REMOTE_CONFIG_READ=1` 时让上述查询返回 `Err`，以便经真实 CLI 验证「读取失败不回退路径」。release 构建中该函数恒为假。
  - 匿名目标的跟踪行保持现状：裸名目标与 `./dst` 一样写 `refs/remotes/<参数原文>/<b>`，`--force-with-lease` 对同一参数原文的读取因此在新旧仓库里一致。这与 Git（匿名远端不写跟踪分支）不同，属既有差异，登记 DEFER-PS-10，本计划不改变写入或读取。
  - 路径存在但不是仓库（如空目录）时，沿用 `./<name>` 已有的 `InvalidRemoteUrl` 拒绝（探针 #5），只是文案里的参数是裸名。
  - 不存在的裸名保持现有 `fatal: remote '<name>' not found`（`LBR-CLI-003`、129）与提示，不改为 Git 的 `does not appear to be a git repository`（128）：在 Libra 中，一个既未配置、又不是现存路径的裸词几乎总是远端名拼写错误，现有提示更可操作。登记为有意差异（DEFER-PS-02）。
- **Alternatives considered:**
  - 直接扩展 `is_anonymous_repository_spec`：会同时改变 `fetch`/`pull` 的行为，而它们不在 #531 范围，且 #532 计划正在并行起草（DEP-PS-04）。
  - 完全照 Git，未配置的名字一律当作路径：会把远端名拼写错误变成「不是仓库」的报错，丢掉 did-you-mean 提示。
- **Consequences:** 新的失败路径（配置读取失败）按 GC-PS-05 F 型验收。`fetch dst`、`pull dst` 暂时仍报远端不存在：这是 ADR-HP-05 在 `fetch`/`pull` 上的剩余实现缺口，按 DEFER-PS-01 移交，新 helper 留待它们采用；新增的是共享 helper，PS-01 命中 ER-13 `T-1`。匿名目标的 `-u` 仍有推送后失败的既有缺陷（探针 #33），不在本卡轴上，登记 DEFER-PS-09。
- **Revisit when:** `fetch`/`pull` 的计划决定采用同一规则；或用户需要 Git 的不存在报错。

### ADR-PS-02：`--all`/`--branches` 的语义与互斥

- **Status:** Accepted
- **Context:** Git 中 `--branches` 是 `--all` 的别名（`builtin/push.c:710-711`）。选项解析后先执行 `die_for_incompatible_opt4(--delete, --tags, --all/--branches, --mirror)`（`:756-759`），再检查 `--delete` 是否带 ref（`:760-761`）；解析远端之后、联系远端之前检查「`--all`/`--mirror` 不能与 refspec 同用」（`:852-858`），对不存在的匿名路径同样先报这个错（探针 #7）。`--all` 推送 `refs/heads/*` 到同名远端分支、不推标签，按 refname 排序（探针 #6）。
- **Decision:**
  - **参数：** `PushArgs` 增加 `#[clap(long = "all", visible_alias = "branches", overrides_with = "all")] all: bool`；不要求仓库参数。自覆盖使 `--all --all`、`--all --branches`、`--branches --branches` 都被接受且等同一次 `--all`，与 Git 的幂等位加别名一致（`builtin/push.c:710-711`）；clap 的 `SetTrue` 在无自覆盖时会拒绝同一参数 ID 的重复出现。同时去掉 `--tags`、`--mirror` 上的 clap `requires("repository")`（`push.rs:167`、`:171`）：否则不带仓库的 `push --all --tags`、`push --branches --mirror` 会在 `execute_safe` 之前被 clap 拒绝，到不了互斥检查（Git 对这两者报四选项互斥，探针 #10 同理）。不带仓库的 `push --tags`/`push --mirror` 改由 `validate_push_args` 既有分支报 `repository is required when specifying refspecs, --tags, or --mirror`（`push.rs:880-884`，U′ 型）。
  - **互斥（PS-02）：** `execute_safe` 在 `apply_delete_flag` 之前调用新的 `validate_ref_set_selectors`：
    - 当 `--all` 为真，且 `--delete`、`--tags`、`--mirror` 中至少一个为真时，按 Git `die_for_incompatible_opt4` 的格式列出全部为真的选项，顺序固定为 `--delete`、`--tags`、`--all/--branches`、`--mirror`：两项为 `options 'A' and 'B' cannot be used together`，三项为 `options 'A', 'B', and 'C' cannot be used together`，四项为 `options 'A', 'B', 'C', and 'D' cannot be used together`。
    - 否则，当 `--all` 为真且有 refspec 时，报 `--all can't be combined with refspecs`（`--branches` 拼写也用这一文案）。
    - 两者都按 GC-PS-05 的 U 型拒绝；都在仓库解析、`apply_delete_flag` 与任何写入之前。
    - 不含 `--all` 的组合保持现有 Libra 文案（DEFER-PS-08）。
  - **推送（PS-02）：** `validate_push_args` 的「仓库参数但无 refspec」检查把 `--all` 视同 `--tags`/`--mirror`。在 `run_push` 的非镜像分支中，`--all` 时不再排入「无 refspec 时推当前分支」的默认计划，改用新的 `add_all_branch_update_plans`：经 `Branch::list_branches_result(None)` 列出本地分支，按完整 refname 排序，每个分支以 `refs/heads/<b>` → `refs/heads/<b>` 调用现有 `add_update_ref_plan`（非强制，除非 `--force`/`--force-with-lease`）。之后的 `--follow-tags`、`--dry-run`、`--porcelain`、`--json`、`--atomic` 与本地/网络发送都沿用现有路径。
  - **沿用的现有行为：** 仓库参数缺省时，沿用 `branch.<当前分支>.remote`；分离 HEAD 时报 `DetachedHead`。发送前的校验（含按远端通告做的非快进判定）发现任一分支被拒时，整次推送不发送任何数据、目标不变（`LBR-CONFLICT-002`，128）；这只是「发送前」的全有或全无。发送之后的失败沿用现有行为：Git 目标逐个提交 ref、网络目标遇 `ng`，已写入的 ref 都不回滚（`local_push_git.rs:96-124`、`push.rs:2423-2441`）。本地 Git 目标的这一行为由 PS-02 用仅 debug 构建的失败注入（`LIBRA_TEST=1` 加 `LIBRA_TEST_PUSH_FAIL_GIT_REF_AFTER_FIRST=1`：`apply_local_push_to_git` 提交第一个 ref 之后返回错误）验证：报 `LocalPush`（`fatal`、`LBR-REPO-003`、128），目标恰有第一个 ref 被更新，去掉注入后重跑，目标 ref 收敛。收敛只针对目标：失败发生在 `update_remote_tracking_refs`（`push.rs:1456`）之前，重跑时已提交的 ref 因已最新被过滤（`push.rs:1117`），其本地跟踪 ref 不会被重跑刷新；对已配置远端，恢复步骤是重跑之后对每个在失败前已提交的分支执行 `libra fetch <remote> +refs/heads/<b>:refs/remotes/<remote>/<b>`（显式且带 `+` 的 refspec：不依赖 `remote.<remote>.fetch` 是否被 `remote set-branches` 等限制；`+` 允许在 `--all --force` 改写历史后把跟踪 ref 非快进地更新，`fetch.rs:4787` 对不带 `+` 的非快进更新会拒绝），由 PS-02 的门验证。网络 `ng` 路径的部分更新不新增测试、不作恢复承诺（DEFER-PS-03）。与 Git 的差异（Git 逐 ref 部分推送、退出 1；分离 HEAD 可用）登记为 DEFER-PS-03、DEFER-PS-04。
- **Alternatives considered:** 先只加互斥、`--all` 单独使用时报不支持，下一张卡再实现推送：中间版本会把一个可用的 Git 选项发布成「不支持」，且违反「新选项与其互斥同卡交付」（G-02）。把 `--branches` 做成独立旗标：两种拼写的输出可能不同，t5583 要求逐字节相同。
- **Consequences:** `-u` 与 `--all` 同用在 PS-02 发布后仍按现有规则拒绝（计划多于一项），由 PS-03 放开。
- **Revisit when:** #683 引入 `push.default` 与 `remote.<name>.push` 时，确认 `--all` 不受其影响（Git 在 `--all` 时不读 `remote.<name>.push`，`builtin/push.c:434-439`）。

### ADR-PS-03：`-u --all` 为每个分支设置上游

- **Status:** Accepted
- **Context:** Git 的 `push -u --all` 为每个推送结果为成功或已最新的分支写 `branch.<b>.remote` 与 `branch.<b>.merge`（探针 #16、#17）；`--dry-run` 不写配置（探针 #18）。Libra 的 `-u` 要求仓库参数、要求计划恰好一项，`PushOutput.upstream_set` 只有一个值（`push.rs:104-105`、`:1481-1531`、`:704`）。
- **Decision:**
  - 去掉 `-u` 上的 clap `requires("repository")`，改在 `validate_push_args` 中检查：`-u` 且无仓库参数且无 `--all` 时，按 GC-PS-05 的 U′ 型拒绝报 `--set-upstream requires a repository unless --all/--branches is given`（与现在一样拒绝，只是文案变化；不带仓库的普通 `-u` 由 DEFER-PS-06 承接）。
  - `-u --all` 且仓库参数（显式或缺省解析得到）不是已配置远端时（匿名路径/URL/裸名），在仓库解析之后、远端发现与任何写入之前按 U′ 型拒绝：`--set-upstream with --all/--branches requires a configured remote`。理由：现有 `set_upstream_safe_with_output` 只能解析已配置远端（探针 #33），否则会在目标已写入之后失败；匿名目标的 `-u`（Git 写 `branch.<b>.remote=<参数原文>`，见 Git 探针 `push -u --all ./dst`）登记 DEFER-PS-09。
  - 已配置远端时：在推送成功之后（含因已最新而被过滤的分支），按 refname 顺序为每个 `--all` 选中的分支写上游 `<remote>/<b>`，全部键在**一个**数据库写事务中写入：在 `src/command/branch.rs` 新增 `pub(crate) async fn set_upstreams_atomic(entries: &[(String, String, String)]) -> Result<(), BranchError>`（`branch`、`remote`、`merge_short`）。该函数只做持久化：调用方传入已解析好的 `remote`（已配置远端名或本地 upstream 的 `.`，与现有 `write_upstream_config` 收到的值相同，`branch.rs:1503`、`:2072`），函数不做「远端已配置」校验；在 `crate::internal::db::write_transaction`（`db.rs:494`）内依次以 `ConfigKv::set_with_conn` 写 `.remote` 与 `.merge`，并保留现有「值相同则不写」的幂等判定；任一写入失败则整个事务回滚，没有任何分支（包括失败分支自身）留下半对键。现有 `write_upstream_config`（`branch.rs:1462-1492`）改为以单元素调用同一函数，保持单一事实源；`branch -u`、`branch --track` 的本地 upstream（`remote=.`）语义不变，由既有用例 `branch_test::test_branch_set_upstream_to_with_branch_arg_and_local_upstream_matrix`（`tests/command/branch_test.rs:2747`）守住。「目标须为已配置远端」只是 `push -u --all` 自己在仓库解析后做的检查，不进入共享函数。推送在发送前失败（含非快进）时不写任何上游；推送成功而上游事务失败时报 `TrackingRefUpdate`（`fatal`、`LBR-IO-002`、退出 128），目标 ref 已更新，重跑 `push -u --all` 即可（各分支此时已最新，仍会写上游）。`--dry-run` 不写。
  - 与 Git 的差异：Git 的 `set_upstreams`（`transport.c:83-126`）逐 ref 调用 `install_branch_config` 并忽略其返回值，某个分支写失败时继续写后续分支；Libra 改为全有或全无。登记为有意差异，写入文档。
  - 测试缝：沿用仅 debug 构建的失败注入先例（`tag.rs:889-902`），`LIBRA_TEST=1` 加 `LIBRA_TEST_BRANCH_FAIL_UPSTREAM_WRITE=<branch>` 时，`set_upstreams_atomic` 在事务内写完该分支的 `.remote` 之后、写 `.merge` 之前返回错误，从而经真实 CLI 证明半对键也被回滚。release 构建中恒不触发。
  - 输出：人读模式按同一顺序每个分支一行，沿用现有格式 `branch '<b>' set up to track '<remote>/<b>'`；全部已最新时也输出——`render_push_output` 现在在打印 `Everything up-to-date` 后直接返回（`push.rs:2504-2507`），本卡改为在该行之后接着输出上游行（Git 在已最新时同样报告上游设置，探针 #17）。单分支 `-u` 在已最新时随之也输出其上游行。`-q` 时不输出上游行（Git 的 `-q` 同样不打印 `set up to track`）。JSON 的 `upstreams_set` 在全部已最新（`run_push` 的 `plans.is_empty()` 提前返回，`push.rs:1119-1137`）时同样列出全部上游。JSON 新增字段 `upstreams_set: [{"branch": <本地分支>, "upstream": "<remote>/<远端分支>"}]`（按顺序列出本次写入的全部上游；未写时为空数组）；既有 `upstream_set` 只在恰好写入一个上游时为该值的 `upstream` 字符串，否则为 `null`。人读输出与 JSON 都从这份在过滤已最新计划之前就记录的「本地分支 → 上游」列表渲染，不再从 `updates.first()` 推断本地分支（`push.rs:2626-2639` 在已最新时会得到 `?`），因此 `main:published` 这类改名映射在已最新时也报告正确的本地分支。单分支 `-u` 的 `upstream_set` 不变。
  - 单分支 `-u` 的其余规则不变（`validate_set_upstream_plan` 只在非 `--all` 时执行）。
- **Alternatives considered:** 只为实际被更新的分支设上游：与 Git 不同（探针 #17）。`upstream_set` 改为数组：破坏既有 JSON 消费者。照 Git 逐个写入、失败继续：会留下部分分支（乃至单个分支的半对键）指向新远端，且 `branch.rs` 的两次写入本身不在事务内（`branch.rs:1483-1489`）。
- **Consequences:** JSON 模式的新增字段写入 EN/zh 文档的结构说明。`branch.rs` 新增共享写入函数，PS-03 命中 ER-13 `T-1`；`branch --set-upstream-to` 的单分支写入也变为事务内写入（行为不变，只是不再可能留下半对键）。
- **Revisit when:** DEFER-PS-06 处理不带仓库的普通 `-u`。

### ADR-PS-04：Git 语法的 `--progress` 与 `Writing objects` 行

- **Status:** Accepted
- **Context:**
  - Git 的 `push --progress` 是布尔选项，即使 stderr 不是终端也输出进度；与 `--no-progress` 最后出现者生效；`-q` 不压制显式的 `--progress`（`builtin/push.c:732`；探针 #23–#25）。t5523 #13 只检查 stderr 含 `Writing objects`。
  - Libra 的 `--progress <MODE>` 是全局参数，不能在一次调用中出现两次；`index-pack` 用 argv 改写解决同样的冲突（`cli.rs:1109-1147`）。Libra 的文本进度条在非终端不绘制，模板也不含任务名（探针 #26）。
- **Decision:**
  - **argv 改写（`src/cli.rs`）：** 新增 `rewrite_push_progress_args`（只改写、不判断仓库是否存在），在 `parse_async_scoped` 中紧随 `rewrite_index_pack_progress_args` 调用。仅当子命令是 `push` 时，扫描子命令之后、`--` 之前的参数：恰为 `--progress` 的词，若下一个词是 `json`/`text`/`none`/`auto` 之一则保持不变（保留全局 `--progress <MODE>` 的既有写法），否则改写为隐藏的局部旗标 `--force-progress`。`--progress=<MODE>` 与子命令之前的 `--progress` 不改写。
  - **定位子命令：** 现有 `find_subcommand_index`（`cli.rs:1335-1367`）只跳过 `--color`、`--progress` 的分离取值，不跳过同样取分离值的全局 `--max-connections <N>`（`cli.rs:324-325`），`libra --max-connections 1 push --progress origin main` 会把 `1` 当作子命令，改写因此失效。另一方面，该函数把 `--color` 也当作取分离值，但 `--color` 是 `num_args = 0..=1` 且 `require_equals = true`（`cli.rs:265-275`），裸 `--color` 不取下一个词，`libra --color push …` 因此同样定位错误。本卡修正该函数：只对真正取分离值的全局选项（`--progress`、`--max-connections`）跳过下一个词；`--color`、`--json`/`-J` 要求 `=`，裸写只占一个词；`=` 形式照旧作为单个词跳过。`cli.rs` 内全部 12 处调用方随之受影响：各命令的 argv 改写与子命令定位，以及错误分类与命令链检测（`cli.rs:3039`、`:3107`）、控制参数校验（`:3296`）；由 `cli::tests` 全模块回归与本卡 `T-1` 全量守住。
  - **局部旗标：** `PushArgs` 增加隐藏的 `--force-progress`；它与 `--no-progress` 都设 `overrides_with_all([force_progress, no_progress])`（含自身，clap 4 的自覆盖），因此同一旗标可重复出现、两者混用时最后出现者生效，与 Git 的布尔选项相同（`builtin/push.c:732`）。只改这两个旗标。
  - **判定（单一函数）：** `push.rs` 新增私有函数 `push_progress_line_enabled(json_output: bool, local: Option<bool>, mode: ProgressMode) -> bool`，按以下顺序判定：
    1. `json_output`（全局 `--json`/`--machine`）为真 → 假；
    2. `mode == ProgressMode::Json`（全局 `--progress=json`，此时既有报告器在 stderr 输出 NDJSON 进度事件，`output.rs:631-658`）→ 假，保证 stderr 的进度通道只有 NDJSON；
    3. 否则 `local == Some(true)`（最后出现的是 `--progress`）→ 真；其余（`Some(false)` 或 `None`）→ 假。
    `-q` 不参与判定，因此不压制显式 `--progress`（Git 同）。
  - **输出：** 判定为真且本次对象集合非空时，在打包分支全部结束之后（`push.rs:1278-1377` 的 `--thin` 分支与普通编码分支之后、`bytes_pushed` 计算之前，`:1379`）向 stderr 写一行 `Writing objects: 100% (<n>/<n>), done.`（`<n>` 为对象数）。因此 `--thin` 路径（`encode_thin_pack`，`:1326`）与普通编码路径共用同一输出点。现有进度条与 `--no-progress` 行为不变；未给 `--progress` 时（自动模式，含终端）不输出这一行——终端上自动进度的 Git 文本还原属 DEFER-PS-07（TC-2247）。
- **Alternatives considered:** 把裸 `--progress` 一律改写为全局 `--progress=text`：与 `--no-progress`、全局 `--progress=<MODE>` 同时出现时会触发「不能重复给出」，且文本模式在非终端仍不输出。把全局参数改为可选值：改变全部命令的全局合同（T-3）。
- **Consequences:** `libra push --progress text origin main` 这类写法仍按全局模式解析。要对名为 `json`/`text`/`none`/`auto` 的远端强制进度，写 `libra push --progress -- text main`：`--progress` 的下一个词是 `--`，因此被改写为局部旗标，`text` 留作仓库参数；`--progress=<MODE>` 只选全局模式、不等于局部的 `--progress`。文档写明两种写法的区别。`libra --progress=json push --progress …` 只有 NDJSON 进度、没有文本行。
- **Revisit when:** 全局 `--progress` 合同变化，或 DEFER-PS-07 还原 Git 的完整进度输出。

## 全局工程约束

本计划完整继承模板 GC-01..GC-13，另加以下约束：

- **GC-PS-01 单一事实源：** 仓库参数判定只经 `src/internal/protocol/repository_arg.rs`；本地分支列表只经 `Branch::list_branches_result`；ref 计划只经 `add_update_ref_plan`；上游配置的持久化只经 `branch.rs` 的事务写入函数 `set_upstreams_atomic`（单分支调用方 `write_upstream_config` 以单元素调用，`push -u --all` 以全部分支一次调用）；进度行判定只经 `push_progress_line_enabled`。不得复制函数体。
- **GC-PS-02 零写入与检查顺序：**
  - **纯语法检查**（只看 argv 的互斥、缺参）在仓库解析之前完成。
  - **依赖配置的检查**（配置读取失败、`-u --all` 的目标是否为已配置远端）在仓库解析成功之后、远端发现之前完成。
  - 两类检查都在以下动作之前：远端发现、对象收集、向目标写对象或 ref、写跟踪分支、写上游配置。
- **GC-PS-03 零命中守卫：** Verification 中凡标「零命中」的命令，都在 `bash` 中先定义下列函数再调用。该函数按模板对 `rg` 退出码三分支判定（模板已在 `bash -e` 与 `zsh -e` 下验证三条分支）：

  ```bash
  zero_hits() {
    pattern="$1"; shift
    if rg -n -- "$pattern" "$@"; then
      echo "FAIL: forbidden pattern found"; return 1
    else
      rc=$?
      if [ "$rc" -ne 1 ]; then echo "ERROR: rg failed with exit $rc"; return "$rc"; fi
      echo "OK: zero hits"
    fi
  }
  ```

- **GC-PS-04 测试隔离：**
  - 新用例全部用 `tempdir()` 夹具与显式 cwd；环境变量只给子进程设置，不改测试进程环境，因此不需要 `#[serial(env)]`。
  - 每个 Libra 与 `git` 子进程都把 `HOME`、`XDG_CONFIG_HOME`、`LIBRA_CONFIG_GLOBAL_DB`、`LIBRA_CONFIG_SYSTEM_DB` 指向该用例的临时目录，`git` 子进程另设 `GIT_CONFIG_NOSYSTEM=1`（GC-13 的测试隔离要求）。
  - 夹具中的目标仓库由 `git init --bare` 或 `libra init` 在临时目录内建立；不访问网络。
- **GC-PS-05 拒绝门族与门集合：** 本计划每条新增或新可达的失败路径（拒绝）都按下表展开成一组门。每个门是一个独立命名的测试函数，只断言一个谓词，计入所在卡的 G-03 分子（由 EX-PS-01 承载超限）。
  - **命名与单门执行：** 集成门由 PS-01 在 `tests/command/push_test.rs` 新增的宏 `refusal_gates!` 生成，或手写为普通测试函数，全名为 `command::push_test::<门名>`（`tests/command_test.rs` 挂载 `mod command`）。单门执行一律用 `source .env.test && cargo nextest run --test command_test --no-tests=fail -E 'test(=command::push_test::<门名>)'`（零匹配即失败；`cargo test … -- --exact <不含 command:: 的名字>` 会匹配 0 个用例且退出 0，禁止使用）。一张卡的全部集成门用前缀正则 `-E 'test(/^command::push_test::ps0N_/)'` 一次运行（`test(=…)` 只做全名精确匹配，不能用于前缀）。库内单元门用 `source .env.test && cargo nextest run --lib --no-tests=fail -E 'test(=<模块路径>::<fn>)'`。
  - **门集合相等（shell 门）：** 每张实现卡另有一个门集合门，证明编译出的 `ps0N_` 测试恰为本卡判据规范列出的集合（防止宏漏生成或改名后静默少测）。下列函数在 `bash -euo pipefail` 中定义并调用；列举失败、实际集合为空或与期望不等都使调用失败：

    ```bash
    set -euo pipefail
    gates_u() { for id in "$@"; do for x in msg code exit stdout state json machine_lines machine_json; do echo "${id}__${x}"; done; done; }
    gates_x() { for id in "$@"; do for x in msg code exit stdout state json machine_lines machine_json hint; do echo "${id}__${x}"; done; done; }
    gates_v() { for id in "$@"; do for x in msg code exit stdout state json_envelope json_message machine_lines machine_envelope machine_message hint; do echo "${id}__${x}"; done; done; }
    gate_set() {
      local prefix="$1"; shift
      test "$#" -gt 0 || return 1
      local listing actual expected
      listing="$(cargo test --test command_test -- --list "command::push_test::${prefix}")" || return 1
      actual="$(printf '%s\n' "$listing" | sed -n 's/: test$//p' | sort)" || return 1
      expected="$(printf 'command::push_test::%s\n' "$@" | sort)" || return 1
      test -n "$actual" || return 1
      test "$actual" = "$expected" || return 1
    }
    lib_gate_set() {  # $1 = 全名前缀；其余 = 期望全名
      local prefix="$1"; shift
      test "$#" -gt 0 || return 1
      local listing actual expected
      listing="$(cargo test --lib -- --list "${prefix}")" || return 1
      actual="$(printf '%s\n' "$listing" | sed -n 's/: test$//p' | sort)" || return 1
      expected="$(printf '%s\n' "$@" | sort)" || return 1
      test -n "$actual" || return 1
      test "$actual" = "$expected" || return 1
    }
    ```

    `gates_u` 用于 U、U′、W 型（8 门），`gates_x` 用于 C、F 型（9 门，含 `__hint`），`gates_v` 用于 V 型（11 门）。库内单元门的集合用 `lib_gate_set <全名前缀> <期望全名…>`。三个函数已用桩 `cargo` 验证：集合相等时通过，多一个期望门、列举失败或列举为空时失败。EX-PS-01 的「每门可单独执行」对测试门指上面的单门 nextest 命令，对门集合门指各卡的 `gate_set` 调用。
  - **通道：** 依据探针 #31、#20 与 `error.rs:1276-1287`：stdout 恒为空；人读模式 stderr 依次为人读行（`error:`/`fatal:` 前缀）、`Error-Code:` 行、可选的空行加 `Hint:` 行，stderr 非终端时末尾另有一行紧凑 JSON；`--json` 在 stderr 输出美化 JSON；`--machine` 在 stderr 输出单行 JSON。JSON 的 `message` 不带 `error:`/`fatal:` 前缀（`error.rs:1174`）。
  - **夹具（全局，供各卡引用；每个门在新建夹具上独立运行）：**
    - **FX-SRC：** 临时目录 `T` 下的 Libra 仓库 `T/src`：文件 `a`、提交 `one`（`main`，当前分支）；分支 `b1` 在 `one` 之上另有提交 `two`，分支 `b2` 在 `one` 之上另有提交 `three`（三个分支的 tip 两两不同，且 `b1`、`b2` 都不是当前分支）；注解标签 `t1`、轻量标签 `light` 指向 `one`。测试在推送前用 `libra show-ref` 记下源仓库 `refs/heads/*` 的「refname → OID」映射 M，作为比较基准。
    - **FX-DST-SENTINEL：** `git init --bare T/dst`，再从一个独立的临时 Git 仓库推入 `refs/heads/sentinel`（与 `src` 无共同提交），使「目标不变」不是空集对空集。
    - **FX-DST-CLEAN：** `git init --bare T/clean`、`T/clean2`（空）。
    - **FX-UP：** `git init --bare T/up.git`，在 `src` 中 `remote add up ../up.git` 并设 `branch.main.remote=up`、`branch.main.merge=refs/heads/main`。
    - **FX-PLAIN：** 普通目录（非仓库），内含文件 `SENTINEL`，内容为 `sentinel`。
    - **FX-ABSENT：** 指定路径不存在。
  - **状态快照 `__state`（逻辑快照，执行前后各取一次，逐项比较）：**
    - 源仓库：以 sea-orm 打开 `.libra/libra.db`，`SELECT * FROM reference ORDER BY id` 的全部行（含匿名跟踪行，不经 `show-ref`/`branch -r` 的远端枚举）；`libra config --list` 的 stdout；
    - argv 中已存在的 Git 目标：目标目录下全部普通文件的「相对路径 + 内容 SHA-256」有序列表（覆盖 `objects/`、pack/idx、`refs/`、`packed-refs`）；
    - argv 中已存在的 Libra 目标：其 `.libra/libra.db` 的 `reference` 全部行，加 `.libra/objects/` 下全部文件的「相对路径 + 内容 SHA-256」有序列表；
    - argv 中的 FX-PLAIN 目录：其下全部文件的「相对路径 + 内容 SHA-256」有序列表；
    - argv 中的 FX-ABSENT 路径：执行后仍不存在。
    - 快照 helper 由 PS-01 新增，并由五个各自独立命名的自证门（`command::push_test::ps01_snapshot_detects_*`）证明：对上述每一类对象各做一次人为修改（改目标仓库一个文件、在源 `reference` 表插入一行、改一个源配置键、改 `SENTINEL` 内容、创建 FX-ABSENT 路径），修改后的快照与修改前不同。
  - **U 型（用法冲突，ADR-PS-02）：** 构造 `CliError::fatal(msg).with_stable_code(StableErrorCode::CliInvalidArguments)`。门：
    - `__msg`：stderr 第 1 行等于 `fatal: <msg>`；
    - `__code`：stderr 第 2 行等于 `Error-Code: LBR-CLI-002`；
    - `__exit`：退出码为 129；
    - `__stdout`：stdout 为 0 字节；
    - `__state`：状态快照不变；
    - `__json`：以 `--json` 重跑，stderr 解析出的 JSON 对象等于 `{"ok":false,"error_code":"LBR-CLI-002","category":"cli","exit_code":129,"severity":"fatal","message":<msg>}`（无 `hints`）；
    - `__machine_lines`：以 `--machine` 重跑，stderr 恰为一行；
    - `__machine_json`：同一次 `--machine` 运行的 stderr 解析出的对象与 `__json` 的期望对象相等。
    每条 U 型拒绝因此为 8 个门。
  - **U′ 型（`command_usage`，沿用 `PushError::InvalidArguments` 映射）：** 与 U 型相同的 8 个门，但 `__msg` 期望 `error: <msg>`，JSON 的 `severity` 为 `error`。
  - **V 型（裸名指向非仓库路径，ADR-PS-01，沿用 `InvalidRemoteUrl` 映射，探针 #5 形状）：** `command_usage` + `LBR-CLI-002` + 提示 `check the remote URL with 'libra remote get-url <name>'`（字面 `<name>`）。消息尾部含绝对路径，记前缀 P = `invalid remote URL '<arg>': invalid local repository '<arg>': `、信封 E = `{"ok":false,"error_code":"LBR-CLI-002","category":"cli","exit_code":129,"severity":"error","hints":["check the remote URL with 'libra remote get-url <name>'"]}`。11 个门：
    - `__msg`：stderr 第 1 行以 `error: ` 加 P 开头；
    - `__code`、`__exit`、`__stdout`、`__state`：同 U 型；
    - `__json_envelope`：`--json` 重跑，解析出的对象去掉 `message` 键后等于 E；
    - `__json_message`：同一次 `--json` 运行的 `message` 以 P 开头（结构化消息不带 `error: `）；
    - `__machine_lines`：`--machine` 重跑，stderr 恰为一行；
    - `__machine_envelope`：同一次 `--machine` 运行的对象去掉 `message` 后等于 E；
    - `__machine_message`：同一次 `--machine` 运行的 `message` 以 P 开头；
    - `__hint`：人读模式 stderr 中恰有一行等于 `Hint: check the remote URL with 'libra remote get-url <name>'`。
  - **C 型（`--all` 中有分支非快进，沿用 `NonFastForward` 映射，探针 #20 形状）：** 9 个门：
    - `__msg`：stderr 第 1 行等于 `fatal: cannot push to '<ref>': non-fast-forward update`；
    - `__code`：第 2 行等于 `Error-Code: LBR-CONFLICT-002`；
    - `__exit`：128；
    - `__stdout`、`__state`：同 U 型；
    - `__json`：对象等于 `{"ok":false,"error_code":"LBR-CONFLICT-002","category":"conflict","exit_code":128,"severity":"fatal","message":<msg>,"hints":["pull and integrate remote changes first: 'libra pull'","or use --force to overwrite (data loss risk)"]}`；
    - `__machine_lines`：`--machine` 重跑，stderr 恰为一行；
    - `__machine_json`：同一次运行的对象与 `__json` 期望相等；
    - `__hint`：以 `Hint: ` 开头的 stderr 行依次恰为上述两条提示。
  - **F 型（配置读取失败，ADR-PS-01，沿用 `RepoState` 映射）：** `CliError::fatal` + `RepoCorrupt`，注入时消息固定为 `failed to read repository state: LIBRA_TEST_PUSH_FAIL_REMOTE_CONFIG_READ failpoint`（文案证明到达了注入点）。9 个门：`__msg`（stderr 第 1 行等于 `fatal: ` 加该消息）、`__code`（第 2 行 `Error-Code: LBR-REPO-002`）、`__exit`（128）、`__stdout`、`__state`、`__json`（对象等于 `{"ok":false,"error_code":"LBR-REPO-002","category":"repo","exit_code":128,"severity":"fatal","message":<上述消息>,"hints":["try 'libra status' to verify repository state"]}`）、`__machine_lines`（`--machine` 重跑时 stderr 恰为一行）、`__machine_json`（同一次运行的对象与 `__json` 期望相等）、`__hint`（stderr 恰有一行等于 `Hint: try 'libra status' to verify repository state`）。
  - **W 型（上游事务失败，ADR-PS-03，沿用 `TrackingRefUpdate` 映射）：** `CliError::fatal` + `IoWriteFailed`，注入时消息固定为 `failed to update local tracking ref: LIBRA_TEST_BRANCH_FAIL_UPSTREAM_WRITE failpoint (branch b2)`，无提示。8 个门：`__msg`（第 1 行等于 `fatal: ` 加该消息）、`__code`（第 2 行 `Error-Code: LBR-IO-002`）、`__exit`（128）、`__stdout`、`__state`（此型只比较源仓库 `libra config --list`：推送本身已成功，目标 ref 的变化不属禁止写入）、`__json`（对象等于 `{"ok":false,"error_code":"LBR-IO-002","category":"io","exit_code":128,"severity":"fatal","message":<上述消息>}`）、`__machine_lines`（`--machine` 重跑时 stderr 恰为一行）、`__machine_json`（同一次运行的对象与 `__json` 期望相等）。（`category` 依据 `error.rs:450`、`:172`。）

### Task PS-02：`--all`/`--branches` 推送全部分支及其互斥

**Task type:** `implementation`

**Lifecycle / Acceptance:** `pending` / 空

**Description:** 按 ADR-PS-02 新增 `--all` 与可见别名 `--branches`：推送全部本地分支到同名远端分支；与 `--delete`/`--tags`/`--mirror` 同用时按 Git 的 `die_for_incompatible_opt4` 文案拒绝，与 refspec 同用时报 `--all can't be combined with refspecs`；为让不带仓库的组合也能到达这些检查，去掉 `--tags`/`--mirror` 的 clap 仓库要求；并以仅 debug 构建的失败注入验证本地 Git 目标在发送后部分失败时的既有行为与重跑收敛。唯一行为轴是 `--all`/`--branches` 选项（选择全部分支及其自身的互斥规则）。
