## 文档职责

本文解决 issue #498：`libra tag <name> <commit>` 拒绝位置参数形式的目标（clap 报 `unexpected argument '<commit>' found`，`LBR-CLI-002`，退出码 129），用户只能在 HEAD 上建 tag；依赖「在指定提交上建 tag」的脚本因此静默缺 tag，随后 `merge <tag>` / `merge refs/tags/<tag>` 报 `not something we can merge`，看起来像 merge 缺陷（#477 DEFER-13 撤回结论）。目标是：`libra tag` 接受可选的 `<commit>`（commit-ish：分支、tag、修订表达式、对象名），按 Git 语义在该目标上创建轻量、附注或签名 tag，并以 Git 兼容、可被脚本区分的错误契约拒绝无效目标；同时先修复 tag 列表过滤器对「标签链」只 peel 一层的缺陷，使本计划开放的嵌套标签不会让 `tag --contains` 等过滤器失败。

本文只规划任务，不宣称实现完成。每张任务卡开工时都必须按 ER-01..ER-03 刷新源码、测试与文档锚点；任一任务状态推进时，同一变更必须同步更新 [`plan-status.md`](../plan-status.md)（本计划已在其「issues/ 下的计划」表登记 `issues/498.md` 行）。

### 适用范围

- `libra tag [-a] [-m <msg> | -F <file>] [-e] [-f] [-s] <name> [<commit>]`：第二个位置参数 `<commit>` 的解析、校验与建 tag 行为（轻量；`-a`/`-m`/`-F`/`-e` 附注；`-s` vault-PGP 签名；`-f` 覆盖），连同目标失败的 Git 兼容错误契约，在 TT-02 一个发布切片中交付。
- `<commit>` 的解析语义：复用共享严格 resolver `util::resolve_object_spec_typed`（不 peel）与 TT-05 新增的 typed peel 包装 `util::peel_to_non_tag_typed`，接受 commit 对象与「peel 链终点为 commit」的 tag 对象；peel 链终点为 tree / blob 的目标 fail-closed 拒绝（ADR-TT-01）。
- 非创建模式（`-d`、`-v`、列表与过滤器旗标）出现 `<commit>`、以及创建模式出现第三个位置参数时的用法错误契约（ADR-TT-02）。
- tag 列表过滤器 `--points-at`、`--contains`、`--no-contains`、`--merged`、`--no-merged` 对嵌套标签链与 tree / blob 终点标签的 peel 语义（ADR-TT-03）。
- #498 复现与 DEFER-13 场景回归：在显式目标上创建的 tag 可被 `merge <tag>` 与 `merge refs/tags/<tag>` 消费。
- 同步：`src/command/tag.rs` 的 `TAG_EXAMPLES`（`--help`）、`docs/commands/tag.md`（EN）、`docs/commands/zh-CN/tag.md`、`docs/development/commands/tag.md`、`COMPATIBILITY.md` tag 行、`../libra-backend/apps/tanstack-app/content/docs/commands/tag.en.md`；每张活动卡一个独立发布切片（`patch + 1` + `gh release create`）。

### 非目标

- 为 tree / blob 对象（含 peel 链终点为 tree / blob 的 tag 对象）建 tag：本计划 fail-closed 拒绝并文档化（DEFER-TT-01；2026-10-02 实测：源仓库含 tree / blob tag 时 `libra clone` 失败，见「事实基线」）。
- 嵌套 tag 的 Git advice 提示（`hint: You have created a nested tag…`、`advice.nestedTag`）：Libra 没有 advice 框架（DEFER-TT-02）。
- `-f` 覆盖已有 tag 时 Git 的 `Updated tag '<name>' (was <abbrev>)` 措辞，以及 Git「已存在检查先于编辑器」的顺序：既有差异，HEAD 形态同样存在（DEFER-TT-03）。
- `show <嵌套 tag>` 的 tag 头链展示与 `log --decorate` 对嵌套 tag 的装饰（DEFER-TT-04，log/show 命令族）。
- 本地 clone / fetch 对 Git 源中 tree / blob tag 目标的 pack 组装失败（DEFER-TT-05，传输族既有缺陷）。
- `tag -n<k>` 对指向 vault 签名提交的轻量 tag 显示 `gpgsig -----BEGIN PGP SIGNATURE-----` 而非提交标题（DEFER-TT-06，2026-10-02 实测的既有缺陷，不在本计划任何行为轴内）。
- 14 个对 umask 敏感的既有测试（DEFER-TT-07）：它们断言 `0o755` 等固定模式，在本机默认 `umask 0002` 下失败、在 CI 一致的 `umask 022` 下通过；修正这些测试的环境假设不在本计划范围，本计划的全量门统一在 `umask 022` 下执行。
- #533 的其余 tag 缺口：多名 `-d`/`-v`、多 pattern `-l`、重复 `--points-at` 及其参数侧不 peel 语义、`--format`、`--trailer`、`--no-sort`、`-i`、版本排序、非法 tag 名校验、`--create-reflog`（Libra `tag` 当前不支持该旗标）等，由 [`issues/477b.md`](477b.md) HW-05 承接（DEP-498-01）；本计划只保证新位置参数不与其冲突。
- Git GPG 互操作（`-s`/`-v` 维持 vault-PGP，`COMPATIBILITY.md` 既有有意差异）。
- 不新增稳定错误码；不改 SQLite schema、连接建构、bootstrap 或 migration（GC-13 N/A）；不新增或更名 `--test` target。

### 成功定义

- `libra tag <name> <commit>` 在 commit-ish 目标上创建 tag：轻量 tag 的 ref 值等于 `libra rev-parse <commit>`（不 peel；对 annotated tag 名即其 tag 对象）；附注 / 签名 tag 对象的 `object` 等于该值、`type` 为 `commit` 或 `tag`；省略 `<commit>` 时行为与现状一致（HEAD）；给出 `<commit>` 时不读取 HEAD（HEAD 未诞生也可建 tag）。
- #498 复现（`libra tag vside side`、`libra tag -m msg vann side`）成功；`libra merge vside` 与 `libra merge refs/tags/vann` 成功合入 `side`（DEFER-13 场景的两种拼写）。
- 无法解析（名字不存在、歧义前缀、完整 id 不存在）、peel 链终点非 commit、HEAD 未诞生、读失败 / 损坏、位置参数误用均满足 ADR-TT-02 的 Git 兼容契约并零写入；人读、`--json`、`--machine`、退出码与零写入各自作为独立的门验收（GC-04）。
- tag 列表过滤器在存在嵌套标签与 tree / blob 终点标签时不再失败，结果与同 fixture 下 Git 2.43.0 实测一致（ADR-TT-03）。
- 已移植并守卫的上游场景（pin `git@1630431f326e15fcde608827b5ff38422528eb59`）：`t/t5305-include-tag.sh:71`「create hidden inner tag」、`t/t7004-tag.sh:1866`「--points-at finds annotated tags of commits」，以及 `t/t7004-tag.sh:1412`「creating a signed tag pointing to another tag should succeed」的 vault-PGP 原生变体。
- TT-05、TT-02 各自取得 C 组发布（`patch + 1`、`gh release create`）与 D 组远端证据，文档、兼容矩阵与网站同步；计划全量收口门（ER-13）中 fmt、clippy 与 `umask 022` 下的全量 nextest 全部全绿后，计划才可标记完成。

## 评审结论与修订记录

| 维度 | 结论 | 修订动作 |
|---|---|---|
| 合理性 | 缺口使 Git 常见用法（`git tag <name> <commit>`）不可用并伪装成 merge 缺陷；修复后新开放的嵌套标签会触发既有过滤器缺陷，必须先处理 | TT-05 先行，再交付目标参数 |
| 可行性 | 共享 resolver、peel 循环与 tag 对象写入路径均已存在；只需新增 typed peel 包装、位置参数、目标感知的创建入口与错误映射 | ADR-TT-01..04 固定复用点与交付方式 |
| 任务卡粒度 | 原草稿四张卡把「根因」「实现」「回归」「测试 / 文档 / 发布」拆开，违反 G-02；按 G-03 独立谓词并按 GC-04 把每种渲染、退出码与零写入单独计数后，两个行为轴的门族分别为 34 与 108 个，属于「同一恢复轴上的机械门族」；R1 曾按表面轴把创建拆为三卡，但中间契约 G1 / G3 制造了大量一次性门（R3 F19），waiver 获批后合并回单卡 | 废弃 TT-01 / TT-03 / TT-04；TT-06 / TT-07 合并回 TT-02；两卡以已批准的 EX-TT-01 承载门族，一门 = 一个只断言一个谓词的具名测试函数或一条守卫命令 |
| 依赖与顺序 | 两张卡都写 `src/command/tag.rs`、`tests/command/tag_test.rs` 与 tag 文档（G-10 I–I 相交）；TT-02 放开嵌套 / tag 对象目标前必须先修过滤器，且消费 TT-05 的 typed peel 包装 | `TT-05 -> TT-02` |
| 完整性 | 每张卡含实现、测试、EN / zh-CN / 开发 / 网站文档、`COMPATIBILITY.md` 与 C / D 发布 | 逐文件列入写集（ER-06a） |
| 安全性 | tree / blob 目标会产出 Libra 自身无法 clone 的仓库；目标解析失败若晚于编辑器、消息文件读取或对象写入会留下副作用 | ADR-TT-01 fail-closed；GC-TT-02 零写入顺序；TT-02 G36–G38 |
| 功能正确性 | peel 与不 peel 的选择决定 `rev-parse <name>` 结果；签名载荷必须与落库对象的 `object`/`type` 一致；过滤器对非 commit 终点必须排除而不是失败 | ADR-TT-01、ADR-TT-03；TT-02 G27–G30、TT-05 G1–G24 |
| 接口兼容 | 新增可选位置参数，不改既有形态；不新增错误码；`--json`/`--machine` schema 不变；无效目标退出码沿用 Libra `LBR-CLI-003` 契约（129，Git 为 128） | ADR-TT-02；`COMPATIBILITY.md` 与文档记录差异 |
| 数据流与控制流 | 目标解析与校验先于编辑器、消息文件读取、对象写入与 ref 写入；过滤器深 peel 只在过滤器生效时执行 | GC-TT-02；ADR-TT-03 |
| 性能与容量 | 目标解析为表达式开销（有界次带索引的 ref 查询、`~N` / `:<path>` 按表达式深度）加 O(peel 链长) 次 tag 对象读取；过滤器每个 tag 额外 O(链长) 次类型读取 | 各卡 Performance budget |
| 可靠性与容错 | 链断裂、读失败必须 fail closed，且不得被误报为「storage broken」 | TT-05 G21–G24；ADR-TT-02 E5 |
| 可维护性 | 不得在 tag 模块复制 peel 循环或 resolver | GC-TT-01；TT-05 G30 零命中守卫 |

## 已决议设计决策

实现时若需偏离本节，必须先修改计划并说明原因，不得在代码中静默改语义。

### ADR-TT-01：`<commit>` 按 Git 语义解析为未 peel 的 commit-ish 对象，tree / blob 终点 fail-closed

- **Status:** Accepted
- **Context:** 根因有两处：`TagArgs` 只暴露一个位置参数（`src/command/tag.rs:43-46`），以及 `internal::tag::create` 总是在 HEAD 上建 tag 并写死 `ObjectType::Commit`（`src/internal/tag.rs:113-123`、`:159-197`）。Git 用 `get_oid` 解析 `<commit>|<object>`，不 peel，并记录对象实际类型；Libra 已有同语义的共享严格 resolver（`src/utils/util.rs:2174-2189`）。2026-10-02 实测：源仓库含 tree / blob tag 时 Libra 的本地 clone 失败，嵌套 tag 则可被传输。
- **Decision:**
  1. `TagArgs` 新增第二个可选位置参数 `target: Option<String>`（clap `value_name = "COMMIT"`，帮助文本说明默认 HEAD、只在创建时有效）。
  2. 目标解析只经共享 helper：`util::resolve_object_spec_typed(<commit>)` 得到未 peel 的对象 id `T`（接受该 resolver 支持的全部语法，语法由 `compat_rev_parse_peel_selectors` 守卫，本计划只验收代表形态）；`util::require_object_exists_typed(T, <commit>)` 证明 `T` 存在；`util::peel_to_non_tag_typed(T, <commit>)`（TT-05 引入）返回 peel 链终点 `(F, kind)`。`kind` 为 commit 时目标合法；`T == F` 则 `T` 的类型为 `commit`，否则为 `tag`；`kind` 为 tree / blob 时 fail-closed（E2）。
  3. 轻量 tag 的 ref 值 = `T`；附注与签名 tag 对象的 `object` = `T`、`type` = `T` 的类型；签名载荷的 `object`/`type` 行与落库对象逐字节一致（`tag -v` 按落库字段重建载荷，`src/internal/tag.rs:295-298`）。
  4. 给出 `<commit>` 时不读取 HEAD；省略时保持现状（HEAD，未诞生则 `HeadUnborn`）。
  5. `internal::tag` 新增接受已解析目标（对象 id + 类型）的创建入口；既有 `create(name, message, force, sign)` 保留为「目标 = HEAD」的包装，既有调用方（`src/command/tag.rs:821`、`src/utils/util.rs:3568`、`:3619`）不改。
- **Alternatives considered:** (a) 用 `get_commit_base_typed(<commit>)` peel 到 commit 再建 tag——拒绝：`rev-parse <name>` 与 Git 不同，`t5305-include-tag.sh:71` 的嵌套 tag 无法建立，且静默改变用户指定的对象身份；(b) 接受任意对象（tree / blob）——本期拒绝：实测会产出 Libra 自身无法 clone 的仓库，列表过滤器亦受影响（GC-07 fail-closed；DEFER-TT-01 登记重启条件）；(c) 在 tag 模块另写解析逻辑——拒绝（GC-02）；(d) 以 `get_commit_base_typed(&T.to_string())` 判定 commit-ish——拒绝：只能得到 `InvalidReference(String)`，E2 需要的终点类型只能靠解析错误文本（R1 F7）。
- **Consequences:** 嵌套 tag 与「轻量 tag → tag 对象」变为用户可直接创建，因此必须先由 TT-05 修复过滤器并提供 typed peel 包装（`TT-05 -> TT-02`）；与 Git 的有意差异（tree / blob 目标被拒）写入 `COMPATIBILITY.md` 与命令文档；`show`/`log --decorate` 对嵌套 tag 的展示差异登记 DEFER-TT-04。
- **Revisit when:** DEFER-TT-01 的重启条件满足（clone / fetch / push 支持非 commit tag 目标，且 tag 列表与 `show`/`log` 消费者对 tree / blob 终点完成验证）。

### ADR-TT-02：目标相关的错误与用法契约

- **Status:** Accepted
- **Context:** 需要在不新增稳定错误码的前提下，让失败路径与 Libra 现有命令一致且可被脚本区分；Git 的对应失败均为 128。
- **Decision:** 契约如下；人读 stderr、`--json` 错误信封、`--machine` 单行信封、进程退出码与零写入各为独立验收的门（GC-04）；目标解析与校验发生在编辑器、消息文件读取、对象写入与 ref 写入之前（GC-TT-02）。`--json` / `--machine` 门比较信封的 `(error_code, exit_code, message)` 三元组。

  | 契约 | 触发 | 消息（人读首行；`message` 字段为其去掉 `fatal: ` / `error: ` 前缀的部分） | 稳定码 | 退出码 |
  |---|---|---|---|---|
  | E1 无法解析 | resolver 报 `InvalidReference`（名字不存在，或对象名前缀歧义 `ambiguous argument: <x>`），或完整长度对象 id 不存在（`require_object_exists_typed` 失败） | `fatal: Failed to resolve '<commit>' as a valid ref.`，hint `use 'libra log --oneline' to see available commits.` | `LBR-CLI-003` | 129 |
  | E2 非 commit 终点 | 解析成功且对象存在，但 `peel_to_non_tag_typed` 的终点类型为 tree 或 blob | `fatal: cannot tag '<commit>': it resolves to a <tree 或 blob> object, not a commit`，hint `only a commit, or a tag that peels to a commit, can be tagged` | `LBR-CLI-003` | 129 |
  | E3 位置参数误用 | 非创建模式（`-d`、`-v`，或 `tag_requests_list` 为真的任一旗标）给出 `<commit>`：`error: the <commit> argument '<x>' is only valid when creating a tag`；创建模式给出第三个位置参数：clap 原生 `error: unexpected argument '<x>' found` | 消息含被拒参数原文 | `LBR-CLI-002` | 129 |
  | E4 HEAD 未诞生 | `<commit>` 经由 HEAD 解析（`HEAD`、`@`、`HEAD~1` 等）且 HEAD 未诞生 | 复用 `fatal: Cannot create tag: HEAD does not point to a commit` | `LBR-REPO-003` | 128 |
  | E5 读失败 / 损坏 | resolver 或 peel 报 `ReadFailure` 或 `CorruptReference`（含 tag 对象的目标缺失） | 读失败：`fatal: failed to resolve '<commit>': the object store could not be read`，hint `check that the repository is readable and retry.`；损坏：`fatal: failed to resolve '<commit>': its object graph is corrupt or incomplete`，hint `run 'libra fsck' to inspect missing objects.` | `LBR-IO-001` / `LBR-REPO-002` | 128 |

  E3 在 `validate_cli_args` 中、仓库预检之前拒绝（与既有「usage 先于 repo-not-found」一致），`run_tag` 为程序化入口重复同一校验。读失败分支无法经正常 CLI 稳定复现，故提供测试 failpoint：同时设置 `LIBRA_TEST=1` 与 `LIBRA_TEST_TAG_FAIL_TARGET_READ=1` 时，目标解析在调用 resolver 之前直接返回 `CommitBaseError::ReadFailure`，使 E5 读失败的人读、`--json`、`--machine`、退出码与零写入可经真实 CLI 路径验收。该 failpoint 只编译进 debug 构建（`#[cfg(debug_assertions)]`，release 构建为恒返回「未触发」的同名空实现），并以 `LIBRA_TEST` 哨兵门控——沿用 `stash` 的 debug-only failpoint 先例（`src/command/stash.rs:2095-2135`）与 `am` 的环境变量门控先例（`src/command/am.rs:755`）；release 二进制不存在该路径，未设置 `LIBRA_TEST` 时该变量无效。全部目标错误的面向用户文案都是上表的固定文本，不拼接底层存储错误（底层错误可能含本地对象路径，`src/utils/util.rs:1648`、`src/utils/storage/local.rs:410`）；底层细节只经 `tracing::warn!` 记入日志。
- **Alternatives considered:** 沿用 Git 的 128 退出码——拒绝：`LBR-CLI-003` 的退出码由稳定码类别统一决定（`src/utils/error.rs:410-414`），与 `branch <new> <bad>`、`tag --points-at <bad>` 一致更重要；为每个目标失败新增错误码——拒绝（无新语义，GC-04 要求复用既有码）；以通用文案先行、后续卡再细分——拒绝（R3 F19：中间契约制造一次性门，见 ADR-TT-04）。
- **Consequences:** 消息首行沿用 Git 文案（E1），退出码差异（129 vs 128）写入命令文档与 `COMPATIBILITY.md`；`docs/error-codes.md` 不变。
- **Revisit when:** 稳定错误码体系调整 CLI 类退出码，或 #533 统一 tag 族的多余参数文案。

### ADR-TT-03：tag 列表过滤器沿标签链完全 peel，非 commit 终点从过滤结果中排除

- **Status:** Accepted
- **Context:** `collect_tags` 用 `tag_peeled_commit` 只 peel 一层（`src/command/tag.rs:1002-1013`），导致嵌套 tag 漏列、`--contains`/`--no-contains` 因把 tag 对象或 tree 当 commit 遍历而整体失败（`LBR-IO-001`），`--no-merged` 误列 tree / blob tag。Git 的 ref-filter 对嵌套 tag 完全 peel，并在 `--contains`/`--no-contains`/`--merged`/`--no-merged` 生效时丢弃非 commit 终点（事实基线「Git 过滤器 fixture 期望」）。
- **Decision:**
  1. `src/utils/util.rs` 新增 `pub` typed 包装 `peel_to_non_tag_typed(object_id, display_name) -> Result<(ObjectHash, ObjectType), CommitBaseError>`，内部直接委托既有私有 `peel_object_to_type_typed(object_id, None, display_name)`（不复制 peel 循环与环检测），再读取终点对象类型。
  2. 只在 `--points-at`、`--contains`、`--no-contains`、`--merged`、`--no-merged` 中任一生效时，对每个 tag 的 ref 对象求终点：ref 对象本身是 commit / tree / blob 时直接取其类型（不 peel），是 tag 对象时调用该包装；终点为 commit 时以该 commit 参与全部过滤；终点为 tree / blob 时该 tag 从这五个过滤器的结果中排除（`--points-at` 的参数侧仍经 `get_target_commit` peel 到 commit，因而 tree / blob 终点也不可能匹配）。
  3. 链断裂（中间对象缺失）或环（包装返回 `CorruptReference`）：fail closed，固定文案 `tag '<name>' cannot be peeled to a commit: its tag chain is broken`（hint `run 'libra fsck' to inspect missing objects.`），`LBR-REPO-002`、退出码 128，stdout 不输出部分列表；包装返回 `ReadFailure` 时为固定文案 `failed to read the tag chain of '<name>'`（hint `check that the repository is readable and retry.`），`LBR-IO-001`、退出码 128。底层存储错误不拼入文案（可能含本地路径），只经 `tracing::warn!` 记入日志。读失败分支以测试 failpoint 触发，以便经真实 CLI 路径验收：同时设置 `LIBRA_TEST=1` 与 `LIBRA_TEST_TAG_FAIL_CHAIN_READ=<tag 名>` 时，只有名字等于该值、且 ref 对象为 tag 对象的那个 tag 在调用包装之前返回 `ReadFailure`，其余 tag 照常处理，故错误所指的 tag 与列表迭代顺序无关；与 ADR-TT-02 的目标 failpoint 相同，只编译进 debug 构建并以 `LIBRA_TEST` 门控（先例 `src/command/stash.rs:2095-2135`、`src/command/am.rs:755`）。
  4. 不带上述过滤器的列表（含 `-n`、pattern、`--sort`、`--column`）不做深 peel，输出不变。
  5. `tag_peeled_commit` 删除；tag 模块不再保留自有 peel 函数。
- **Alternatives considered:** 在 `collect_tags` 里遇错 `continue`——拒绝：静默掩盖损坏仓库（GC-07）且仍漏列嵌套 tag；在 tag 模块用 `load_object_trait` 自写循环——拒绝（GC-02 重复实现 peel 与环检测）；拼接 `"<oid>^{}"` 字符串再走 `resolve_object_spec_typed`——拒绝（以解析器间接调用私有语义，类型信息仍需二次读取）。
- **Consequences:** `--points-at` 参数侧（Git 不 peel 参数）与重复 `--points-at` 仍由 477b HW-05（#533）承接；`src/utils/util.rs` 属 GC-02 共享 helper，TT-05 按 ER-13 `T-1` 跑全量；TT-02 复用该包装判定 commit-ish 并取得终点类型。
- **Revisit when:** #533 改变 `--points-at` 参数侧语义，或 DEFER-TT-01 放开 tree / blob 目标。

### ADR-TT-04：目标参数在 TT-02 一个发布切片中完整交付

- **Status:** Accepted（R3 修订；取代 R1 的「三切片分阶段交付」）
- **Context:** R1 为满足 G-03 上限把创建拆为 TT-02（轻量 + 通用契约 G1 + 临时契约 G3）、TT-06（附注 / 签名 / 嵌套，移除 G3）、TT-07（把 G1 细分为 E1/E2/E4）。R3 评审指出中间契约本身需要大量只在中间版本存在的门（例如 G3 对五个旗标各需一组门，F19），而 EX-TT-01 获批后 G-03 上限已不再是拆分理由。
- **Decision:** 「`<commit>` 位置参数、全部创建模式（轻量、`-a`/`-m`/`-F`/`-e` 附注、`-s` 签名、`-f` 覆盖、嵌套）与 ADR-TT-02 的最终 E1–E5 契约」作为单一行为轴「tag 创建的显式目标」在 TT-02 一个切片中交付；不存在中间契约 G1 / G3；TT-06、TT-07 编号保留为墓碑。
- **Alternatives considered:** 保留三切片——拒绝：两个中间版本需要一次性门与两次额外发布，且中间文案需要在后续版本撤回；把 TT-05 也并入——拒绝：过滤器 peel 是独立可恢复的行为轴，且必须先于创建发布。

- 退出码门：只断言该场景主命令的进程状态码。
- 语义门：只断言命令之后的一项仓库事实（`rev-parse` 值、`cat-file -p` 前两行对象头、消息体、`HEAD^2`、过滤结果等）。
- 人读门：成功场景只断言主命令 stdout 与 inline 期望完全相等；失败场景只断言 `parse_cli_error_stderr` 拆出的人读部分与 inline 期望完全相等，或以 inline 期望开头（用法错误后接 clap / 提示行时），或与 inline 正则整体匹配（含动态对象 id 或底层细节时）——每门只取其中一种比较。
- `--json` / `--machine` 门：成功场景只断言信封 `data` 对象与 inline 期望相等；失败场景只断言信封 `(error_code, exit_code, message)` 三元组与 inline 期望（`message` 含动态细节时为整体正则）相等。
- 零写入门：只断言 GC-TT-02 定义的写入快照在命令前后相等。
- fixture 构造步骤（例如先 `libra tag v4.0`、先 `libra tag -m inner inner HEAD`）的成功是前置条件，失败即用例构造错误，不是独立的门。
