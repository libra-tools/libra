## 文档职责

### 适用范围

让 `show <rev>:./path` 与 `<rev>:../path` 按 Git 的 cwd 相对规则解析，让 `--quiet` 加显式格式仍打印格式行，并让 `show :<path>` 在人读、quiet、JSON 三条路径上报告真实的 index 错误。覆盖 TC-2627（t2070 #8，含 `show HEAD:./first.t` 与 `show :./first.t`）与 TC-2694（t7007 #16）。TC-3116 里 show `:<path>` 的部分由 I1043-03 守护；apply 的 `--directory` 与 `-p` 顺序及 TC-3116 目前暂列 I1043-04，卡片粒度和发布边界仍须重设计。

## 已决议设计决策

### ADR-I1043-01: show 的 rev:path 对 `./`、`../` 前缀按 cwd 解析

- **Status:** Accepted（2026-11-07 按 Claude R3 的 P1-1、P1-2 修订）
- **Context:** Git `resolve_relative_path`（`object-name.c:1701-1712`）只对以 `./` 或 `../` 开头的 spec 经 `prefix_path` 折叠全部 `.`/`..`，越出工作树报 `'%s' is outside repository at '%s'`（`setup.c:154`）；其余 spec 按字面量在树里查找。Libra 的 index 路径已按这一规则实现（`util.rs:2812-2824`），show 的树路径没有。
- **Decision:** 在 `show.rs` 内新增一个私有函数，供人读（`show_commit_file`，`show.rs:933`）、quiet（`validate_commit_file`，`:957`）与 JSON（`collect_commit_file_output`，`:1352`）三处 `<rev>:<path>` 共用：路径以 `./` 或 `../` 开头时，用公开的 `util::normalize_abs_path(util::cur_dir().join(path))` 折叠，再用 `util::is_sub_path` 判断是否在 `util::working_dir()` 之内，越界就返回 `CliInvalidTarget`（`LBR-CLI-003`，与现有 path-not-found 同族、同退出码），消息为 `'<spec>' is outside repository at '<worktree>'`（与 Git `setup.c:154` 和 `util.rs:2819` 相同），在内则用 `util::to_relative` 得到仓库相对路径；其余路径保持字面量（`HEAD:dir/../first.t` 仍按不存在的路径失败，与 Git 一致）。这与 `util.rs:2812-2824` 的 index 规则逐条相同；两处各约十行、调用同一组公开 helper，本计划不改 `util.rs`（GC-02 例外：抽到 util 会让本卡与写 `util.rs` 的活动卡冲突，等 util 写者释放后由后续卡合并，登记为 DEFER-I1043-HELPER）。
- **Alternatives considered:** 放宽 `util.rs:2753` 的共享解析器（会改变 rev-parse 等入口）；把中部 `..` 也保持字面量（与 Git 及 index 规则不一致）。
- **Consequences:** 越界失败时 stdout 为空。写集不含 `util.rs`。
- **Revisit when:** 所有 rev:path 入口都要接受 `./`。

### ADR-I1043-02: quiet 下只有 commit 对象的显式格式输出格式行

- **Status:** Accepted（2026-11-07 按 Claude R3 的 P1-7 修订）
- **Context:** 全局 quiet 合同（`src/cli.rs:282-284`、`docs/development/cli-error-contract-design.md:39-42`）要求 quiet 抑制全部 stdout；TC-2694 要求 `show --quiet --format=%s main3` 输出 `main3`；`show_test.rs:273` 要求裸 quiet 为空。
- **Decision:** quiet 时先照旧执行 `validate_show_quiet` 的全部校验（含补丁生成校验），校验失败就以现有错误退出、stdout 为空；校验通过后按下表输出：

| 情形 | quiet 下的 stdout | 与 Git |
|---|---|---|
| commit，显式 `--format`/`--pretty=<名或格式>`/`--oneline` | 只有该格式渲染的头部，不含 diff（`--pretty=medium` 按现有过滤输出默认多行头） | 相同 |
| commit，无显式格式 | 空 | Git 打印默认头部；登记差异 |
| commit，只有 `format.pretty` 配置 | 空（配置不算显式请求） | Git 打印头部；登记差异 |
| commit，显式格式加 diff 输出选项（`--stat`、`--shortstat`、`--name-only`、`--name-status`、`--raw`、`--patch-with-stat` 等） | 只有格式头部 | 有意差异：Git 的显式 diff 格式选项可重新启用 diff 输出；`--name-only` / `--name-status` 与 quiet 的组合则报错 |
| 带注释 tag、tree、blob（有无显式格式） | 空 | Git 打印 tag 头部与 blob 内容；登记差异 |

  show 是全局 quiet 合同的已登记例外：`docs/development/cli-error-contract-design.md` 在该段追加一句说明（显式格式请求在 `show --quiet` 下仍输出格式头部，issue #1043），`src/cli.rs` 的帮助不改（它描述的是全局默认）。
- **Alternatives considered:** quiet 总是打印 Git 默认头部（破坏 `show_test.rs:273` 与全局合同）；对 tag 也输出（tag 头部不经 formatter，格式语义不明确）。
- **Consequences:** 三份文档里「quiet 只验证、抑制 stdout」的句子改写为上表的事实；文档门核对旧句已删。
- **Revisit when:** 全局 quiet 合同改成 Git 的 per-command quiet。

### ADR-I1043-03: `:<path>` 的错误按种类映射，三条路径共用

- **Status:** Accepted（2026-11-07 按 Claude R3 的 P1-4 修订）
- **Context:** `resolve_index_path_typed` 对「不在 index」「在 index 但不在该 stage」「越界」返回 `InvalidReference`。`util.rs:2831-2834` 给所有 index 加载错误加上 `failed to read`，因此按 `:1995-2008` 的分类器归入 `ReadFailure`，包括损坏或截断的 index；不能宣称该路径返回 `CorruptReference`。show 在 `:403-405`、`:466-468`、`:1160-1162` 把这些错误一律改成 `bad revision`。FIX-LTR-05Q（`c0373cb`）规定读失败是 `LBR-IO-001`，不是 bad revision（`plan-20261025-qualification.md:842-860` 的 AC-1）。
- **Decision:** `show.rs` 内一个私有映射函数供三处共用：`InvalidReference(msg)` → `CliInvalidTarget`（`LBR-CLI-003`），消息用 util 的原文；`ReadFailure` → `IoReadFailed`（`LBR-IO-001`）；`CorruptReference` → `RepoCorrupt`（`LBR-REPO-002`）；其余变体保持现有 `bad revision`。必须改产品代码（现状输出 `bad revision ':x'`）。
- **Alternatives considered:** 再实现一遍解析器（重复且可能破坏 `:/` 搜索）。
- **Consequences:** JSON 错误信封的 `error_code` 随之区分。
- **Revisit when:** util 的错误枚举增加新变体。

**D 取自发布候选分支，不承接其它提交。** 第一段把同一个 SHA 同时推到 `main` 与 `release/v<VERSION>`。`base.yml` 的 push 触发是 `branches: [main, 'release/**']`，注释写明「Release candidates must finish even while main continues advancing」（`.github/workflows/base.yml:3-5`），`cancel-in-progress` 只对 PR 与 `refs/heads/main` 生效（`:13-15`）；`.github/workflows/codeql.yml:16` 的 push 同样包含 `release/**`；`cancel-superseded-main.yml` 只在 `main` 上触发、只取消 `main` 的 run；`release.yml` 只由 `v*` tag 触发，推候选分支不会发布任何东西。仓库先例：`release/v0.30.155` 上 SHA `3462306b` 的 base run 41976607602（约 178 分钟）与 CodeQL run 41976607585 在 2026-11-05 都是 success，该分支事后已删除（2026-11-07 查询远端为 404）；更早有 `release/v0.30.92`。所以第二段只认候选分支上 head SHA 等于本卡 SHA 的 run，正是 ER-04 D 的「同一 head SHA」，没有偏离，也不承接任何后继提交的结论。候选分支是发布授权范围内的远端 ref，不是功能分支，不开 PR，第四段在 release 全部成功后删除它。

上游前进时不用 `libra pull` 制造合并提交。若 C 组提交之后、第一段推送之前 `origin/main` 前进，按以下步骤恢复，每步失败都停止：
1. 此时工作区必须干净（本卡改动都已在 C 组提交里，工作区独占检查保证没有他人改动）。执行 `libra rebase origin/main`。它失败时执行 `libra rebase --abort`：abort 成功说明 rebase 遇到冲突，版本面冲突按第 2 步处理，其它冲突手工 rebase：`plan-status.md` 与 `COMPATIBILITY.md` 这类按行登记的文件以 `origin/main` 的版本为底、只重放本卡的行，其它文件按双方语义合并；abort 失败说明 rebase 根本没有开始（例如工作区不干净），按错误信息处理，不计入恢复次数。
2. 版本面冲突（上游改了版本）：`libra reset --mixed HEAD^` 撤销本卡尚未推送的 C 组提交，同时清空暂存区（只涉及本卡自己的改动；`--soft` 会把本卡改动留在暂存区，之后的工作区独占检查与暂存守卫都会拒绝，2026-11-07 在隔离仓库实测两者差别），`libra restore --source HEAD --worktree Cargo.toml Cargo.lock install.sh install.ps1` 把四个版本面文件恢复为此时 `HEAD`（本卡原基线）的内容，使随后的 `pull --ff-only --autostash` 无冲突地带入上游的新版本，然后从生命周期第 3 步的第 1 小步重新开始（外部前置检查与工作区独占检查、`pull --ff-only --autostash`、窗口检查、在上游版本上 bump、C 组全套）。
3. rebase 成功后，以 `PHASE=c` 运行提交后范围检查，并核对 `libra diff --name-only HEAD^ HEAD` 与 rebase 前 `libra diff --name-only "$C_COMMIT^" "$C_COMMIT"` 的路径集合相同，防止重放丢文件；再运行 bump 前窗口检查（它接受父提交为 `origin/main` 的本卡提交）与版本面内容检查（`VSRC=head`）。
4. 先运行「C 组结论携带检查」。上游增量只含文件名未被 `tests/`、`src/`、`build.rs` 与 `.github/` 引用的计划文件，以及增删行不含测试读取模式的 `plan-status.md` 改动时，C 组结论随重放携带：该检查在新树上重跑窗口检查与版本面内容检查并写下携带标记。其它任何增量（包括改到 `tests/compat/agent_architecture_guard.rs:8181-8215` 读取的 `plan-status.md` 行，以及被测试读取的计划文件：`tests/session_capture_docs_contract.rs:10` 与 `tests/opencode_hook_contract_test.rs:24` 编入其它计划文件）都以 C 组运行器在重放后的树上整套重跑本卡全部门与 C 组脚本（含双环境全量 nextest）；此时工作区干净，被测的树就是 `HEAD`。
5. 只在本文件「实施证据」更新 C 组收据（仓库里没有构建或测试读取 `docs/development/plan/issues/`），以 `PHASE=amend` 运行暂存守卫（它只允许本文件，并要求运行器为重放后的树写下的通过标记，或指向当前 `HEAD` 的携带标记），执行 `libra commit --amend -S --no-edit`：`libra rebase` 会把旧提交的 `gpgsig` 头逐字节复制到重放后的提交上（2026-11-07 在 0.30.157 与 0.30.158 上实测），但树与父提交已变，这个签名已经失效，所以签名头存在不代表签名有效，必须用 `-S` 重新签名；随后运行的「记录 C_COMMIT」会比较新旧两个提交的 `gpgsig` 块，相同就失败；原提交信息里的 `Signed-off-by` 随重放保留，不再加 `-s`（加了会出现两行，2026-11-07 已实测）。
6. 以 `PHASE=c` 再跑提交后范围检查，运行「记录 C_COMMIT」脚本，然后重新执行第一段。

需要整套重跑的恢复同一张卡最多 3 次（携带不计次数，但每次携带之后都要重新执行第一段）；第 4 次需要整套重跑时停止，把卡保持在 `in-progress` / `locally-accepted`，在「实施证据」记录每次的上游增量，并向用户报告，由用户决定是否协调其它写者暂停推送。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1043-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。

9. 放弃（释放家族串行锁）：本卡还没有任何推送到远端 `main` 的 C 组提交（状态文件没有 `PUSHED_SHA`），而外部前置长期不可用或用户决定改期时，可以放弃本卡：本地已有未推送的 C 组提交时先 `libra reset --mixed HEAD^` 撤销它；再用 `libra restore` 逐个撤销本卡写集内产品文件与版本面文件的改动、删除本卡新建的未跟踪文件（只限本卡允许集合内的路径）；`plan-status.md` 不整文件还原，只把本计划行改回；然后把 `Lifecycle / Acceptance` 改回 `pending` / 空并写明原因，同步 `plan-status.md` 本计划行，以 `PHASE=abandon` 运行暂存守卫，执行 `libra commit -S -s -m "docs(plan): abandon $CARD (#1043)"`，以 `PHASE=abandon` 运行提交后范围检查与计划目录推送脚本。「没有推送过」不只看可丢弃的本地状态文件：`PHASE=abandon` 的暂存守卫先 fetch，并向 GitHub 核对状态文件里的 `C_COMMIT`（若有）不在远端 `main` 上、`origin/main` 的版本仍等于当前 `HEAD`（撤销后的基线）的版本、下一 patch 版本的候选分支 `release/v<下一版本>` 与 tag `v<下一版本>` 都不存在；任一不满足（例如推送已经落地而状态文件还没写下 `PUSHED_SHA`）就拒绝放弃。已经推送过的卡不能放弃，只能按第 6 步修复或前滚。

**C 组运行器（`bash` 运行，`CARD` 为本卡 ID）：** 从本文件按下列固定锚点抽出脚本，所以执行的就是本文件里经过审查的门块，不靠执行者逐段复制。抽取规则：锚点在全文（或标注为本卡范围时在本卡 `Task` 标题到下一个 `Task` 标题之间）必须恰好出现一次，取它之后的第一个 `bash` 代码块，锚点与代码块之间不得隔着标题。Verification 门块按顺序拼成一个门块脚本，开头是 `set -eo pipefail`，块与块之间插入 `set +u`，在同一个 shell 里执行，所以前置块定义的函数可供后面的门块使用；C 组 fail-closed 脚本单独成一个脚本，在门块脚本通过之后以新的 `bash` 进程运行，门块里 TC 的 `export`（`LIBRA_BIN`、`TC_*`、`GIT_*` 等）因此不会带进 C 组的全量测试。任何一条命令失败，所在脚本立即非零退出，运行器随之停止。锚点只在正文里查找：代码块、「评审结论与修订记录」节与「实施证据」节都不参与匹配，所以脚本自身、日志与收据里出现同样的文字不会造成歧义。各卡的门块锚点及顺序就是下面脚本里 JSON 配置的 `gates`（`card` 表示只在本卡范围内查找），C 组脚本的锚点是 `c`。有 C 组提交的卡，门块脚本先跑 bump 前窗口检查、版本面内容检查（脚本开头导出 `VSRC=worktree`）与有网站面的卡的精确句预检，再跑本卡的 Verification 门块，所以这三项也由通过标记绑定，漏跑会被暂存守卫发现。运行器只接受 `MODE` 为 `normal`（缺省）或 `repair`，并原样传给门块脚本；工作区独占检查用的 `MODE=snapshot`、`MODE=verify` 由运行器在调用时单独设置。`no_c` 列出的卡没有 C 组提交，运行器拒绝它们，它们的门块只由 `PHASE=accept` 的暂存守卫重跑。
