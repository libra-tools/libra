## 已决议设计决策

### ADR-I1047-01: 排序只发生在非 verify 列表

- **Status:** Accepted
- **Context:** Git 的普通 show-ref 按 refname 排序；`--verify` 按参数顺序。
- **Decision:** 只在非 verify 列表排序。排序键是去掉末尾 `^{}` 之后的 refname 字节序，peeled 行紧跟自己的 tag，所以 `refs/tags/v1.0^{}` 不会排到 `v1.0-rc` 后面。不在 `collect_raw_show_ref_entries` 里排序，以免拆开 tag 和 peeled 行。`execute_verify` 仍按参数顺序。
- **Alternatives considered:** 按带 `^{}` 的全名排序。`^` 的字节会把 peeled 行插到别的 tag 中间，和 `docs/commands/show-ref.md` 的现有示例不一致。
- **Consequences:** HEAD 的 refname 是 `HEAD`，按字节序排在 `refs/` 之前。
- **Revisit when:** 出现不以 `refs/` 开头的非 HEAD refname（Git `builtin/show-ref.c:214-215` 已把 HEAD 固定在第一行，Libra 按字节序也得到同一结果）。

### ADR-I1047-02: verify 保留紧随的 peeled 行

- **Status:** Accepted
- **Context:** peeled 行的 refname 不是用户传入的名字，精确过滤会丢掉它。
- **Decision:** `--verify` 且 dereference 时，若收集结果里有紧挨着的 `name^{}` 条目，把它跟在对应 tag 后面输出。
- **Alternatives considered:** 让 verify 走普通列表再过滤。会改变 argv 顺序。
- **Consequences:** 轻量 tag 没有 peeled 对象，不额外输出。
- **Revisit when:** peel 规则扩展到非 tag。

4. 先运行「C 组结论携带检查」。上游增量只含文件名未被 `tests/`、`src/`、`build.rs` 与 `.github/` 引用的计划文件，以及增删行不含测试读取模式的 `plan-status.md` 改动时，C 组结论随重放携带：该检查在新树上重跑窗口检查与版本面内容检查并写下携带标记。其它任何增量（包括改到 `tests/compat/agent_architecture_guard.rs:8181-8215` 读取的 `plan-status.md` 行，以及被测试读取的计划文件：`tests/session_capture_docs_contract.rs:10` 与 `tests/opencode_hook_contract_test.rs:24` 编入其它计划文件）都以 C 组运行器在重放后的树上整套重跑本卡全部门与 C 组脚本（含双环境全量 nextest）；此时工作区干净，被测的树就是 `HEAD`。
5. 只在本文件「实施证据」更新 C 组收据（仓库里没有构建或测试读取 `docs/development/plan/issues/`），以 `PHASE=amend` 运行暂存守卫（它只允许本文件，并要求运行器为重放后的树写下的通过标记，或指向当前 `HEAD` 的携带标记），执行 `libra commit --amend -S --no-edit`：`libra rebase` 会把旧提交的 `gpgsig` 头逐字节复制到重放后的提交上（2026-11-07 在 0.30.157 与 0.30.158 上实测），但树与父提交已变，这个签名已经失效，所以签名头存在不代表签名有效，必须用 `-S` 重新签名；随后运行的「记录 C_COMMIT」会比较新旧两个提交的 `gpgsig` 块，相同就失败；原提交信息里的 `Signed-off-by` 随重放保留，不再加 `-s`（加了会出现两行，2026-11-07 已实测）。
6. 以 `PHASE=c` 再跑提交后范围检查，运行「记录 C_COMMIT」脚本，然后重新执行第一段。

需要整套重跑的恢复同一张卡最多 3 次（携带不计次数，但每次携带之后都要重新执行第一段）；第 4 次需要整套重跑时停止，把卡保持在 `in-progress` / `locally-accepted`，在「实施证据」记录每次的上游增量，并向用户报告，由用户决定是否协调其它写者暂停推送。

第一段会机械检查：工作区干净；当前分支是 `main` 且 `main` 指向被检查的提交；它就是状态文件里的 `C_COMMIT`（C 组提交之后、第一段之前不再叠加任何提交，rebase 恢复的 amend 之后会重新记录）；它只有一个父提交；它相对父提交只改本卡允许集合内的路径；正常模式下四个版本面文件只改了版本行且版本为父提交版本的 patch + 1，修复模式下版本面不变、版本等于父提交版本；该版本还没有 tag；正常模式下父提交的版本（bump 前的基线）已经有 tag，即没有别的发布在途（窗口检查的同一条件，在推送前机械复核）。随后按远端事实推进：该 SHA 已在远端 `main` 上（上一次第一段推送已落地但没有写完状态文件）时跳过 `main` 推送；否则要求父提交就是当前的 `origin/main`，经临时本地分支 `c-push-1047-<CARD>`（检查之后才强制指向被检查的 SHA）推送。推送失败时先看远端：`origin/main` 等于该 SHA 或 GitHub compare 显示它已在 `main` 上，就算成功；`origin/main` 没动是认证、网络或服务端错误（ER-09），直接停止；`origin/main` 已前进到别处，回到上面的恢复步骤。确认在 `main` 上之后立即写入 `PUSHED_SHA` 与 `VERSION`，再处理候选分支：正常模式要求它不存在（或已经指向该 SHA），修复模式要求它存在且是该 SHA 的祖先，然后以快进推送，推送后回读远端分支必须等于该 SHA。所以第一段在任何一步中断后都可以原样重跑。

本检出中 `libra merge-base` 实测约 55–71 秒（2026-11-07，多会话并行时更慢）。签名与 DCO 直接读 `libra cat-file -p` 的提交对象：`libra log -1 --only-trailers --trailer Signed-off-by` 返回的是最近一个带该 trailer 的祖先提交（2026-11-07 实测），不能证明被检查的提交本身带 DCO。四段脚本不调用 `libra merge-base`：快进由「父提交等于 `origin/main`」判定，祖先关系交给 GitHub compare API。

第二段，轮询候选分支上本卡 SHA 的 CI。只认 `--branch release/v<VERSION>`、event 为 push、head SHA 等于 `PUSHED_SHA` 的 run（同一 SHA 有多个时取 ID 最大的）。上限：`base.yml` 7 小时，它的 `test` job 自身超时为 350 分钟（`.github/workflows/base.yml:346`），近期成功 run 用时 138–192 分钟（main 上 42353154227、42310585761，`release/v0.30.155` 上 41976607602 约 178 分钟）；`codeql.yml` 本段等待 90 分钟（workflow 未设 `timeout-minutes`，平台默认 360 分钟；先例 41976607585 约 23 分钟）。判定规则：
- success 即通过，run ID 写入状态文件，供第三段复核。
- cancelled、failure、timed_out 或 startup_failure：同一 SHA 每个 workflow 最多重跑一次（cancelled 与 startup_failure 用 `gh run rerun`，startup_failure 没有可重跑的失败 job；failure 与 timed_out 用 `gh run rerun --failed`，排除基础设施或偶发失败，对应 ER-10 的有界重试）；重跑记录（SHA 与发起时的 attempt）写入状态文件，attempt 没有增加之前不按旧结论判定。重跑后仍不是 success 时非零退出，转入生命周期第 6 步的修复模式（先按 ER-13 在本地复现，确认与本卡无关时向用户报告，不在写集外修改）。
- 其它结论（如 skipped、neutral、action_required）一律非零退出，不算成功。
- `gh` 查询失败按瞬时错误处理，30 秒后重试，计入同一上限。上限内仍没有结论时，本段以超时退出，本卡保持 `in-progress` / `remote-pending`；之后可原样重跑本段继续等待。
