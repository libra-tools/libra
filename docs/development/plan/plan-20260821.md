## 文档职责

本文把 UP-01 设计稿中落在 **libra 仓库** 的范围拆成可执行任务卡：客户端 upgrade 模块的最后缺口（trust table、单调 generation floor）、`release.yml` 的 workflow 卫生与 publish 调用、`install.sh` / `install.ps1` 的 fail-closed 验签、契约测试补齐。

本文只规划任务，不宣称实现完成。落地时每个任务都必须先刷新源码锚点，再按任务卡验收。

### 适用范围

- `src/internal/upgrade/`（trusted_keys、state floor、transition 不变式测试）
- `.github/workflows/release.yml`（workflow 卫生、digest 汇总、`request-stable-manifest` job、environment 划分）
- `install.sh` / `install.ps1`（预置公钥、manifest 验签下载、fail-closed 收敛）
- `tests/upgrade_publish_contract_test.rs` 等测试目标与 `tests/INDEX.md`
- 密钥 ceremony 的公开半边（公钥入库；私钥侧在 libra-backend 计划）

### 非目标

- Backend publish / broker / renew / emergency / Admin UI--由 `libra-backend` 姊妹计划承接（`docs/development/internal/release-signing-auto-upgrade.md` §5–§8）。
- signing Worker 拆分、外部 KMS/HSM、SLSA attestation（设计稿 §10.1 第 9/10 条，未补冻）。
- standby key 预置（设计稿 §7 第 5 条，仅「建议补冻」；若补冻须先改设计稿再改本计划）。
- bucket lock 配置（Cloudflare 控制台动作，登记在上线检查清单，非本仓库代码）。

### 成功定义

- 客户端 `PRODUCTION_TRUSTED_KEYS` 非空版本（**0.22.1**，D9，经 A1-08a/A1-08b 版本跃迁卡到达）发布；upgrade state 持久化单调 generation floor。
- `release.yml` 无 pipe-to-shell、action 全部钉 SHA、四平台 digest artifact 强制产出、Windows 补 `.sha256` 与无后缀副本。
- tag 发布经 OIDC 调用 Backend publish 成功后 release 绿；未签或签名失败 release 红、客户端 fail-closed 不升级。
- `install.sh` / `install.ps1` 预置公钥并对 stable manifest 验签后下载，验签失败 fail-closed。
- 所有卡 `Lifecycle=done` 且 `Acceptance=complete`，计划完成门全绿。

## 已决议设计决策

设计稿 D1–D10 直接构成本计划的 ADR 集，引用而非复制；下列为本计划新增的裁决。

### ADR-UP01-01: 客户端契约零改动

- **Status:** Accepted（继承设计稿 §3）
- **Context:** 客户端 fail-closed 合同已实现并被契约测试钉死。
- **Decision:** 本计划所有卡不得修改 `src/internal/upgrade/manifest.rs` 的 URL 语法、envelope 结构、验签流程；只做增量（trust table 填值、state floor 字段）。
- **Alternatives considered:** 顺带重构 upgrade 模块--拒绝（多轴）。
- **Consequences:** 发布侧必须满足既有契约。
- **Revisit when:** 设计稿修订。

### ADR-UP01-02: trust table 非空版本绑死 0.22.1（D9），经 A1-08a/A1-08b 版本跃迁到达

- **Status:** Accepted（继承 D9；Claude R1 P0-1 修订）
- **Context:** 首个 trust 客户端版本已冻结为 `0.22.1`；当前仓库 `0.20.3`，仅靠本计划各卡 `patch + 1` 构造性不可达。
- **Decision:** 新增 A1-08a/A1-08b（两张 `release` 类型版本跃迁卡，Claude C-R2 P1-7 拆分：每卡一次发布切片）显式承担 `0.20.x -> 0.21.0` 与 `0.21.0 -> 0.22.0` 两次 minor 递增（依据见 ADR-UP01-05）；A1-02 依赖 A1-08b，在仓库版本到达 `0.22.0` 后执行，本卡自身 `patch + 1` 即产出 `0.22.1`。
- **Alternatives considered:** 修订设计稿 D9 改为「当值 patch 版本」--不采纳（D9 已冻结，改冻结决策成本高于一张跃迁卡）；把 minor 递增塞进某张行为卡--拒绝（违反 ER-08「不得用 patch 夹带 / 不得静默改写 minor」）。
- **Consequences:** A1-05（install 验签流程）依赖 A1-02 的公钥定值；A1-08a/A1-08b 在发布窗口中位于 A1-02 之前。
- **Revisit when:** D9 修订。

### ADR-UP01-03: install 脚本 fail-closed 契约统一

- **Status:** Accepted（设计稿 §10.1 第 3 条建议稿）
- **Context:** 脚本从同一可写 CDN 分发，内嵌公钥不能防整体替换；bootstrap 信任锚须带外（GitHub repo 公布哈希）。
- **Decision:** A1-05 落地后：manifest 拉取/验签失败即 fail-closed（未签名回退仅 `LIBRA_ALLOW_FALLBACK=1` 显式 opt-in 保留语义、PowerShell 对齐）；`-v` 指定历史版本与自定义 mirror 为显式 opt-in 的未验签路径。
- **Alternatives considered:** 保持 PowerShell 静态版本默认--拒绝（无校验面）。
- **Consequences:** 需同步 README 与安装文档的信任假设说明。
- **Revisit when:** 设计稿 §10.1 第 3 条补冻。

### ADR-UP01-04: release.yml ↔ broker 调用契约以设计稿为唯一事实源

- **Status:** Accepted（消除跨仓双向依赖闭环，Codex R1 P1-1）
- **Context:** `A1-04`（workflow 调用方）与 backend `B1-05`（broker 实现）若互为前置会形成跨仓闭环，计划不可执行。
- **Decision:** 调用契约（`aud`、三类 `environment`、请求体字段、presigned PUT 头、对象键白名单）以设计稿 §5.2/§5.3 的冻结文本为唯一事实源（版本以设计稿 git commit 锚定）；本计划与 backend 计划各自**消费**该契约、互不构成硬依赖。backend 交付的 broker 端点（原 DEP-03）对 A1-04 为 **informational**。A1-09（upload jobs 真实接入 broker）**硬依赖** DEP-03：该卡的范围本身即「接入已上线的 broker」，端点未上线时置 `blocked`。
- **Alternatives considered:** 把契约抽为独立合同文档--拒绝（设计稿 §5.2 已是冻结契约，再抄一份即两个事实源）。
- **Consequences:** A1-04 用合成 OIDC JWT fixture 即可完整验收；真实 broker 联调证据归 A1-09 的 D 组/上线检查清单。

### ADR-UP01-06: 安装器验签原语选型（Claude C-R5 P1-4）

- **Context:** A1-05 要求两个安装器默认路径对 stable manifest 做 Ed25519 验签、失败 fail-closed。设计稿 §10.1 第 3 条将「install.sh 验签选型（openssl / 其它）」列为待讨论项，尚未冻结；PowerShell 侧无原生 Ed25519（CNG/.NET BCL 均不支持），POSIX 侧 `openssl pkeyutl -verify` 需 OpenSSL 1.1.1+，「验签器不可用」是与「验签失败」不同的第三态。
- **Decision:** 冻结为：POSIX `install.sh` 走 `openssl pkeyutl`（运行前版本探测，OpenSSL < 1.1.1 判为「验签器不可用」）；PowerShell `install.ps1` 嵌入随脚本分发的最小独立 verifier（自包含、无模块依赖）；「验签器不可用」-> 与 manifest 404 同档的显式确认过渡路径（提示 + 用户确认/`LIBRA_ALLOW_FALLBACK=1`），不静默跳过、不直接 fail-closed 到不可用。本决策回写设计稿 §10.1 补冻（本计划开工前同步设计讨论稿变更记录）。
- **Alternatives:** BouncyCastle 模块依赖（需网络拉取，bootstrap 阶段不可接受）；降级为纯 opt-in 未验签（削弱 D9 首个信任版本语义，弃）。
- **Consequences:** A1-05 的 AC 与冒烟增「验签器不可用」场景（第七场景）；scope 维持 M（verifier 以最小独立脚本随安装器分发，计入本卡 prod-files）。

### ADR-UP01-05: 版本跃迁卡（0.21.0 / 0.22.0）的 minor 递增依据

- **Status:** Accepted（Claude R1 P0-1）
- **Context:** ER-08 规定 `minor` 仅用于「删除公开 surface 或破坏兼容的 schema/协议变更」，且须 ADR + 兼容窗口证据；本计划需要到达 0.22.x 而 patch 递增不可达。
- **Decision:** 到达 0.22.0 的两次 minor 递增由 A1-08a/A1-08b（`release` 类型，各承担一跳）显式承担，依据：0.22.x 激活自动升级协议表面（客户端从构造性 inert 转为主动验签升级）属**用户可见的协议级行为变更**，符合 ER-08 minor 的「协议变更」通道；兼容窗口证据 = 客户端 fail-closed（无 trust key 版本对新 manifest 构造性忽略，`tests/upgrade_publish_contract_test.rs` 钉死）+ 老版本不受影响（publish 前各版本行为不变）。每卡一次 `gh release`（Claude C-R2 P1-7：删除 EX-01--ER-08 minor 递增条件不在模板 waiver 白名单内，改为由 ADR-UP01-05 的「协议表面激活」论证直接满足 ER-08 minor 通道本身，无需豁免）；补偿 = 两卡均无任何代码变更、纯版本面，review 仅核对版本面五处 parity。
- **Alternatives considered:** 修订 D9（不采纳，见 ADR-UP01-02）；由其它计划承担（无此计划，且会引入新的悬空 DEP）。
- **Consequences:** 版本面五处出现两次 minor 跳变；`tests/compat/version_surface_sync` 只校验一致性、不校验增量幅度，不受影响。
- **Revisit when:** D9 修订或模板 ER-08 修订。
